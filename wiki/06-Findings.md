## Что доказано надёжно

### 1. Выбор метода зависит от размера задачи
| Размер | Лучший метод |
|---|---|
| ≤25 рейсов | TF-Kotlin standalone (LA) — ансамбли не дают diversification benefit |
| 25–50 | Independent parallel (classic / B1 / H) |
| 50–100 | Process-isolated cooperative (I-iso пик / I_8-iso стабильность) |
| День хаба (~1 358) | **single-stage «всё сразу»** (лучший per-slot) |
| Месяц/сеть (тысячи) | декомпозиция (по неделям/флоту/дням) |

### 2. Single-stage vs two-stage — это вопрос МОДЕЛИ ПРАВИЛ, не алгоритма ⭐ (финал, re-scoring)
Re-scoring (развёртка наряда «через ротации» на реальные рейсы, 100%
покрытие 6 824/6 824, оценка **исходными** правилами; sanity: re-score
одиночного решения совпал с решательским до цифры):
| Наряд | Hard (исходные правила) | Soft |
|---|---:|---:|
| всё сразу (all_at_once) | **0** | −1 639 021 |
| через ротации (развёрнутый) | **−10 570 995** | **−1 092 293** ← на 33% удобнее |

98% hard-нарушений — **min-rest**: исходное правило «10 ч отдыха между
любыми двумя рейсами» штрафует каждую 60-минутную стыковку внутри рабочего
дня ротации (4 037 нарушений). **Модели кодировали разные операционные
миры:** плоская — «экипаж летает ~1 плечо и отдыхает 10 ч» (нереалистично),
ротационная — «плечи цепляются в рабочий день» (реалистично, но нелегально
по плоским правилам v1).

**РАЗВЯЗКА (RULES v2):** после рефакторинга правил отдыха под duty-периоды
(зеркало порогов генератора) прямая расстановка **выиграла по обеим осям**:
0 hard и **−939 150 soft** против −248 225 hard / −1 092 293 у ротационного
наряда. Само разрешение цеплять плечи дало прямому солверу −43% неудобства
(−1 639k → −939k); дальше он обошёл ротации ещё на 14%, потому что
оптимизирует реальную цель напрямую, а two-stage — искажённую synthetic-цель
(H8 считает duty-span как налёт). Gap-статистика подтверждает механизм:
2 582 легальные стыковки, до 5 плеч в день, ноль нарушений.
**Итоговое правило: на дне узла при реалистичных duty-правилах прямая
расстановка (Timefold, всё сразу) — лучший подход и по легальности, и по
удобству; преимущество ротационной декомпозиции на этом масштабе было
иллюзией более мягких правил.** Остаточный дефект — у генератора ротаций
(смены >14 ч, −248k), не у концепции.

### 3. На задаче ротаций ВСЕ полные решения сходятся к одному плато; портфель/обмен не дают ничего ⭐ (финал, тройная проверка)
История в три итерации: (v1) «обмен = без обмена» — контаминированный
харнесс; (v2) «портфель выигрывает 43%» — **артефакт частичной
инициализации**: CH на синтетике (3 031 × 9 097) требует ~300s, интервал —
150s; «выигрышные −554k» были расписаниями с ~50% пустых слотов (пустые не
штрафуются, строка счёта этого не выдаёт). (v3, контроль полноты вживую):
интервал 1 — ни одного полного, 1 535 пустых; первое ПОЛНОЕ решение =
−991 846 = плато; финал ансамбля −991 816 ≈ одиночное плато −991 812…835.
**Все проверенно-полные результаты (любой метод, любые сиды) = плато
≈ −991,8k.** Плато структурное — это, по-видимому, оптимум данной
synthetic-задачи. Урок: сравнивать счета можно только у решений с
подтверждённой полнотой (считайте null-слоты!).

### 4. Process isolation качественно лучше in-JVM
Изоляция убирает GC/JIT/memory contention; per-island throughput
17k → 33k moves/sec (~×2). Обязательна для надёжных ансамблей.

### 5. Cooperative migration > independent parallel на больших задачах
На S5 independent даже не пробивает feasibility за 1200s; I-iso/I_8-iso
надёжно достигают 0 hard и улучшают soft на 20–25% против single-LA.
(Это про **наличие портфеля стилей**, не про сам обмен — см. п.3.)

### 6. OR-Tools не масштабируется на ассайнмент-задачу
Точный оптимум на малых (S1–S3 за секунды), но OOM/таймаут уже на S5+ и на
synthetic-ассайнменте BTS. На pairing-этапе (Stage 1, структурно проще)
справляется отлично. Workers > число ядер — только латентность, без качества.

### 7. Construction-heuristic lever (FFD) НЕ помог S4
FFD реализован корректно (компаратор по дефициту годного экипажа,
подтверждено что сортировка идёт), но даёт построение, идентичное First Fit.
Причина: экипажа достаточно (10–30 годных на слот) → First Fit
order-invariant. Метрика трудности «мало годных» оптимизирует не ту ось.
→ Диверсификация CH по островам (#3) на S4 унаследовала бы тот же ноль.

### 8. Плато S4 — это SUPPLY-проблема (дефицит type rating), не search ⭐
Ключевой capstone-вывод. Диагностика (Python per-constraint breakdown, т.к.
`analyze()` Enterprise-only): плато зафиксированного S4 = **type rating
3×50=150 (68%)** + flight conflict 70. Магнитудные правила (отдых, часы) не
нарушены и уже пропорциональны.

**Все search-рычаги упёрлись в одну и ту же стену — 3 нарушения type rating:**
| Метод | Результат на pinned S4 |
|---|---|
| single-LA (FF) | 6–7 конфликтов + 3 type rating |
| FFD (#1) | построение = FF (order-invariant) |
| gradient smoothing (#5, ∝ overlap) | конфликты 7→6, type rating держится |
| **classic ансамбль +SA, n=5** | **все 5: −268h, 6 конфликтов, 0/5 feasible** |

**Калибровочный тест (решающий):** дали всему экипажу все допуски →
type rating **150 → 0**, счёт **−268h → −22h**, конфликты **6 → 2**.

**Вывод:** блокер S4 — **структурный дефицит type-rated экипажа** (в пиковые
времена рейсов типа T больше, чем рейтингового экипажа). Нельзя посадить
рейтингового, которого нет — ни SA, ни FFD, ни градиент этого не создадут.
**Фикс — калибровка crew** (как на BTS §9.2), не тюнинг алгоритма.

### 9. Мета-урок: сначала диагноз «supply vs search», потом алгоритмы
FFD, #5 и ансамбль на S4 дали ноль/маргинал, потому что все целили в поиск,
а проблема была в снабжении. **Прежде чем тюнить solver — сделать
per-constraint breakdown и понять, инфизибилити структурная (supply) или
это застревание поиска.** Структурную search не лечит.

## Что пока НЕ подтверждено / открыто
- Multi-trial на S6 (есть только single-trial).
- Помогает ли сглаживание градиента жёстких штрафов (#5) на S4.
- Temporally-aware difficulty signal для FFD.
- Two-stage на данных с короткими рейсами / плотной сетью (где он должен
  выигрывать) — на демо рейсы long-haul, two-stage в невыгодных условиях.

```python
def pick_solver(num_flights):
    if num_flights <= 25:   return "TF-Kotlin standalone (LA)"
    if num_flights <= 50:   return "Compr classic (in-JVM 4-island)"
    if num_flights <= 100:  return "I_8-iso (process-isolated)"
    if num_flights <= 1500: return "single-stage (план всё сразу)"
    return "decomposition by week/fleet/day"
```
