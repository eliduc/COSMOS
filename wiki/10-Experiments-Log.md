## RULES v2 — доменный рефакторинг правил отдыха + финальное сравнение
**Сделали:** Kotlin-провайдер переведён на duty-периоды — «Min rest 10 ч
между любыми рейсами» заменён «Minimum turnaround» (≥60 мин) +
«Rest between duty periods» (мёртвая зона 6–8 ч нелегальна, ≥8 ч = отдых);
пороги — точное зеркало `pairing_generator` (примирение моделей). 22
ограничения (10 hard). Python-зеркала обновлены; `constraints.py` (JPype,
v1) помечен как неавторитетный.
**Мгновенная проверка сохранённых нарядов:** ротационный −10,57M → **−248k
hard (−97,7%)** — стена min-rest рухнула, остаток = смены >14 ч (дефект
генератора, открытый №1а); старый плоский наряд остался 0 hard, soft без
изменений (sanity ✓).
**Финал (`_run_duty_solve.py`, свежий прямой solve под v2, 1200s):**
| Наряд | Hard | Soft |
|---|---:|---:|
| **всё сразу (v2)** | **0** | **−939 150** |
| через ротации | −248 225 | −1 092 293 |
| всё сразу (v1, для сравнения) | 0 | −1 639 021 |
Разрешение цеплять плечи дало прямому солверу **−43%** неудобства; он
реально цепляет (2 582 стыковки 60мин–6ч, до 5 плеч/день, 0 нарушений) и
**обходит ротационный наряд на 14%** — тот оптимизировался на искажённой
synthetic-цели. **Вывод: на дне узла при реалистичных правилах прямая
расстановка побеждает по обеим осям; преимущество ротаций было иллюзией
мягких правил.** *(n=1; прямой solve seed-стабилен по v1-замерам.)*
**Артефакты:** `_run_duty_solve.py`, `_duty_full_solved.json`.

## Re-scoring — ФИНАЛ ветки «всё сразу vs через ротации» + вскрыт артефакт v2
**Сделали:** score-only endpoint `/schedules/score` (`SolutionManager.update`
— Community, в отличие от Enterprise-only `analyze`); sanity — re-score
полного решения совпадает с решательским счётом до цифры. Развёртка наряда
«через ротации» на реальные рейсы (`expand_onto_real`, zip по (рейс, роль,
порядок)): покрытие **100%** (6 824/6 824), 978 лишних крю отброшено.
**Смоук вскрыл артефакт v2:** «решённый» ансамблем синтетик имел **2 127 из
3 031 слотов ПУСТЫМИ** — CH на синтетике требует ~300s, интервал 150s;
пустые слоты не штрафуются, строка счёта не выдаёт неполноту → «выигрыши
−554k» v2 были полу-пустыми расписаниями. Контрольный прогон с учётом
полноты (только полные решения в зачёт): интервал 1 — ни одного полного
(1 535 null), первое полное = −991 846 = плато, финал −991 816. **Вывод
v2 о портфеле снят; все полные решения = плато −991,8k.**
**Главный результат (единая шкала, исходные правила):** всё сразу
0h/−1 639 021; через ротации −10 570 995h/−1 092 293 — **на 33% удобнее по
soft, но катастрофически нелегально**: 98% hard = min-rest (10-часовой
отдых между любыми рейсами против 60-минутных стыковок внутри ротаций,
4 037 нарушений). **Сравнение подходов — вопрос модели правил отдыха, не
алгоритмов.** Следующий шаг — duty-период-рефакторинг (открытый №1).
**Артефакты:** `_run_rescoring.py`, `_rescoring_full_solved.json`,
`_rescoring_synth_solved.json`, `_rescoring_expanded.json`.

## Аудит сессии + чистый re-run v2 — ПЕРЕСМОТР выводов по BTS
**Аудит нашёл два фатальных изъяна старого multi-trial:** (1) контаминация —
`solve_with_timefold_kotlin` мутирует расписание на месте, а харнесс
передавал один объект во все trial'ы → trial 2–5 warm-start'ились от
предыдущего (улики: first_feasible=2.0s на холодной задаче из 6 824 слотов,
монотонное улучшение soft «между trial'ами»); (2) seed-монокультура — все
solver'ы и острова делили random-seed=0 → «повторы» меряли дрожание
таймера, LA-остров ансамбля был идентичен одиночному прогону. Плюс: выброс
SA −623k был ошибочно списан на сон (тот прогон был здоров), per-slot
нормализация single↔two-stage несопоставима, «6 островов хуже 4» строилось
на кросс-машинном сравнении.
**Фикс (v2):** `_run_bts_multitrial_v2.py` — сырые JSON + deep-copy на
trial, свежие JVM, `randomSeed` в Kotlin endpoint, свой seed на
trial/остров/интервал; адверсариальное ревью харнесса перед запуском;
эмпирическая проверка seed-проводки.
**Чистый результат (n=5, 1200s):** ансамбль −187,2/слот медиана (бимодален:
3/5 → ~−185, 2/5 → плато), all_at_once −240,6 (размах 0,3), без обмена
−327,2 (размах 0,0). Интервальные логи: все выигрыши — интервал 1
(портфель стилей × сидов); обмен ни разу не улучшил допустимое решение.
**Пересмотрено:** «ансамбль бесполезен» → опровергнуто (артефакт
монокультуры); «всё сразу на 27% лучше» → снято (нужен re-scoring).
**Артефакты:** `_run_bts_multitrial_v2.py`, `data/bts_multitrial2_results.csv`
(колонка run_id); старый `bts_multitrial_results.csv` — недействителен.

## Эксперимент: остаточный шаг — калибровка → чистый 0 hard на S4
**Лесенка на зафиксированном S4** (метрика — число нарушений):
| Шаг | Результат |
|---|---|
| single-LA (грязь) | type rating 150 + 7 конфликтов |
| + gradient smoothing #5 | конфликты 7→6 (маргинал) |
| + ансамбль classic+SA, n=5 | конфликты 6, 0/5 feasible |
| + cross-training (все допуски) | type rating 0, **−22h, 2 конфликта** |
| + **удвоенный экипаж (180)** | **0 hard, 0 конфликтов, 3/3 feasible** (обычный single-LA!) |
**Вывод:** обе стены S4 — дефицит снабжения (рейтинги + количество). Как
только снабжение адекватно, **простейший одиночный планировщик достигает
feasibility мгновенно** — ансамбль не нужен. Ни один search-метод не помог,
пока была нехватка; когда её убрали — хватило самого простого.
**Артефакты:** `_s4_calibrated.json`, `_s4_calibrated_2x.json`.

## Эксперимент: ансамбль + калибровка на pinned S4 — РАЗГАДКА S4
**Вопрос:** пробивает ли диверсификация поиска (SA) плато S4 до feasibility?
**Ансамбль classic (LA+SA+TABU+GD), 300s, n=5** на зафиксированном S4:
**все 5 trial'ов −268h, 6 конфликтов, 0/5 feasible** — SA снизил конфликты
7→6, но **3 type rating (150) неподвижны**. Не гоняли миграцию (I) — она тоже
только поиск, упрётся в ту же стену.
**Калибровочный тест (решающий):** дали всему экипажу все допуски (убрали
дефицит рейтингов) → type rating **150→0**, счёт **−268h→−22h**, конфликты
**6→2**. **Доказано: блокер S4 — структурный дефицит type-rated экипажа
(supply), не поиск.** Фикс — калибровка crew (как на BTS §9.2).
**Мета-урок:** сначала диагноз supply-vs-search (per-constraint breakdown),
потом алгоритмы. FFD/#5/ансамбль дали ноль, потому что целили в поиск, а
проблема в снабжении. См. [06 — Выводы №8,№9](06-Findings.md).
**Артефакты:** `_run_s4_ensemble.py`, `_run_s4_calibrated.py`.

## Эксперимент: #5 — сглаживание градиента жёстких штрафов (S4)
**Гипотеза:** LS застревает на плато, потому что плоские жёсткие штрафы не
дают уклона. **Диагностика:** `SolutionManager.analyze()` оказался
**Enterprise-only** (500 в Community) → написали Python-breakdown
(`_run_constraint_breakdown.py`), считающий вклад каждого жёсткого правила
по решённому расписанию; совпадает со счётом решателя до цифры.
**Что нашли:** плато S4 состоит из **бинарных** нарушений — один инстанс:
100% flight conflict; зафиксированный инстанс: **Type rating 3×50=150 (68%)**
+ flight conflict 7×10=70. Магнитудные правила (отдых, суточная смена,
месячные/недельные часы) **не нарушены вовсе** и так уже пропорциональны —
#5 там нечего чинить.
**Тест:** сделали flight conflict пропорциональным наложению (в часах,
`ofHard(1)×overlap_h`) и прогнали FF на зафиксированном S4 (4 раза):
конфликты **7 → 6** (градиент реально помог обменять большое наложение на
меньшее — плоский штраф такой ход видел как ноль). Но **feasibility не
достигнута** — бинарный type rating (150) блокирует.
**Вывод:** #5 даёт **маргинальный** выигрыш (−1 конфликт), не пробивает S4.
Настоящий блокер — структурный дефицит type rating (3 слота не получают
рейтингового экипажа в свои времена): бинарен, не сглаживается. Лечится
калибровкой crew или диверсификацией поиска (ансамбль ранее дотягивал до
−70h), а не градиентом. Пропорциональный flight conflict **оставлен** — он
консистентен с пропорциональным стилем остальных временных правил и не
влияет на feasible-прогоны (там конфликтов нет).
**Артефакты:** `_run_constraint_breakdown.py`, `_run_conflict_test.py`,
`_s4_pinned.json` (зафиксированный инстанс), endpoint `/schedules/analyze`
(оставлен, но Enterprise-only → 500 в Community).

## Эксперимент: construction-heuristic lever на S4 (FFD)
**Гипотеза:** feasibility выигрывается на этапе черновика; диверсификация
острова сейчас только по acceptor'у, а CH у всех один (FIRST_FIT).
**Сделали:** реализовали FFD + difficulty-компаратор (по дефициту годного
экипажа: навык + допуск на тип, тай-брейк длительностью), параметр `ch` у
`/schedules/single`. Прошли API-переход 2.0
(`comparatorFactoryClass`/`ComparatorFactory`) и обход бандла FFD через
`ALLOCATE_ENTITY_FROM_QUEUE + DESCENDING` (см. [грабли §6,§7](08-Gotchas.md)).
**Результат:** **null** — FFD даёт построение, байт-в-байт совпадающее с FF.
Подтвердили, что сортировка реально идёт (`compare()` ~2400 вызовов = одна
сортировка 292 сущностей). Причина: экипажа достаточно (10–30 годных/слот),
First Fit order-invariant; узкое место S4 — **временные** конфликты.
**Вывод:** CH-рычаг не для этой структуры данных; #3 (CH по островам) на S4
унаследовал бы ноль. Инфраструктура `ch` оставлена (корректна, пригодится на
данных с дефицитом квалификации).
**Следующее (обсуждалось):** #5 — сглаживание градиента жёстких штрафов
(целит в LS-плато −270h…−610h). Кандидат — flightConflict (плоский 10 за
пару). Прервано до диагностики breakdown'а нарушений.

## Эксперимент: «честный» single vs migration на одном расписании
**Сделали:** `ts_classic` (один длинный прогон) vs `ts_iso_I_8` (миграция) на
идентичном наборе. **Результат:** оба −990 212 до цифры. Обмен лишь быстрее к

`num_workers=8` недетерминирован → разные равно-оптимальные наборы ротаций →
трудность гуляет −425k…−990k. Фикс `num_workers=1` (проверено воспроизводимостью).

## Эксперимент: Tier 1 — использовать больше ядер (16/32, 128 GB)
**Сделали:** 6-island `I_6wide`, multi-trial parallel.
**Результаты:** (1) multi-trial parallel дал **×9.9** wall-clock speedup
(42 мин vs 7 ч). (2) 6-island хуже 4-island и на S5, и на BTS — TABU/GD
добавляют шум. (3) Нашли migration-degradation баг (seed best-of-interval) и
PHASE_ASSERT (CH 84 мин). (4) 3 concurrent trial = oversubscription (18 JVM
на 16 ядрах), 1/5 сбой → max_concurrent=2.

## Two-stage decomposition (S1–S6 + BTS)
**На демо:** выигрыш только на S2 (single-flight ротации, без CNF). На
остальных проигрывает: синтетический рейс over-count'ит H8 часы. **На BTS:**
работает на реальной hub-структуре (24 731 ротация, CP-SAT optimal за 2s,
Timefold 0 hard за 127s). Но по per-slot уступает single-stage.
