# COSMOS — оптимизационное планирование лётных экипажей

Система решает две классические задачи планирования экипажей и доводит
их до рабочего инструмента планировщика: веб-интерфейс, конвейер
расчёта, проверки результата и документация.

**Пейринг** — построение многодневных цепочек рейсов, которые выполняет
один экипаж: вылет из базы, работа, ночёвки, возврат на базу. В цепочку
входят рабочие участки, наземные стыковки, отдых и перевозки экипажа
пассажиром (перегон, deadhead) для позиционирования.

**Ростеринг** — назначение конкретных людей на построенные цепочки с
соблюдением правил труда и отдыха: минимальный отдых, месячные пределы
налёта и рабочего времени, допуски, недоступные дни.

Основа — quickstart [`flight-crew-scheduling`](https://github.com/TimefoldAI/timefold-solver-python/tree/main/quickstarts/flight-crew-scheduling)
от TimefoldAI, расширенный до системы: правила реальной гражданской
авиации, точная задача покрытия на CP-SAT, приёмка результата,
многоязычный интерфейс и конвейер самоусовершенствования.

## 1. Устройство

| Слой | Что это |
|---|---|
| Веб-интерфейс | одностраничное приложение (`webapp/static/`), пять языков: русский, английский, узбекский, казахский, арабский |
| Сервер приложения | FastAPI: `webapp/app.py` и 56 модулей рядом — данные, задачи, проверки, экраны |
| Оптимизационный конвейер | этап 1 (построение цепочек, Python + CP-SAT), этап 2 (ростеринг, решатель Timefold на Kotlin/JVM) |
| Артефакты | неизменяемые файлы результатов: каталоги цепочек, решения, сертификаты проверок |

Код и данные разделены: результаты расчётов живут в каталоге-спутнике
`<репозиторий>-data` вне системы контроля версий (`_data_paths.py`,
переопределяется переменной `CREW_DATA_DIR`).

### Принципы, которых держится система

1. **Отказ вместо умолчания.** Неопознанный вход, непрочитанное правило,
   недостающее предусловие — отказ. Умолчание, подставленное молча, даёт
   правдоподобный неверный результат.
2. **Заявлено ≠ исполнимо.** Правило, для которого в расчёте нет места,
   попадает в список «заявлено, но неисполнимо», а не применяется молча.
3. **Проверка доказывает, что не прошла вхолостую** — каждая проверка
   приёмки возвращает, сколько объектов рассмотрела; нулевой охват = отказ.
4. **Вердикт — барьер, а не отметка.** Активным становится только
   решение с вердиктом `OK`.
5. **Идентичность объекта — от содержания**: составной адрес рейса,
   отпечатки входных данных, проверка происхождения перед продвижением.

## 3. Наборы данных

Все включённые наборы — **открытые либо синтетические**.

| Набор | Каталог | Происхождение |
|---|---|---|
| GERAD | `data/gerad/` | академические экземпляры задачи построения цепочек (комплект G-14-22) |
| BTS | `data/bts_schedules/`, `data/bts/` | публичная статистика полётов Бюро транспортной статистики США |
| Образцы формата | `data/samples/` | синтетический файл SSIM, написанный вручную для тестов адаптера |
| **UniA** | `data/unia/` | **синтетический анонимный набор**, см. ниже |

> Экземпляры GERAD распространяются по условиям первоисточника. Перед
> переводом репозитория в публичный эти условия нужно проверить
> отдельно — здесь они не проверялись.

### UniA — синтетическая авиакомпания

`Universal Airlines` — полномасштабный синтетический набор, построенный
так, чтобы воспроизводить статистическую структуру реальной сети
(размер, топологию, распределения), не содержа ни одного реального
идентификатора.

| | |
|---|---:|
| Аэропортов | 73 (выдуманные коды и названия) |
| Рейсов | 3435 |
| Сотрудников | 1344 (имена вида `UniA Crew 0001`) |
| Мест экипажа | 18 595 |

Проверено машинно: в наборе нет ни одного кода станции, номера рейса или
названия реального перевозчика — сканирование 277 067 строк, ноль
находок. Набор годится для воспроизведения расчётов и для передачи во
внешние среды.

Файлы: `payload-unia.json` (набор), `source-rules-unia.json` (правила
расчёта), `pin-catalog-unia.json` (закрепления). Подробнее —
`data/unia/README.md`.

## 4. Как запустить

Требуется Python 3.11–3.14.

```bash
python -m venv .venv
.venv/Scripts/pip install -e ".[dev]"
```

Прогон тестов:

```bash
.venv/Scripts/python -m pytest tests/ -q
```

Веб-приложение:

```bash
.venv/Scripts/python -m uvicorn webapp.app:app --port 8092
```

Решатель этапа 2 собирается отдельно (`kotlin-solver/`, Maven + JDK 21).

> `.github/workflows/ci.yml` — описание намеченной сборки, которое до сих
> пор ни разу не исполнялось (репозиторий был локальным). На GitHub оно
> запустится при первом же push и, скорее всего, покраснеет: часть
> зависимостей и решатель на JVM в нём не устанавливаются. Это описание
> намерения, а не запись об успешных сборках.

## 6. Чего здесь нет

Репозиторий содержит **приложение**, а не рабочий архив проекта. Не
включены:

- данные и документы заказчиков — они не покидают контур заказчика;
- внутренняя переписка внешних аудитов и отчёты по проектам;
- вендорские сборочные инструменты и настройки среды разработчика.

История коммитов не переносилась: репозиторий начат чистым срезом,
поскольку в прошлых коммитах рабочего репозитория лежат материалы
заказчиков.
