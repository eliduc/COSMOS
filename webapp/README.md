# COSMOS — веб-интерфейс конвейера пейринг–ростеринг

COSMOS = Crew Optimization System for Multi-horizon Operational Scheduling.

Запуск:

    .venv/Scripts/python.exe -m uvicorn webapp.app:app --port 8090

Интерфейс: http://127.0.0.1:8090 (вкладки «Данные», «Расчёты»,
«Результаты», «Формат и правила», «Демо»; у администраторов —
«Пользователи»). API-контракт: `API-CONTRACT.md`.
Канонический формат задачи (Слой 1): `schema/canonical_payload.schema.json`.

## Онбординг и язык интерфейса

- Интерфейс двуязычный: русский (по умолчанию) и английский; кнопка
  RU/EN в шапке переключает ВЕСЬ интерфейс (словарь —
  `static/i18n.js`, выбор хранится в localStorage `crewLang` и общий
  со страницей входа token-режима).
- Вводный тур (последовательность карточек поверх интерфейса)
  автоматически показывается один раз новому пользователю (флаг
  `tour_seen_at` в каталоге; в token-режиме — localStorage) и всегда
  доступен по кнопке «Тур».
- Вкладка «Демо» — два сценария по готовым артефактам (ничего не
  пересчитывается): «сквозной процесс» (весь конвейер на месяце
  gerad-1) и «сравнение решателей» (набор против одного и против
  GENCOL/Jeppesen; числа — из утверждённого отчёта и живых
  артефактов через `/api/demo/*`, доступно любому вошедшему).

## Аутентификация

Три режима, выбираются переменной окружения `CREW_AUTH_MODE`
(`access` | `token` | `dev`). Если `CREW_AUTH_MODE` не задана, но задана
`CREW_ACCESS_AUD`, по умолчанию включается режим `access`.

### Режим `access` — рабочий (Cloudflare Access, вход по коду на email)

Перед приложением (https://cos.fregene.ai) стоит Cloudflare Access
(команда blackmini.cloudflareaccess.com). Как это выглядит для
пользователя:

1. Пользователь открывает сайт; Cloudflare показывает страницу входа и
   отправляет одноразовый код на указанный email.
2. Пользователь вводит код — Cloudflare выпускает подписанный талон
   (JWT, заголовок `Cf-Access-Jwt-Assertion`), и запрос доходит до
   приложения.
3. Приложение НЕ доверяет заголовку вслепую: оно повторно проверяет
   подпись талона по открытым ключам команды Cloudflare (алгоритм
   RS256), адресата (метка `aud` должна совпадать с `CREW_ACCESS_AUD`)
   и сроки действия (`exp`/`iat`).
4. Затем приложение сверяет email из талона со СВОИМ каталогом
   пользователей (белым списком): кого нет в каталоге или чья запись
   отключена — тот получает страницу `unauthorized.html`
   («Этот адрес электронной почты не уполномочен…») со ссылкой на выход.

То есть пройти нужно два рубежа: код на email (Cloudflare) и белый
список с ролями (приложение). Роли: `admin` (видит вкладку
«Пользователи», колонку «Владелец» в списке экземпляров и управляет
каталогом) и `user` (обычная работа с конвейером).

Выход в режиме `access` — через Cloudflare: кнопка «Выйти» ведёт на
`/cdn-cgi/access/logout` (сессия отзывается на границе Cloudflare, а не
в приложении).

### Как добавить пользователя

Администратор: вкладка «Пользователи» → форма «Добавить пользователя»
(email + роль). Новому пользователю ничего настраивать не нужно: при
первом входе он получает код на свой email от Cloudflare, а приложение
находит его в каталоге. Там же: смена роли и статуса (активен /
отключён) выпадающими списками прямо в таблице, удаление с
подтверждением, счётчики (входы, задачи, загрузки) и сводный блок
статистики. Защита от самоблокировки: последнего активного
администратора нельзя удалить, отключить или понизить до пользователя
(сервер отвечает 409, интерфейс показывает понятное сообщение).

Также нужно, чтобы адрес прошёл первый рубеж — политику Cloudflare
Access (список разрешённых адресов для одноразовых кодов) в панели
blackmini.cloudflareaccess.com.

Идентичность в интерфейсе: `GET /api/me` → `{email, role, mode}`;
шапка показывает email, роль и кнопку «Выйти».

### Режим `token` — прежний (общий токен, для этапа локальной сети PROART)

Одна общая учётная запись оператора:

- При ПЕРВОМ запуске сервера, если файла `webapp/config/auth.json` нет,
  генерируется случайный токен (24 символа). Токен печатается в консоль
  сервера ровно один раз — прочитайте его из лога запуска. В файле
  хранится только sha256-хэш, открытый токен нигде не сохраняется.
- Вход: страница `/login` (или `POST /api/login {"token": "..."}`).
  После входа выдаётся HttpOnly-cookie со случайным идентификатором
  сессии; сессии хранятся в `webapp/config/sessions.json` (переживают
  перезапуск сервера) и удаляются через 30 дней.
- Выход: кнопка «Выйти» в шапке (`POST /api/logout`) — отзывает сессию
  на сервере.
- Сброс токена: остановите сервер, удалите `webapp/config/auth.json`,
  запустите снова — новый токен будет напечатан в консоль. При
  необходимости отозвать все сессии — удалите
  `webapp/config/sessions.json`.
- Без валидной сессии: запросы к `/api/*` получают 401, страницы
  перенаправляются на `/login`.
- Для публикации за Cloudflare/TLS установите переменную окружения
  `CREW_WEBAPP_COOKIE_SECURE=1` — cookie сессии получит флаг `Secure`
  и не будет передаваться по незашифрованному HTTP.

В этом режиме нет персональных учётных записей: вкладка «Пользователи»
скрыта, email в шапке не показывается.

### Режим `dev` — только для тестов

Личность берётся из переменной окружения `CREW_DEV_USER`, никакой
проверки подлинности нет. Режим включается ТОЛЬКО явным
`CREW_AUTH_MODE=dev` (никогда — по умолчанию) и предназначен для
автоматических тестов.

Файлы `webapp/config/auth.json` и `webapp/config/sessions.json` — секреты;
они добавлены в `.gitignore` и не должны попадать в git.

## Импорт SSIM

Вкладка «Данные» → форма «Импорт SSIM»: файл или вставленный текст в
формате IATA SSIM (глава 7; используются записи типа 3 — рейсовые),
название, необязательный диапазон дат и обязательный список баз экипажей
(SSIM не содержит экипажей, поэтому базы задаются вручную:
аэропорт + число пилотов).

API: `POST /api/import/ssim` c JSON
`{"name": str, "ssim_text": str, "date_from": "YYYY-MM-DD"|null,
"date_to": ...|null, "bases": [{"airport": str, "count": int}, ...]}`.
Сервер запускает адаптер `_ssim_to_payload.py` подпроцессом; при успехе
канонический payload сохраняется в `data/uploads/<slug>.json`, рядом —
артефакт проверки конвертации `<slug>.conversion_check.json`
(число записей, развёрнутых рейсов, нарушения проверок), ответ —
`{"id", "conversion_check": {...}}`. Любая ошибка адаптера (битые записи
типа 3, нарушения здравого смысла, база вне расписания) — 422 с выводом
адаптера дословно, в `data/uploads/` ничего не остаётся.

## Параметры правил авиакомпании (Ярус 1) — применяются

Параметры (шесть чисел: минимальная стыковка, максимум посадок за смену,
длительность смены, минимальный отдых, месячный налёт, длительность
пейринга) сохраняются в `webapp/config/airline_default.json` и
ПРИМЕНЯЮТСЯ к новым запускам: все этапы конвейера получают их через
переменную окружения `CREW_RULES_CONFIG` (единый источник —
`rules_config.py`, Kotlin-профили читают тот же файл), а отпечаток задачи
включает правила. Значения, отличные от встроенных, дают другой отпечаток
задачи — каталоги и результаты ведутся отдельно для каждого набора правил.
В интерфейсе у каждого параметра метка «по умолчанию» / «изменено»
относительно встроенных значений.

## Что умеет интерфейс

- Реестр экземпляров: месяцы GERAD 1–7, день хаба BTS, загруженные
  payload-файлы (`data/uploads/`).
- Загрузка задачи в каноническом формате с валидацией по JSON Schema и
  ссылочным проверкам (неизвестные аэропорты/рейсы — отказ с перечнем
  ошибок, ничего не сохраняется); импорт SSIM (см. выше).
- Запуск этапов конвейера как задач с живым журналом и остановкой:
  этап 1 (генерация колонок), достройка каталога, этап 2
  (ростеринг; бюджет и зерно настраиваются), валидация.
- Результаты: вердикт гейта (OK / несовместимость входа и модели /
  непригоден), карточки этапов, строки валидаторов, выгрузка наряда в
  CSV (с колонкой пассажирских перегонов), скачивание артефактов по
  белому списку.
- Конфиг параметров правил авиакомпании (Ярус 1) — сохраняется и
  применяется к новым запускам (см. выше).

## Честные ограничения

- Запуски ПЕРЕЗАПИСЫВАЮТ канонические артефакты (журналы, наряды) — так
  устроен конвейер («последний прогон побеждает», промоушен защищает
  только лучшие каталоги). Управление версиями артефактов — git: после
  демонстрационных прогонов восстановите протокольные артефакты
  `git checkout -- final-report/... data/gerad/...`.
- Персональные учётные записи и роли есть только в режиме `access`
  (Cloudflare); в режиме `token` — один общий токен на всех операторов.
