## Как исполняется

```
C:\Python314\python.exe uninstall_cosmos.py            # холостой прогон
C:\Python314\python.exe uninstall_cosmos.py --apply    # исполнение
```

- **Холостой прогон — умолчание.** Без `--apply` программа проходит ВСЕ
  гейты и печатает, что сделала бы, не меняя ничего.
- **Каждый гейт печатает, сколько объектов рассмотрел.** «Нарушений 0»
  без числа рассмотренных за проверку не принимается: гейт, прошедший
  вхолостую, и гейт, разобравший 19 430 объектов, обязаны выглядеть
  по-разному.
- **Журнал сноса** — `%LOCALAPPDATA%\cosmos-uninstall\journal-<время>.txt`,
  ведётся только при `--apply`. В него до удаления пишется отпечаток
  каждого удаляемого объекта, а по окончании — отметка «снос завершён».
- **Человек за клавиатурой отвечает словом, а не ключом.** После
  холостого прогона программа спрашивает согласие и при «да» проходит
  ВТОРЫМ заходом целиком — все гейты пересчитываются непосредственно
  перед удалением, а не берутся из вердикта минутной давности. Вопрос
  задаётся, если есть что делать: каталоги, задача, правило или
  процессы, — а не только когда существуют каталоги. Поток ввода бывает
  закрыт и там, где он выглядит консолью: отсутствие ответа — это «нет»,
  а не авария.
- **Почему Python, а не PowerShell.** Целый класс дефектов исчезает по
  построению: git отдаёт имена байтами и декодируются они нами как
  UTF-8 (кодовая страница консоли ни на что не влияет); поток ошибок
  `java -version` читается как текст, без обёрток `ErrorRecord`; код
  возврата каждой команды виден явно.

Почему не «просто `rmdir /s /q C:\cosmos`»: на этой машине уже нашлись
живой процесс установки, невидимый проверкам по портам; каталог, куда
владелец мог переместить свой файл; общая запись NTFS, у которой
удаление снимает защитный атрибут. Гейты — плата за то, чтобы снос не
задел чужого.

## Б. Предусловия — гейты (любой отказ = СТОП, ничего не изменено)

**Правило отсутствия.** Гейты судят только СУЩЕСТВУЮЩИЕ объекты.
Отсутствие каталога, правила, задачи — не отказ, а состояние «этого уже
нет»: шаг печатает «объект отсутствует» и пропускается. Полное
отсутствие всех следов — успешное завершение «машина уже чиста». СТОП
означает одно: объект существует, но не опознан как продукт установки
либо не поддаётся безопасному разбору.

**Ж. Условия исполнения** (функции `run_git`, `read_port`, `is_admin`,
`find_unfinished_journal`). Проверяются до всего остального: доступен ли
git (без него любой файл выглядел бы посторонним); каковы порты — они
задаются анкетой установки и читаются из пусковых файлов
(`--port` в `run-cosmos.cmd`, `QUARKUS_HTTP_PORT` в `run-solver.cmd`), а
не вписаны в план числом; есть ли права администратора (нужны только для
задачи планировщика и правила брандмауэра); нет ли журнала
незавершённого сноса. Все вызовы git — в единой форме
`git -C <цель> --no-optional-locks -c core.quotepath=false … -z`:
`-C` — потому что `ls-files` печатает пути относительно текущего
каталога; `--no-optional-locks` — чтобы проверка не трогала индекс;
`-z` — против квотирования имён с пробелами. Код возврата каждого вызова
проверяется: у git есть режимы, где отказ выглядит как пустой ответ.

**Б1. Подтверждение цели** (`gate_b1_markers`). `C:\cosmos` признаётся
установкой COSMOS, только если одновременно: `run-cosmos.cmd` содержит
строку «Пусковой файл создан установщиком COSMOS» (читается в UTF-8 —
маркер записан в этой кодировке), существует `webapp\app.py`, существует
`.venv`. Маркеров нет и журнала незавершённого сноса нет — происхождение
каталога не доказано: **СТОП**.

**Б1б. Остаток незавершённого сноса** (ветка в `main`). Каталог без
маркеров может быть остатком прерванного прогона этого же плана.
Опознание строгое, потому что здесь отключён гейт содержимого:
- время создания каталога должно совпасть с записанным в журнале — иначе
  это НЕ остаток, а новый каталог владельца на том же месте (свежий клон
  репозитория, восстановление из копии): **СТОП**;
- каждый оставшийся объект должен быть в записанном перечне — новое имя
  **СТОП**;
- у каждого должны совпасть размер и обе метки времени с записанными:
  под прежним именем может лежать документ владельца, и сверка одних
  имён этого не заметила бы (тот же дефект, из-за которого класс 1
  судит содержимое, а не имя): **СТОП**;
- гейт ссылок Б5 в этой ветке **исполняется**: владелец мог перенести
  остаток на другой диск и оставить соединение.

**Б1а. Постороннее в каталоге установки.** Удаление рекурсивно до дна,
значит и гейт видит всё дерево. Способов сверки два, и они зависят от
того, есть ли опись установленного.

### Способ первый — по ОПИСИ (`gate_by_manifest`), слепых зон нет

Установщик последним шагом снимает опись всего дерева: по объекту на
строку (относительный путь, размер, время изменения), сжато, рядом с
журналом установки и ВНЕ каталога цели — она обязана пережить и сам этот
каталог. Снимается после установки, но ДО проверки: проверка поднимает
приложение, и его рабочие файлы должны попасть не в опись, а в разряд
порождённых работой.

Каждый объект дерева попадает в один из трёх разрядов:

1. **В описи** — продукт установки. Если объект лежит ВНЕ зоны работы
   программы, дополнительно сверяются размер и время: изменился —
   значит под именем файла программы может лежать чужой документ, и он
   судится посторонним. Имя доказывает не больше, чем маркер.
2. **Нет в описи, но лежит в зоне работы программы** (`.git`,
   `__pycache__`, `webapp\config`, `kotlin-solver\target`, `*.pyc`,
   `*.log`) — след работы, а не чужое: эти файлы программа законно
   создаёт и меняет уже после установки.
3. **Всё прочее — постороннее: СТОП с перечнем.**

Печатается: рассмотрено, в описи, порождено работой, изменено после
установки, постороннее.

Так закрыт целый класс слепоты: прежде без пофайловой сверки
принимались клон с историей, окружение python и набор инструментов —
шестнадцать тысяч объектов из девятнадцати, и перенесённый туда
документ владельца снос уничтожил бы молча.

### Способ второй — БЕЗ описи (`gate_foreign_by_git`), слепые зоны есть

Установка сделана прежней версией установщика — описи нет. Тогда
действует прежняя сверка, и снос честно говорит об этом в выводе.

1. **Продукт — по имени И ПО СОДЕРЖИМОМУ.** Файл значится в `ls-files`
   и не показан изменённым ни в `status --porcelain`, ни в
   `diff --name-only HEAD`. Отслеживаемое имя с изменённым содержимым —
   постороннее: владелец мог сохранить свой документ под именем файла
   продукта (`README.md` — готовый пример), и совпадение имени
   доказывает происхождение ИМЕНИ, но не принадлежность ФАЙЛА
   установке. **Объявленная граница:** сверка опирается на индекс и HEAD
   клона, которые лежат внутри удаляемого дерева; владелец, выполнивший
   в клоне `git add && commit` со своим файлом или
   `git update-index --skip-worktree`, сделал бы подмену «чистой».
   (Замер: `ls-files -v` — все 1105 записей `H`.)
2. **Слепые зоны** — продуктовые внутренности и порождаемое работой:
   `.git`, `.venv`, `.tools`, `kotlin-solver\target`, `__pycache__`,
   `*.pyc`, `*.egg-info`, `webapp\config`, пусковые файлы всех служб
   пакета (`run-cosmos`, `run-solver`, `run-cdpm`, `run-catalog`),
   журналы их работы (`webapp-server.log`, `solver-server.log`,
   `cdpm-server.log`, `catalog-server.log`).
   Принимаются целиком, БЕЗ пофайловой сверки. **План называет это
   прямо: перемещённый в слепую зону чужой файл гейт не заметит.**
   Полное закрытие потребовало бы манифеста от установщика — это
   записано как задача установщика, а не умолчано.
   `installation-report.md` слепой зоной НЕ является: редакции
   установщика, запускавшиеся на этой машине, писали отчёт к корню
   ДИСКА, и та запись падала с отказом в правах; редакция, пишущая
   внутрь цели, на машине присутствует, но как установщик здесь не
   запускалась. Значит файл с этим именем внутри цели положил бы
   человек — он судится классом 3.
3. **Всё остальное — постороннее: СТОП с перечнем.**

Печатается: рассмотрено, судимо, пропущено слепыми зонами, класс 1,
класс 3. Печать «пропущено слепыми зонами» обязательна — иначе одно
число «19 430» создавало бы впечатление сплошной проверки, тогда как
судится 1104 объекта. Ошибка перечисления любого участка — СТОП.

**Б2. Снимок довеставочного окружения.** `java -version` (поток
ошибок!), `JAVA_HOME`, `C:\Python314\python.exe -V`, `git --version`.
Пустая позиция — отказ гейта: сверять было бы нечего. Те же команды
повторяются в пост-проверке.

**Б3. Процессы установки — перечисление, без действий**
(`classify_processes`). Печатается: рассмотрено процессов, наших,
упоминающих путь, с нечитаемым путём образа. **Нечитаемый путь — не
повод для остановки**: у половины процессов машины (197 из 398) он не
читается без прав администратора, это обычное состояние, а не
подозрение. Проверка по портам самостоятельного значения не имеет:
процесс установки может не слушать ничего — именно так на этой машине и
есть.

**Б4. Данные пользователя** (`gate_b4_data`). `C:\cosmos-data`
удаляется, только если содержимое **в точности равно продукту
установщика**: ровно два пустых подкаталога `final-report` и `rules`,
файлов нет. Любое отклонение — СТОП с показом перечня (кроме
опознанного по журналу остатка собственного сноса — иначе прерванный
снос заблокировал бы шаг навсегда). Ошибка перечисления — СТОП.

**Б5. Точки повторной обработки** (`gate_b5_reparse`). Проверяются сами
корни и всё содержимое обоих деревьев. Корень — ссылка либо внутри
найдена хотя бы одна — СТОП: перечисление внутрь соединения не входит,
поэтому подменённый подкаталог выглядел бы пустым и прочие гейты его не
заметили бы. **Б5 — единственная защита от подмены ссылкой**, и он
исполняется в том же прогоне, что и удаление.

**Гейт жёстких ссылок** (`gate_hardlinks`). Удаление снимает атрибут
«только чтение» с записи файла, а запись в NTFS одна на все его имена:
у чужого оригинала за пределами установки, имеющего второе имя внутри
неё, защита пропала бы. Поэтому у каждого файла с этим атрибутом
проверяется число имён (`st_nlink`); больше одного — СТОП с перечнем.
Гейт исполняется по всему дереву, включая слепые зоны. (Показания
опытов о том, снимается ли вместе с «только чтение» ещё и «скрытый» с
«системный», разошлись; отбор по признаку «только чтение» достаточен
при любом из двух исходов.)

## В. Шаги удаления (строго в этом порядке)

**В1. Остановка процессов установки.** Наш процесс — тот, для которого
верно одно из трёх:
1. путь образа лежит внутри цели (JVM решателя из `.tools`);
2. **запускаемый файл (первый токен командной строки) лежит внутри
   цели** — так работает приложение: венв Python 3.14 запускает базовый
   интерпретатор, поэтому путь образа у него `C:\Python314\python.exe`
   (охранный список!), а внутри цели — только `.venv\Scripts\python.exe`
   из `argv[0]`. Отбор по одному пути образа промахнулся бы мимо самого
   приложения и объявил бы его «посторонней программой»;
3. системная оболочка, **запущенная пусковым файлом**: путь
   `run-cosmos.cmd`/`run-solver.cmd`/`run-cdpm.cmd`/`run-catalog.cmd`
   (перечень `LAUNCHERS` в коде — по пусковому файлу на каждую службу
   пакета, включая службу каталога шаблонов) стоит отдельным токеном, а всё до
   него — только образ оболочки и её ключи (`tokenize_cmdline`,
   `invokes_launcher`). Признак намеренно узкий: `cmd /c type <файл>`,
   `Get-Content <файл>` и любое иное УПОМИНАНИЕ пути под него не
   подпадают. Замер: подстрочный признак отобрал бы 5 процессов, включая
   оболочку постороннего сеанса; строгий — ровно один, искомый.

**Никогда не останавливаются**: собственный процесс и вся цепочка его
предков (цепочка строится с проверкой времени создания — «родитель»
моложе ребёнка родителем не является); процессы, лишь упоминающие путь —
они печатаются владельцу, но не трогаются. Запуск деинсталляции ИЗ
пусковой консоли установки — СТОП с объяснением: остановить её значило
бы убить самого себя.

*Как останавливается* (`PinnedProcess`): `OpenProcess` закрепляет
описатель, и пока он открыт, номер процесса не может быть переиспользован
системой; тождество со снимком доказывается временем создания,
прочитанным у самого описателя (`GetProcessTimes`, допуск 1 мс —
замеренное расхождение представлений составляет 3 тика по 100 нс);
остановка — `TerminateProcess` через тот же описатель. **Процесс, уже
завершившийся вместе с родителем, — успех, а не отказ**: система
отвечает «доступ запрещён» и на мёртвый процесс, поэтому судим по коду
выхода (`GetExitCodeProcess`), а после остановки дожидаемся
фактического конца — только что убитый ещё держит файлы, и удаление,
начатое сразу, спотыкалось бы о них. Расхождение
времени создания — СТОП: под этим номером уже другая программа.

**В2. Задача планировщика.** Имя `cosmos-<порт>`. Есть задача, но её
команда ведёт не в цель — СТОП. Нужны права администратора (задача
создавалась с `/rl highest`); их нет — СТОП с указанием перезапустить.

**В3. Правило брандмауэра.** Ищется и удаляется по **`-DisplayName`**:
установщик создаёт правило именно так, а `-Name` — внутренний
идентификатор (сгенерированный GUID), и поиск по нему вернул бы пустоту,
то есть шаг и пост-проверка солгали бы согласованно. **Объявленная
граница:** признака конкретной установки в правиле нет (оно создаётся по
порту, без привязки к программе), поэтому у второй установки COSMOS на
том же порту удаление отнимет сетевой доступ; ущерб восстановим
перезапуском её установщика. Правила других программ под это имя не
подпадают.

**В4. Каталог `C:\cosmos`.** Гейты Б1а, Б5 и гейт жёстких ссылок
исполняются в том же прогоне непосредственно перед удалением. Перед
удалением в журнал пишется отпечаток каждого объекта — без этого
невозможны ни продолжение после обрыва, ни поимённый отчёт. Удаление —
`cmd /c rmdir /s /q`, без следования по ссылкам. **Результат проверяется
существованием, а не кодом возврата**: `rmdir` при отказе печатает
ошибку и возвращает 0, снеся часть дерева, а при отсутствующем каталоге
возвращает 2. Остался — перечислить остаток, показать и СТОП «удаление
неполное». Отметка «снос начат» остаётся в журнале, по ней продолжит
Б1б.

Внутри уйдут: клон с `.git`, `.venv`, загруженные JDK и Maven
(`.tools`), собранный решатель (`kotlin-solver\target`), пусковые файлы,
журнал с паролем, рабочие файлы приложения (`auth.json`,
`airline_default.json`, каталоги `instance-*`), `__pycache__`.

**В5. Каталог `C:\cosmos-data`.** Заново Б4 и Б5, затем удаление тем же
способом и та же проверка существованием.

**В6. Отчёт у корня диска — только доклад, БЕЗ удаления.** Файл
`C:\cosmos-installation-report.md` след ЭТОЙ установки быть не может
(запись туда падала с отказом в правах), значит его положил человек, и
маркер в первой строке доказал бы происхождение СОДЕРЖИМОГО, но не
принадлежность ФАЙЛА установке. Существует — назвать владельцу и не
трогать.

## Г. Пост-проверка (печатает числа; расхождение = ошибка)

1. `C:\cosmos` отсутствует; `C:\cosmos-data` отсутствует. **Если
   какой-то из каталогов уцелел** (например, Б4 не разрешил удаление
   данных) — это не «успех с оговоркой», а расхождение: остаток
   называется владельцу поимённо.
2. Правило `COSMOS <порт> (local subnet)` отсутствует (проверять по
   `-DisplayName`); задача `cosmos-<порт>` отсутствует.
3. **Процессов установки не осталось** — проверяется правилом В1 по
   всему списку процессов, с печатью числа рассмотренных. Проверка
   портов недостаточна и самостоятельного значения не имеет.
4. Снимок Б2 воспроизводится теми же командами и совпадает.
5. Печатается перечень удалённого из журнала, включая объекты ВНЕ цели:
   остановленные процессы, задача, правило брандмауэра, каталог данных.

## Д. Чего план сознательно НЕ делает

- Не удаляет программы, поставленные через winget сценарием подготовки
  (Python, git): здесь они стояли до установщика, и в любом случае это
  общесистемные программы, которыми мог начать пользоваться кто-то ещё.
- Не чистит кеш pip и репозиторий Maven (А5).
- Не удаляет журнал демона компилятора Kotlin в `%TEMP%`
  (`kotlin-daemon.<дата>.log`, 52 КБ, побочный след сборки решателя).
  Уточнение по факту: рассчитывать, что временный каталог убирает сама
  система, нельзя — там лежат такие же журналы четырёхдневной давности.
  Решение остаётся прежним (разбирать чужой временный каталог план не
  берётся), но след назван владельцу, а не умолчан.
- Не отзывает ключи развёртывания на GitHub: это действие на стороне
  репозитория.
- Не трогает сохранённые в браузерах пароли и сессии COSMOS.
- Не закрывает консоль установки, запущенную владельцем из
  `C:\work\COSMOS` (А8).

## Е. Свойства

- **Повторяемость.** На чистой машине прогон печатает «объект
  отсутствует» по каждому шагу и ничего не меняет. После прерванного
  удаления не заклинивает: остаток опознаётся по журналу с проверкой
  времени создания каталога и отпечатков объектов.
- **Односторонность известна:** удаление цели необратимо уничтожает
  пароль входа и журнал приложения; это названо, а не подразумевается.
- **Прослеживаемость.** Каждый гейт печатает, сколько объектов
  рассмотрел; итог — поимённый перечень удалённого и подтверждение
  целости охранного списка.
- **Проверяемость.** Холостой прогон — режим по умолчанию; на этой
  машине он выполнен, все гейты пройдены, изменений не внесено.
- **Закреплённость.** Проверки живут в наборе тестов проекта
  (`tests/test_uninstaller_gates.py`, `tests/test_installer_cycle.py`), а
  не в записках: каждый тест назван по дефекту, который он закрывает.
  Правки установщика впредь идут не вслепую.
- **Что НЕ проверено.** Ветки для Linux (`systemd`, файлы `.sh`,
  `rm -rf --one-file-system`, перечисление процессов через `ps`)
  написаны, но ни разу не исполнялись: подходящей площадки не было. Это
  сказано прямо, потому что заявленное однажды запустят.

## История ревизий

Ревизии 1–11 — план в форме прозы; ниже только то, что каждая закрыла.
Ревизия 12 сменила форму на исполняемую, ревизия 13 донесла до
документа уроки живых прогонов (см. конец списка).

- **1** — исходный план по машинной инвентаризации.
- **2** — гейт точек повторной обработки; удаление без следования по
  ссылкам; маркер у файла отчёта; скрытые файлы в гейте данных.
- **3** — проверка reparse-атрибута у самих корней; критерий «в точности
  продукт установщика» для данных; предусловия только читают; остановка
  через удерживаемый описатель; пересчёт гейтов перед удалением.
- **4** — механизм остановки исправлен на реально существующий
  (`.Kill($true)` в среде нет, `Get-Process` описатель не держит);
  потомки — поимённо; гейт жёстких ссылок.
- **5** — уточнено, какие файлы несут атрибут «только чтение».
- **6** — гейт постороннего для верхнего уровня цели; «Правило
  отсутствия».
- **7** — **блокер:** гейт постороннего охранял только верхний уровень,
  а удаление рекурсивно до дна; переписан на полную глубину со слепыми
  зонами, объявленными честно.
- **8** — **блокер:** отчёт у корня диска удалялся по маркеру
  содержимого, хотя положить его мог только человек; сверка имён не
  сходилась на кириллице (восьмеричное экранирование git).
- **9** — **блокер:** та же ошибка внутри цели (`installation-report.md`
  в слепых зонах); опровергнуто, что перечисление входит внутрь
  соединения.
- **10** — **два блокера:** класс «продукт» судил по имени — документ
  владельца под именем файла продукта погиб бы молча; ошибочно снятый
  гейт жёстких ссылок возвращён (удаление снимает атрибут с общей записи
  NTFS).
- **11** — **восемь блокеров трёх параллельных аудитов:** живой процесс
  установки, невидимый всем проверкам по портам (они судили по портам, а
  он ничего не слушал); семь дефектов исполнимости — кодировка вывода
  git, рабочий каталог git, бесполезный код возврата `rmdir`,
  заклинивание после частичного удаления, `java -version` в потоке
  ошибок, молчаливое проглатывание ошибок перечисления, правило
  брандмауэра по `-Name`.
- **12** — **три блокера ветки «остаток сноса» и смена формы
  артефакта.** Аудит показал, что введённая ревизией 11 ветка
  продолжения сама открыла три дыры: удаление по совпадению ИМЕНИ при
  отключённом гейте содержимого; незакрываемый журнал, из-за которого
  под «остаток» попадал бы новый каталог владельца на том же месте;
  отключённый в этой ветке гейт ссылок. Все три закрыты в коде:
  отпечаток (размер и обе метки времени) каждого объекта в журнале,
  сверка времени создания самой цели, отметка «снос завершён», гейт
  ссылок исполняется всегда. Сверх того исправлено по факту: приложение
  работает БАЗОВЫМ интерпретатором `C:\Python314\python.exe` (венв
  Python 3.14 запускает его, а не свой), поэтому отбор процессов ведётся
  ещё и по запускаемому файлу из `argv[0]` — иначе снос объявил бы
  собственное приложение посторонней программой и остановился; отпущен
  ложный СТОП на нечитаемом пути образа (у 197 из 398 процессов машины
  путь не читается без прав администратора — это норма); уточнено, что
  редакция установщика, пишущая отчёт внутрь цели, на машине
  присутствует, но здесь не запускалась. Главное же: спорные места
  больше не разрешаются формулировкой — они разрешаются кодом, который
  можно запустить вхолостую и проверить.
- **13** — уроки ЖИВЫХ прогонов на настоящей машине. До этой ревизии
  всё проверялось в песочнице, где не было ни правила брандмауэра, ни
  процесса-потомка, ни половинчатого состояния после обрыва. Владелец
  прогнал снос на своей машине и нашёл пять дефектов ОДНОГО класса —
  «тихий пропуск»: неопределённость трактовалась как «делать нечего», а
  не как отказ или вопрос.
  1. Признаки наличия правила и задачи возвращались из PowerShell
     ПО-РУССКИ и приходили искажёнными кодовой страницей консоли:
     сравнение не срабатывало никогда, существующее правило молча не
     удалялось. Признаки переведены на латиницу, нераспознанный ответ —
     СТОП.
  2. Остановка процесса, уже завершившегося вместе с родителем,
     считалась ОТКАЗОМ: снос обрывался, часть процессов убита. Судим по
     коду выхода; после остановки ждём фактического конца.
  3. Вопрос об удалении задавался, только если существуют каталоги.
     Когда остались лишь правило и задача — «проверки пройдены, ничего
     не сделано» при живом следе установки. Теперь вопрос задаётся по
     непустому перечню предстоящих действий.
  4. Удаление правила выполнялось, но не печаталось — для человека
     неотличимо от бездействия.
  5. Пост-проверка смотрела только каталоги и процессы и объявляла
     успех, не взглянув на задачу и правило.
  Плюс: порт брался из любой записи журнала и затирался портом решателя
  (9096), отчего имена задачи и правила вычислялись неверно; вопрос
  падал с трассировкой при закрытом потоке ввода; снос, запущенный ИЗ
  удаляемого каталога, отказывал на последнем шаге.
  **Опись установленного** (этой же ревизии) закрыла слепые зоны: снос
  сверяет каждый объект, а не принимает поддеревья на веру; размер и
  время ловят подмену файла продукта под тем же именем. Опись сжата и
  весит около 250 КБ на установку вместо пяти мегабайт.
  Наконец, проверки перенесены из записок в набор тестов проекта: 22
  теста, каждый назван по дефекту, который закрывает.
