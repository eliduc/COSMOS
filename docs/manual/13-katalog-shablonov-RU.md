# Часть 13. Каталог шаблонов (шаги 1–7: извлечение из кода, переход продуктов на каталог, версия каталога в пакете, привязки исполнителей со стендом, служба каталога и пять экранов, конвейер пополнения, снятие носителей кода)

## 13.1. Что такое каталог шаблонов

Шаблон — описание одного типа правила («пределы рабочей смены», «полы
отдыха между сменами», «штраф за ночёвку вне базы») или одного вида
критерия («минимум человеко-дней командировки», «нормированная стоимость
по рангам»). В описании нет чисел конкретной авиакомпании — только
механика: над чем считаем, в каких единицах, что считается нарушением,
какие параметры нужны и с какими единицами и отношениями. Числа приходят
из документов авиакомпании через CDPM (модуль обработки данных).

Каталог шаблонов выносит эти описания из кода в данные. Им пользуются оба
продукта — CDPM и COSMOS — подключая закреплённую версию: у каталога своя
версия, свой отпечаток и своя история изменений. Каталог — знание о
механике правил вообще, одинаковое для всех заказчиков (принцип
обезличенных шаблонов): правило того же типа с другими значениями другой
авиакомпании исполняется без правки кода и без нового носителя контура.

На шаге 1 (07.09.2026) каталог собран из кода инструментом извлечения и
поле в поле равен тому, что до этого несли реестр типов шаблонов и
словари: 16 семей правил, 2 вида критериев, 46 имён параметров (23 — с
семьёй, 21 — из словаря CDPM без семьи, 2 — только словаря решателя),
22 шаблона проверок, закрытые словари. Код обоих продуктов на шаге 1 не
трогается: он по-прежнему читает свои константы, а гейт паритета
подтверждает, что каталог им равен. На шаге 2 (07.09.2026) оба продукта
читают каталог: CDPM — мостом `cdpm/catalog_bridge.py` (часть 10),
COSMOS — дверью и обёрткой (раздел 13.6); константы кода COSMOS стали
проекциями каталога, эталон гейта — замороженный снимок констант шага 1.

Часть 13 названа в оглавлении комплекта (`00-INDEX-RU.md`): номер 13
закреплён за каталогом шаблонов, частей 11–12 в комплекте пока нет.

Файлы каталога руками не редактируются. Со шага 5 правки вносит служба
каталога (раздел 13.9): правка становится черновиком вне пакета, а в
пакет попадает кнопкой «Собрать черновик»; выпуск версии — только по
решению владельца. Инструмент извлечения `catalog/tools/build_from_code.py`
остаётся свидетелем: он работает с ключом `--check` и отказывается
писать в папку, где есть журнал версий, заявки или выпуски. Правка мимо
службы ломает отпечаток шапки, и проверка каталога называет это ошибкой.

## 13.3. Как читать

    import template_catalog as tc

    cat = tc.load("catalog")            # папка; также catalog.json, единый файл, версия
    cat.version()                       # "0.1.0-draft.3"
    cat.fingerprint()                   # sha256 канона, 64 знака — вычислен из данных
    cat.families()                      # {семья: имена параметров} — форма реестра
    cat.family("duty_limits")           # полная запись семьи (копия)
    cat.params()                        # {имя параметра: единица, отношение, уточнитель, семья, источник}
    cat.lexicon()                       # слова-носители предмета семей, дополняющие пары, порядок
    cat.criteria()                      # {вид критерия: запись}
    cat.dictionaries()                  # закрытые словари + вычисленный area_param_names
    cat.check_templates()               # шаблоны проверок: поля, необязательные поля, группа

    tc.current()                        # тот же каталог одним экземпляром на процесс;
                                        # перечитывается сам, когда файлы папки изменились
    tc.subject_words("duty_limits")     # слова-носители предмета семьи кортежем (нет слов — пустой)
    tc.complements()                    # {семья: кортеж дополняющих семей}

Обращение к неизвестной записи (`cat.family("нет")`) — отказ словами с
перечнем известных. Кривой файл, дубль ключа, отсутствующий раздел —
отказ словами с путём файла при загрузке.

Запись семьи несёт: класс (ядро/расширение), заголовок, предмет и
слова-носители предмета, дополняющие семьи, вид (HARD/SOFT) и зону
(пейринг/ростеринг/обе), природу (расписание / люди / параметр мира /
история сотрудника) и свидетеля природы, единицу нарушения и размер
нарушения (у мягких), чтение истории, параметры (имя,
единица, отношение, уточнитель, заметка), альтернативные наборы
параметров, условия исключения, форму правила в пакете, семантику словами
(совокупность, единица, мера, текст), виды исполнителей, шаблоны
проверок, стендовые задачи (на шаге 1 пусты), критерий приёмки,
происхождение, статус, историю.

**Три поля записи семьи, заведённые каталогом 0.5.0 (11.09.2026).** Все
три — носители признаков, которые до 0.5.0 держались рукописными
перечнями в коде обоих продуктов (руководство
[Часть 09](09-spravochnik-RU.md), раздел 6в).

| Поле | Значение | Что им проверяется |
|---|---|---|
| `reads_history` | `null` либо объект `{need, kind}`: `need` — потребность словами, `kind` — слово словаря `history_read_kinds` (`accumulator` — остаток накопителя с начала месяца или за окно; `boundary` — конец и место последней смены до горизонта; `series` — серия смен или выходных через границу; `window` — календарь суток за скользящее окно) | X15 — форма поля (вид из словаря, непустые слова потребности); X19 — семья природы `history` обязана назвать, что читает. Обратное не требуется: семьи границы горизонта читают историю при природе `schedule` — правило судит расписание, а историю читает сама мера |
| `violation_size` | `null` либо слово словаря `violation_sizes`: `count` — штраф растёт числом единиц нарушения (смен, ночей, событий), `magnitude` — величиной превышения (часов сверх) | X16 — поле задано ровно у мягких семей (`kind == SOFT`), как X03 для единицы нарушения |
| `nature_confirmed_by` | слово словаря `nature_witnesses`: `solver_tables`, `certifier_registry`, `change_request`, `none` | X17 — свидетель по природе (таблица в 13.13); X18 — запись, пришедшая конвейером пополнения (в `origin` — заявка), опереться на `certifier_registry` не вправе: этот перечень ведёт тот же контур, что завёл запись, и природа держалась бы на её собственном слове |

Восемь семей каталога 0.5.0 несут `reads_history` (`span_accumulators`,
`balanced_workload`, `rest_floors`, `night_series`, `duty_series_limit`,
`days_off_floor`, `rolling_rest`, `calendar_windows`), четыре мягкие —
`violation_size`, свидетеля природы несут все семнадцать.

## 13.4. Как проверить

1. Проверка каталога читателем:

        cat.validate()                  # список проблем; пустой — зелёный

   Каждая проблема — адрес, код правила, слова, серьёзность
   (`[error] families/duty_limits/params[2].unit: …`). Правила: схема и
   форма файлов (S), словари (D), перекрёстные ссылки (X), шапка и
   версии (H), заявки (R), обезличенность (A). На шаге 1 законны только
   предупреждения X07 «запись без стендовых задач»; со шага 4 стендовые
   задачи есть у каждой записи, и на живом каталоге `validate()`
   отвечает пустым перечнем — ни ошибок, ни предупреждений.

2. Паритет каталога с кодом — ЗАКОН и его свидетель (13.13):

        .venv\Scripts\python.exe catalog\tools\parity.py
        .venv\Scripts\python.exe catalog\tools\parity.py --with-candidates
        .venv\Scripts\python.exe tests\fixtures\freeze_registry_step1.py --check
        .venv\Scripts\python.exe -m pytest tests/test_template_catalog_reader.py tests/test_template_catalog_validate.py tests/test_template_catalog_parity.py tests/vmp/test_template_registry_wrapper.py tests/vmp/test_catalog_access.py -q

   Первая команда судит ЖИВОЙ каталог: код 0 — красных правил нет,
   1 — есть красные (названы словами), 2 — судить не удалось. Вторая
   судит «живой каталог ⊕ все кандидаты `catalog/candidates/**`» —
   именно так конвейер пополнения и служба видят каталог до сборки
   записи (13.10, 13.13). Генератор снимка отвечает «расхождений 0»
   (код 0), «расходится» (код 1) либо «ревизия недоступна» (код 3 —
   неполный клон). База заморозки — снимок шага 1 (блок `base` посева:
   код, версия, отпечаток, перечни семей, критериев и видов); рост от
   этой базы описывает ВЫЧИСЛЕННАЯ дельта `transition/step4_additions.json`,
   и правило L23 сверяет её свежесть по отпечатку каталога.
   Пересмотр атрибутов БАЗОВЫХ записей (заголовок, класс, вид, зона
   семьи из снимка) — по-прежнему новая заморозка новым файлом снимка
   по слову владельца.

3. Проверка инструментом извлечения (ничего не пишет; со шага 5 это
   единственная его команда над живым каталогом, которая ПИШЕТ, — запись
   в папку с непустым журналом версий, непустыми заявками или папкой
   выпусков инструмент отклоняет словами и кодом 3):

        .venv\Scripts\python.exe catalog\tools\build_from_code.py --out catalog --check
        .venv\Scripts\python.exe catalog\tools\build_from_code.py --out catalog --check --from-catalog
        .venv\Scripts\python.exe catalog\tools\build_from_code.py --out catalog --refresh --check

   Ожидаемый вывод первой: «расхождений 0» (код 0) — заметка шапки по
   умолчанию у инструмента совпадает с заметкой каталога (черновик 3
   по ответу CDPM); разделы `families`, `criteria`, `dictionaries`,
   `requests`, `versions` и копия схемы равны байт в байт. Что эта
   проверка доказывает: детерминизм инструмента и совпадение копии
   схемы. Вторая (`--from-catalog`) судит ЛЮБУЮ папку из её же
   курируемых полей ⊕ кода: «каталог ≡ курируемое(каталог) ⊕ код» —
   этим и держится L18 после первой сборки службой. Третья отвечает
   «посев и дельта свежи» (код 0) либо называет отставший раздел
   (код 1); лечение — `--refresh` без `--check`, он переписывает ТОЛЬКО
   `tools/catalog_seed.json` и `transition/step4_additions.json`.
   Паритета каталога с кодом решателя и с постановкой эти команды не
   доказывают — его доказывает ЗАКОН (пункт 2, раздел 13.13): здесь
   судится детерминизм сборки и то, что посев с дельтой не отстали.
   Со шага 4 инструмент читает посев, таблицы Kotlin и константы
   проверок, а обёртку и словарь критериев не импортирует. Правка
   инструмента — зона `catalog/**`. Перевод строки (LF/CRLF после
   перематериализации файлов git) расхождением не считается; сам
   инструмент пишет LF.

4. Привязки исполнителей (шаг 4) — детерминизм сборки и гейт продукта:

        .venv\Scripts\python.exe -m vmp.bindings_build --check vmp/bindings.json
        .venv\Scripts\python.exe -m vmp.bindings_gate

   Первая команда пересобирает файл в памяти и сверяет его с файлом на
   диске без изменчивых полей (`generated_at`, `generated_from`, моменты
   записей стенда): код 0 — сошлось, 1 — расхождение названо словами
   («families/duty_limits исполнитель 3 (Builder.duty_limit_ok): поле
   params — в файле […], собрано […]»), 2 — сборка не состоялась.
   Вторая печатает матрицу «запись × вид → есть / нет / заявлен /
   — (не объявлено)» и проверяет, что каждый символ строки «есть»
   существует в коде: код 0 — зелёно.

5. Стенд шаблонов (шаг 4):

        .venv\Scripts\python.exe -m vmp.stand_tasks

   Таблица «запись × задача × вид × исход × получено/ожидалось». Виды
   чистого Python (`builder_method`, `check_template`, `check_code`)
   прогоняются здесь и сейчас; виды решателя (`kotlin_*`) отвечают
   `skipped` со словами «решатель не зван». Код 1 — есть `failed` вне
   явного перечня `KNOWN_FAILED`.

   **Живой прогон видов решателя ПОДКЛЮЧЁН** (08.09.2026). С ключом

        .venv\Scripts\python.exe -m vmp.stand_tasks --with-solver <адрес>

   виды `kotlin_*` судятся настоящим решателем: пакет постановки
   собирается библиотекой CDPM по своду задачи, уходит прогоном по
   идентификатору, и повкладовый счёт назначений стенда под пакетом
   ЭТОГО прогона даёт числа. `<адрес>` — решатель ТОГО контура, на
   котором проверяете (решатель Test на legion — `http://127.0.0.1:8098`,
   [Часть 08](08-administrirovanie-RU.md), таблица «Контур — Решатель»);
   экземпляр владельца (`9099`) — только по его слову: его пул прогонов
   занят рабочими задачами, и стенд встанет в чужую очередь. Адрес
   приходит ТОЛЬКО этим ключом: умолчания нет, и без ключа стенд к
   решателю не обращается.

   Прослеживаемость исхода до прогона службы дают ПОЛЯ строки результата
   (`run_id`, `package_fingerprint`); адрес решателя назван один раз —
   шапкой `solver` файла результатов и строкой над печатной таблицей, а
   сама печатная таблица дописывает к строке `[прогон …, пакет …]`. В
   словах строки (`note`) этих значений нет по замыслу: слова уезжают в
   `stand_verified` файла привязок, и идентификатор прогона сделал бы
   привязки каноном ПРОГОНА, а не каталога — перепрогон менял бы два
   десятка строк при побайтово тех же числах.

   Несостоявшееся звено — красная строка со словами отказа, а не пропуск:
   решатель молчит, пакет отвергнут его гейтом, ограничения нет в разборе
   счёта — всё это `failed` с причиной. Красная строка тоже называет свой
   прогон полем `run_id`, если он успел начаться.

   Перед серией стенд спрашивает живость службы, а занятый пул опознаёт
   ПЕРВЫМ прогоном (короткий потолок ожидания): служба молчит либо первый
   прогон не дошёл до «готов» — остальные строки видов решателя красные
   словами и БЕЗ прогонов, чтобы стенд не набивал очередь чужого
   экземпляра.

   Полная команда живого прогона бывает ДВУХ форм, и вместе они не
   сочетаются: `--records` сужает прогон до записей, а `--write-results`
   пишет свидетельство ВСЕГО каталога — вместе они стёрли бы исходы
   прочих записей, поэтому команда отвечает отказом кодом 2.

   Форма 1, прогон записи (свидетельство на экран, файл не трогаем):

        .venv\Scripts\python.exe -m vmp.stand_tasks --with-solver <адрес> \
            --records <id[,id…]> \
            [--solver-identity <sha256>] [--budget-s <секунды>] \
            [--deterministic] [--tmp-dir <папка>]

   Форма 2, весь каталог с записью файла результатов:

        .venv\Scripts\python.exe -m vmp.stand_tasks --with-solver <адрес> \
            --write-results vmp/stand_results.json \
            [--solver-identity <sha256>] [--budget-s <секунды>] \
            [--deterministic] [--tmp-dir <папка>]

   **Окружение пусковика (РВ-138, 04.10.2026).** Обе формы — и любая
   команда с `--with-solver` или `--write-results` — идут лишь в
   окружении пусковика площадки, том же, что у панели: `CREW_CONTOUR`,
   `CDPM_EXPORT_SPEC_VERSION`, `CREW_TEMPLATE_CATALOG`,
   `CREW_COSMOS_BINDINGS`, `CREW_CDPM_BINDINGS`. Нет хоть одной — отказ
   кодом 2 до старта с именами недостающих: окружение, собранное рукой,
   03.10 трижды судило не то, что исполняет панель (без
   `CDPM_EXPORT_SPEC_VERSION` пакеты стенда ушли контрактом 1.18, и
   решатель прочёл их «архивом»). Файл результатов несёт шапку
   `environment` — контур, контракт, путь каталога, отпечатки файлов
   привязок, без ключей. Для разработки и проб есть явный ключ
   `--outside-launcher`: команда идёт, шапка называет недостающие
   переменные, а дверь привязок такой файл не принимает («вне окружения
   пусковика»). Живой прогон вне пусковика этим ключом НЕ открывается:
   сборка пакетов (`run_tasks` с решателем) без окружения отказывает
   сама, и пройти её можно лишь явным контрактом `--spec-version`
   (тестовый контракт, не умолчание). Файлы без шапки (до 04.10)
   судятся прежними законами.

   Три ключа живого прогона добавлены 08.09.2026 по просьбам проекта
   пакета «Kotlin-исполнители агентом»; без `--with-solver` каждый из
   них — отказ кодом 2 словами (ключ, который ничего не делает, читается
   как сделанная работа):

   * `--solver-identity <sha256>` — отпечаток артефакта решателя,
     отвечающего по адресу. Уезжает в шапку `solver.artifact_sha256`
     файла результатов, и привязка «адрес → артефакт» живёт в самом
     файле, а не только в свидетельстве кандидата. Без ключа поле
     `null`, и это не молчание: причина названа словами в `note` шапки —
     иначе `null` читался бы как «артефакт тот же». Значение не формы
     sha256 (64 знака `0-9a-f`) — отказ кодом 2: шапка о личности
     артефакта лгать не должна. РЕГИСТР ЛЮБОЙ: `Get-FileHash` PowerShell
     на площадке печатает заглавные, `hashlib.hexdigest()` конвейера —
     строчные; в файл значение уезжает строчными (канон `hexdigest`),
     чтобы один артефакт выглядел в файле одинаково.
   * `--budget-s <секунды>` — предел времени КОМАНДЫ, и отсчёт идёт от
     НАЧАЛА СЕРИИ. Исчерпав его, стенд новых прогонов не ставит, а
     оставшиеся строки видов решателя закрывает словами «бюджет стенда
     исчерпан»; файл результатов пишется с ЧАСТИЧНЫМИ строками, и упор в
     предел назван словами и числом строк в итоге команды. ОСТАТОК
     предела уезжает В СТРОКУ: звенья живой строки (постановка прогона,
     ожидание «готов», разбор счёта) получают потолок не больше остатка,
     а кончившийся посреди строки остаток — красная строка теми же
     словами бюджета. Поэтому строка, начатая у самой границы, предел не
     переезжает. Чистые виды бюджет не ОБРЫВАЕТ (они идут секундами и
     сети не касаются), но их время в предел ВХОДИТ — он предел команды,
     а не одних живых строк; ставьте его секунд на 60 меньше потолка
     команды конвейера (`CATALOG_CMD_TIMEOUT_S`), запаса на запись файла
     и чистых судей этого хватает. Без ключа предела нет, и худший
     случай (решатель молчит на каждой задаче) упирается в потолок
     команды конвейера кодом 124 без диагноза.
   * `--deterministic` — прогон профилем Д1 (зерно 0, счётный предел 1).
     **Умолчание — ВЫКЛ**, и это не лень: ниже сказано, почему. Ключ
     включают на решателе С ПРАВКОЙ остановки Д1 (страховочный предел
     стенных часов внутри Д1, сделана 08.09.2026 на стороне решателя):
     такой решатель отдаёт признак остановки полем `termination` ответа
     о состоянии прогона, и стенд кладёт его ПОЛЕМ СТРОКИ (вид,
     признак воспроизводимости, слова) — печатная таблица показывает
     его хвостом строки рядом с прогоном и отпечатком пакета, а итог
     команды сводит признаки ПО СТРОКАМ («wall_clock_safety — строк 2»).
     В `note` признака нет намеренно: вид остановки зависит от
     секундомера прогона (страховка судится раньше счётного предела), а
     `note` уезжает в `stand_verified` привязок и обязан быть каноном
     каталога. Решатель БЕЗ правки отвечает без этого поля — итог
     команды говорит это числом строк («поля termination нет — строк N:
     служба этих прогонов старой сборки, без правки Д1»), и включать на
     нём ключ нельзя: прогон на мире без исполнимого хода занял бы поток
     пула навсегда.

   Серия обрывается рано: три отказа ПОДРЯД БЕЗ ЖИВОГО ОТВЕТА службы
   (соединение не встало, состояние прогона не отдано, потолок ожидания
   истёк) значат «считать некому», и остальные живые строки красные
   словами «решатель не отвечает: прогоны прекращены после 3 отказов
   подряд» БЕЗ единого нового прогона — очередь чужой службы стенд не
   набивает. ЛЮБОЙ ответ службы счётчик сбрасывает: и пакет, отвергнутый
   её гейтом, и прогон, УПАВШИЙ на своём пакете. Падение — ответ живой
   службы о неудаче этого пакета: оно приходит первым же опросом и
   времени не стоит, поэтому обрывать по нему серию значило бы терять
   свидетельство прочих строк (а три падения подряд у одной записи —
   не случайность, а общий шаблон мира её задач).

   Прогон крошечный (предел одна секунда) и РЕШЕНИЯ его не читает: числа
   берутся разбором счёта назначений стенда, а он от хода поиска не
   зависит. Детерминированный профиль Д1 (зерно, счётный предел) прогону
   стенда по умолчанию НЕ задаётся: на сборке решателя БЕЗ правки
   остановки (о ней ниже) он останавливает прогон НЕ НА ВСЕХ мирах
   стенда. Механика (измерено 08.09.2026): счётный
   предел судится только МЕЖДУ ЗАВЕРШЁННЫМИ шагами поиска, а стенные часы
   — на каждом ходе; на мире без исполнимого хода (один сотрудник, все
   назначения заданы) первый шаг не завершается никогда, предел не
   наступает, и поток пула занят навсегда (`st-layover-1` при
   `step_limit` 1 и 200 и при `unimproved_step_limit` 1); на мире, где
   принятый ход есть, шаг завершается и предел срабатывает (`st-duty-1` —
   «готов» за 0,53 с). Общей остановкой на всех мирах служат сегодня
   только стенные часы, и стенд идёт ими. Правка остановки сделана на
   стороне решателя 08.09.2026: счётные пределы Д1 остались главными, а
   рядом с ними в той же ИЛИ-составной остановке живёт СТРАХОВОЧНЫЙ
   предел стенных часов — он же и есть ранний выход, потому что
   признака «исполнимых ходов нет» Timefold 2.0 наружу не даёт.
   ПЕРЕКЛЮЧАТЕЛЬ у профиля есть (`--deterministic`), и включают его на
   решателе С этой правкой: он отдаёт признак остановки полем
   `termination` (вид `kind`, признак `reproducible`), и стенд кладёт
   его ПОЛЕМ строки. На решателе без правки поля у строки нет, а итог
   команды говорит это числом строк; включать ключ там нельзя: прогон на
   мире без исполнимого хода занял бы поток пула навсегда. При пределе в
   одну секунду большинство прогонов Д1 честно получают
   `wall_clock_safety` и `reproducible: false` — стенд это принимает
   сознательно: РЕШЕНИЯ прогона он не читает вовсе, числа берутся
   разбором счёта назначений стенда. Ни изменчивых чисел прогона (шаги,
   миллисекунды), ни самого вида остановки в СЛОВАХ строки нет: вид
   зависит от секундомера (страховка стенных часов судится раньше
   счётного предела — измерено 08.09.2026: тот же профиль на том же мире
   дал `step_count` при 104 мс и `wall_clock_safety` при 1017 мс), а
   слова строки уезжают в `stand_verified` привязок и сделали бы файл
   каноном ПРОГОНА, а не каталога.

   **ПРАВКА РЕШАТЕЛЯ СДЕЛАНА (08.09.2026, ветка `solver-d1`).** Взята
   страховка стенными часами внутри Д1: счётный предел остаётся главным,
   рядом с ним в остановке живёт страховочный предел стенных часов
   (предел запроса `spentLimitSeconds`, без него — 60 с). Прогон Д1
   больше не занимает поток пула навсегда и ГОВОРИТ, по какому пределу
   остановился, — поле `termination` статуса прогона и `applied-rules`
   (раздел 3 руководства, «Признак остановки прогона»). Сам стенд по-
   прежнему идёт стенными часами: возврат профиля Д1 — ОТДЕЛЬНЫЙ ключ
   стенда, его правит другая дорожка; этот абзац описывает решатель, а
   не стенд.

   Без ключа `--tmp-dir` команда заводит папку прогона под `_repro/stand`
   в самом дереве (место снято с учёта git) и удаляет её за собой при
   штатном выходе; во временный каталог системы не пишет — его чистит
   сама система. Прогон, снятый на полпути, папку `_repro/stand/stand-*`
   оставляет: её убирают рукой.

Правило версий: старшая — переименование или снятие записи, смена вида,
зоны, природы, единицы нарушения, единицы или отношения параметра,
переезд параметра между семьями, удаление значения словаря, смена ВИДА
значения словаря (перечень стал картой); младшая —
новая запись, новый параметр или набор, новое значение словаря, новое
поле записи, стендовые задачи, история, семантика; патч — опечатки и
заметки. На версиях 0.x младшая вправе нести смысловые изменения.

**Шаг 4 (08.09.2026): `0.2.0-draft.1`.** Версия младшая, потому что
шаг 4 добавляет, а не переименовывает: три имени параметров получили
семью (`max_monthly_block` → `span_accumulators`,
`max_deadheads_per_flight` и `max_deadheads_per_day` →
`deadhead_rules`), записям объявлены виды исполнителей, у которых код
COSMOS есть, заведены шесть записей критериев-метрик решателя, у всех
записей появились стендовые задачи, в словари добавлены форма мира
`tables` и синтетические идентификаторы наборов. Поле
`legacy_registry_rev` получает НОВОЕ 12-значное значение: это та же
старая формула над той же картой семей, а карта изменилась раздачей
трёх имён — свидетель неизменности честно говорит, что данные
изменились (гейт паритета пересчитывает формулу сам, L10). Флаг
`gates.stand_tasks_required` остаётся выключенным: полноту стендовых
задач требует дерево (гейт паритета L11 — на живом каталоге
`validate()` без единой проблемы), а включённый флаг обрушил бы оба
продукта на любой записи без задач, в том числе на пробных записях
тестов и будущих записях из заявок. Включение флага — при `1.0.0` по
слову владельца.

**Черновик 2 (08.09.2026): `0.2.0-draft.2`.** По слову владельца тем же
младшим номером сделаны две правки. Первая: три порога получили
отношение «не больше» (`max`) — `duty_extension_cap`,
`long_duty_threshold`, `workload_spread_threshold`. Решатель этих имён в
своих таблицах не держит, отношение им назначено решением владельца, и
дельта перехода называет это отдельным разделом `params_relation_set`

семьи получили ещё три имени словаря — `fleet_type` →
`fleet_exclusions`, `max_sit_duration` → `connection_windows`,
`max_weekly_block` → `span_accumulators`; непривязанных параметров
осталось 17 (было 20), имён «только словарь решателя» не осталось ни
одного. Поле `source` в записи параметра не заводится: источник семьи
читатель выводит сам. Предупреждений B01/B03 у читателя после раздачи
нет.

целиком, а не дополняется патч-версией — поэтому отпечаток выпуска
отличается от отпечатка черновика 2 без этих правок.
Записаны: первая запись `catalog/versions.json`, неизменяемая копия
`catalog/releases/0.2.0/` (шесть файлов читателя, `schema/` и
`transition/families_order.json`), шапка без суффикса черновика.
Отпечаток тела выпуском не изменился — суффикс черновика в отпечаток не
входит.

Три следствия выпуска, о которых надо знать заранее:

* **инструмент извлечения больше не пишет** в `catalog/`: каталог ведёт
  служба (непустой журнал версий и папка `releases/`), у инструмента
  остаются `--check` и `--out <временная папка>`. Сверка `--check`
  журнал версий не сравнивает — его ведёт только служба;
* **сторож дрейфа стал строже**: «стоп защищает выпуски». Пакет с той
  же версией и другими данными теперь ОСТАНАВЛИВАЕТ расчёт (у черновика
  это было предупреждение), и то же — при разнице среднего числа на
  0.x. Пакеты контура, выпущенные по `0.1.0-draft.3`, после выпуска
  останавливаются при нажатии и подлежат перевыпуску производителем
  (CDPM);
* **привязки продуктов** обязаны нести номер выпуска: `vmp/bindings.json`
  и `vmp/stand_results.json` перевыпущены под `0.2.0` в том же окне
  коммитов; `cdpm/bindings.json` и `cdpm/stand_results.json`
  перевыпускает сессия CDPM.

**Каталог `0.5.0` (11.09.2026): четыре носителя признаков.** Выпуск
гасит четыре долга, при которых признак семьи жил рукописным перечнем в
коде, а не записью каталога. Что сделано и каким уровнем правки:

| Правка | Уровень | Почему |
|---|---|---|
| Словарь `violation_units` стал КАРТОЙ «код → слово» (`{"day": "сутки", "duty": "смена", "event": "событие", "hour": "час", "minute": "минута", "night": "ночь"}`) вместо перечня кодов | **старшая** | смена вида значения: читатель, ждавший перечень, на карте ломается — и это честно названо, хотя номер на `0.x` вышел бы тот же. Ключи остались кодами (латиница), членство каталога судится по КЛЮЧАМ, слово — подпись рядом с кодом; второй карты слов у продуктов больше нет (прежняя `vmp.chain_price.UNIT_WORDS`) |
| Поля записи семьи `reads_history`, `violation_size`, `nature_confirmed_by` (13.3) | младшие | новые поля ничего не отменяют: они называют то, что прежде выводилось из кода |

Номер: `0.4.0` → `0.5.0` (на версиях `0.x` и старшая, и младшая правка
дают `0.{minor+1}.0`; уровень «старшая» в журнале версий записан всё
равно — по нему судят читатели пакетов, а не по номеру). Отпечаток
каталога меняется, значит после выпуска обязательны: стоп сторожа
дрейфа у всех пакетов прежней версии, перевыпуск привязок обоих
продуктов и перевязка комплектов Н0, Н0-B, Н0-C, Н0-К, Н0-КИ. Числа
прогонов при этом сдвигаться не должны: параметры семей выпуск не
трогает.

## 13.6. Шаг 2: дверь и обёртка COSMOS (07.09.2026)

**Какой каталог.** Путь каталога — настройка продукта
`CREW_TEMPLATE_CATALOG` (папка каталога); не задана — папка `catalog/`
рядом с читателем. Формула пути у двери COSMOS (`vmp/catalog_access.py`)
дословно та же, что у моста CDPM, поэтому в одном процессе (веб-приложение
несёт оба продукта) у CDPM и COSMOS один экземпляр каталога — один
отпечаток у посадок, манифеста и реестра исполнителей. Единый файл
выгрузки на шаге 2 COSMOS не принимает (переходных носителей у него нет;
мост CDPM тот же файл принимает — асимметрия названа в тексте отказа).

**Что живое.** Всё, что COSMOS читает из каталога, привязано к
экземпляру, а не к процессу: шесть констант обёртки
(`RULE_MECHANIC_TYPES`, `PARAM_TO_FAMILY`, `FAMILY_KIND_ZONE`,
`FAMILY_VIOLATION_UNIT`, `VIOLATION_UNITS`, `CRITERION_TYPES`) и словарь
видов критериев `vmp.criteria.SPEC` строятся один раз на экземпляр и
отдаются тем же объектом, пока файлы разделов и `transition/` не менялись;
правка на диске даёт новые объекты у всех потребителей без перезапуска.
Новый экземпляр проверяется один раз (`validate()`; кривой каталог —
отказ с кодами проблем, отказ запоминается и не пересчитывается).
Для тестов есть `vmp.template_registry.forget()`; подмена констант в
тестах — только каталогом (tmp-копия через `tests/catalog_copies.py`),
не `setattr`.

Проекции обёртки — свойства с отказом: `getattr(tr, "PARAM_TO_FAMILY",
{})` и `hasattr(tr, "RULE_MECHANIC_TYPES")` от отказа каталога не
защищают (поднимается ошибка каталога, не `AttributeError`) — читатель
ловит `vmp.catalog_access.CATALOG_ERRORS`; читатели CDPM
(`cdpm/model.py`, `cdpm/vmp_form.py`) держат внешний `except`, и при
переводе их на читатель каталога снимать его нельзя.

Порядок проекций. `PARAM_TO_FAMILY`, `RULE_MECHANIC_TYPES` и карта
`families_map()` идут в порядке `transition/families_order.json`
(порядок кода шага 1). `VIOLATION_UNITS` идёт в порядке словаря
каталога (`day, duty, event, hour, minute, night`; с 0.5.0 словарь —
карта «код → слово», и это порядок её КЛЮЧЕЙ), не кода (`night,
duty, hour, day, minute, event`): состав тот же, но перечень единиц в
тексте находки формы ВМП («единица … вне словаря day, duty, …») и
кортеж `cdpm/vmp_form.violation_units()` теперь в порядке словаря
(отступление п. 21 приложения схемы записи; гейт сверяет состав со
снимком шага 1, кортеж — со словарём каталога). `families()` и
`families_meta()` идут в порядке читателя (по идентификатору семьи);
потребители порядком не пользуются, `registry_rev()` от порядка не
зависит.

**Без каталога.** Запаса из кода у COSMOS нет: без каталога, без
читателя (`template_catalog` не установлен рядом с `vmp`) и при кривом
каталоге первая операция отказывает словами с путём и именем переменной.
Где это видно: кнопка расчёта — без каталога первым отвечает гейт
пакета производителя (Ш-1: «остановка производителя: красный гейт
пакета: база шаблонов недоступна (template_families пуст) — контракт
посадки не судится»), а каталог, пропавший после гейта пакета и вывода
реестра (раскат между шагами), ловит рубеж Ш-1п2 — «остановка: каталог
шаблонов недоступен» (гейт соответствия, пробел вида
`catalog_unavailable` с путём и именем переменной в заметке); канал ВМП
— колонка реестра исполнителей матрицы готовности с текстом ошибки
(запуск запрещён, исключения нет), а на повторе пакета — заметка
«вывод реестра исполнителей не удался: …» в кратком вердикте и в строке
журнала приёмов (`registry_note`; реестр остаётся прежним, первое
нажатие скажет «реестр устарел» — причина названа заранее); экран
«Админ → База шаблонов» — 503 словами; вход построителя пейринга —
отказ словами; отчёт покрытия критерия — «невычислима: каталог шаблонов
недоступен».

**Исполнители и виды критериев.** До шага 4 исполнители семей жили в
переходном носителе `catalog/transition/executors_legacy.json`. Со
шага 4 их даёт файл привязок продукта `vmp/bindings.json` (раздел 13.8):
`RULE_MECHANIC_TYPES[семья]["executors"]` — строки «есть» в форме
«вид · символ · файл», в порядке файла привязок. Прежняя опись остаётся
на диске СВИДЕТЕЛЕМ — шаг 7-Б её оставил: она левая сторона гейта
«ничего не потеряно» (`tests/vmp/test_bindings.py`, п. 13; раздел
13.12), и другого носителя этой правды в дереве нет. Дверь её не
читает, инструмент её не пишет, а гейт доказывает, что каждый её
идентификатор нашёлся среди строк «есть» той же семьи, кроме явного
перечня с причинами. Порядок семей — по-прежнему
`transition/families_order.json`; носитель проверяется на равенство
множеству семей каталога.

`criteria.SPEC` — записи критериев «есть», у которых `computable_by`
содержит `builder_method` И ЕСТЬ ФОРМА ЭКЗЕМПЛЯРА (`instance_form`):
`SPEC` — словарь видов БЛОКА `criterion` пакета, а вид без формы
экземпляра в этом блоке невыразим. Отбор по форме заведён шагом 4
вместе с критериями-метриками решателя: метрика живёт в целевой
(`objectives[].metric`), экземпляра не имеет и в `SPEC` не входит —
иначе судья критерия объявлял бы пробел там, где вида в блоке пакета
быть не может. Исполнитель вида критерия — код (`EXECUTORS`) ЛИБО
строка «есть» любого вида в привязках: на экране и в карте
`families_map()` признак `has_executor` истинен у всех восьми записей,
а `known_to_spec` у метрик ложен — два признака различны, и это видно.

**Режима среза больше нет (шаг 7-Б, 08.09.2026).** Прежде переменная
контура `CREW_VMP_TEMPLATE_BASE` подменяла базу шаблонов срезом (файл
набора, например `etalon/NSH-H0.json`), и три функции обёртки отвечали
по срезу, а константы — по каталогу. Это снято: у обёртки одна сторона —
каталог. Что делать вместо этого — в 13.12. Срез базы остался
артефактом НАБОРА: его по-прежнему ВЫВОДЯТ из каталога генератором
`open-bench/polyaris/build_nsh_h0.py` и по нему судят покрытие ВМП, но
им больше ничего не подменяют. `families()` и `families_meta()` идут в
порядке читателя (по идентификатору семьи), константы и `families_map()`
— в порядке `families_order.json` (см. «Что живое»); значение
`registry_rev()` от порядка не зависит.

**Сертификат.** Дополняющие семьи (предел ↔ продление) сертификат берёт
из поля `complements` записей каталога, лексикон CDPM ему больше не
нужен; каталог читается только при потолке продления в своде —
сертификат пакета с потолком без каталога отказывает словами.

**Реестр исполнителей и сторож дрейфа.** Выведенный реестр несёт блок
`catalog` (версия, отпечаток, путь), а со шага 4 — и блок `bindings`
(сводка привязок: файл, версия продукта, коммит и момент сборки, версия
и отпечаток каталога привязок, отпечаток КАНОНА файла, счётчики клеток
и строк, итог стенда числами задач и строк, слово о привязках CDPM).
Сторож дрейфа
сверяет оба отпечатка с текущими — смена каталога либо строк
исполнителей = «реестр исполнителей устарел: код, каталог шаблонов или
привязки изменены после сверки», лечится повторной отправкой пакета.
Сверяется именно отпечаток КАНОНА привязок (файл без изменчивых полей
`generated_at` / `generated_from` и без моментов записей стенда): иначе
любая перегенерация файла старила бы реестры площадок, ничего не меняя
в исполнителях. Реестр без блока `catalog` (выведен до шага 2) или без
блока `bindings` (до шага 4) по этим псевдофайлам не судится — он и так
устаревает по отпечатку каталога. Ожидание: первый запуск после шага 2 (и после раската
на каждом контуре) даст «реестр устарел» — `vmp/criteria.py` изменён и
блок появился; повторная отправка пакета — штатная пересверка.
Несостоявшийся перевывод на повторе (например, каталог недоступен)
канал не глотает: заметка «вывод реестра исполнителей не удался: …»
дописывается в `detail` краткого вердикта повтора и в строку журнала
приёмов (`registry_note`), приём повтора остаётся принятым, реестр —
прежним.

**Раскат.** По слову владельца; каталог и читатель приходят клоном
репозитория (`catalog/` и `template_catalog/` отслеживаются git);
проверка установки реестр и каталог не проверяет — поручение
(`template_catalog.validate_path()` в шаге проверки установщика); после
раската — повторная отправка пакета на каждом контуре.

## 13.7. Шаг 3: версия каталога в пакете и сторож дрейфа (07.09.2026)

**Зачем.** Пакет постановки выпускает CDPM по каталогу шаблонов, а
считает по нему COSMOS. Если между выпуском и нажатием каталог сменился,
правила пакета, сойдясь по именам, исполнялись бы не тем, чем посажены.
Поэтому пакет НЕСЁТ В СЕБЕ, каким каталогом он выпущен, а нажатие это
сверяет.

**Что в пакете.** Необязательный ключ манифеста `catalog` —
ровно два поля: `version` (версия каталога) и `fingerprint` (его
отпечаток, 64 знака). Ключ появился «Дополнением к 1.18»: номер
спецификации пакета не меняется, эталоны и золотые комплекты не
перевыпускаются, пакет БЕЗ ключа остаётся законным. Рядом стоит сводка
`fits_catalog` — какими ревизиями посажены строки самого пакета.

**Одна мерка вместо двух.** Со шага 3 ревизия посадки правила
(`template_fit.registry_rev`), поле формы ВМП `registry_rev` и
`manifest.catalog.fingerprint` — это одно и то же число: полный
отпечаток каталога. Прежняя 12-значная ревизия реестра кода больше
нигде не считается (она осталась в шапке каталога полем
`legacy_registry_rev`, см. 13.5).

**Что делает сторож при нажатии.** Перед расчётом COSMOS сравнивает
ключ пакета с каталогом, которым идёт сам, и отвечает одним из четырёх
слов; они же стоят в состоянии кнопки (паспорт попытки, поле
`template_catalog.manifest_check`), в журнале нажатия (строка `Ш-1кш`)
и в блоке `catalog` реестра исполнителей этого нажатия:

| Что видит сторож | Слово | Что происходит |
|---|---|---|
| данные каталога те же (версия та же) | `match` | нажатие идёт, строка `Ш-1кш` — «сошлось» (у каталога-черновика добавляется пометка «каталог в черновике» — у черновика одна версия законно несёт разные данные) |
| ключа `catalog` в пакете нет | `not-declared` | предупреждение «версия каталога шаблонов пакетом не объявлена», нажатие идёт (пакет прежнего образца) |
| версия та же, отпечаток другой, и хотя бы одна сторона — ЧЕРНОВИК | `mismatch-fingerprint` | предупреждение с обоими отпечатками, нажатие идёт |
| версия та же, отпечаток другой, обе стороны — ВЫПУСКИ | `stop` | **расчёт не начинается**: «одна версия каталога X — разные данные (отпечаток пакета …, привязок …)», машинный код `catalog-version-mismatch` |
| разница только в младшем числе версии (PATCH), а на версиях от 1.0.0 — и в среднем (MINOR) | `mismatch-fingerprint` (при совпавшем отпечатке — `match`) | предупреждение «patch/minor — продолжаем с предупреждением», нажатие идёт; строка `Ш-1кш` — «предупреждение» даже при совпавшем отпечатке: статус выводится из вердикта, а не из равенства отпечатков |
| разница в среднем числе на версиях 0.x, и ОБЕ стороны — черновики | `mismatch-fingerprint` | предупреждение с обоими отпечатками, нажатие идёт (шаг 4, принцип «стоп защищает выпуски»); слова называют обе версии и обоих участников, а перевыпуск пакета — дело производителя |
| разное старшее число версии (в любую сторону); разница в среднем числе на версиях 0.x, когда хотя бы одна сторона — ВЫПУСК; версия несравнима либо ключ записан не по образцу (нет версии, отпечаток не 64 знака) | `stop` | **расчёт не начинается**: отказ словами называет версию пакета и версию продукта; на панели — до занятия кнопки, попытка не заводится, машинный код отказа `catalog-version-mismatch` |

**Стоп защищает выпуски (шаг 4).** Черновик тем и черновик, что данные
под ним меняются. Останавливать расчёт из-за разницы ЧЕРНОВЫХ номеров
значило бы требовать переиздания всех живых пакетов при каждом
черновике каталога: на локальном контуре это, например, пакет
`cdpm-runs/run-0089/channel/task-package.zip`, выпущенный каталогом
`0.1.0-draft.3`, а на площадках — пакеты, выпущенные до раската
каталога. Поэтому закон один: старшее число — стоп всегда; среднее на
0.x — стоп, как только хотя бы одна сторона ВЫПУСК; два черновика —
предупреждение с обоими отпечатками. Закон живёт в одном месте — в
читателе (`template_catalog.manifest.is_stop`); его зовут и сторож перед
нажатием, и правило B01 проверки привязок, и ни один продукт его не
дублирует.

Отказ самого каталога сторож не судит: строка `Ш-1кш` помечается
«пропущен» словами отказа, а расчёт останавливают свои рубежи.

**Мерка исхода — рядом с исходом.** Паспорт попытки и блок `catalog`
реестра исполнителей несут `manifest_check_against` — версию, отпечаток
и источник той стороны, по которой вынесен исход. С шага 7-Б источник
всегда `catalog`: второй, необъявленной стороны у продукта не осталось.
Поле не убрано намеренно — записи ПРЕЖНИХ прогонов несут в нём
`slice`, и читаются они как прежде.

**Обратная задача H0 после шага 7-Б.** Прогон по срезу базы шаблонов
(переменная `CREW_VMP_TEMPLATE_BASE`) больше не поддерживается: срез
подменял вторую сторону сверки, оставаясь необъявленным в пакете, и
прогон по нему был непроверяем. Обратная задача идёт по каталогу той
версии, которой выпущен пакет; сам срез (`etalon/NSH-H0.json`) остаётся
описью покрытия набора и выводится ИЗ каталога.

**Эталоны.** Наборы H0 и H0-К несут прежнюю 12-значную ревизию и
перевыпускаются ТОЛЬКО по отмашке владельца. До перевыпуска сборка
среза НШ-H0 расходится с эталоном ровно полем `registry_rev`, а разбор
покрытия честно называет это словами (`registry_rev_stale` у эталона,
`rule_rev_mismatch` у свежей сборки) — других расхождений нет. Прежний
пункт очереди «генераторы срезов пишут `catalog_version` и
`catalog_fingerprint`» с шага 7-Б отпал вместе с режимом среза: сверять
пакет с ним больше некому.

**Как проверить.**

## 13.8. Шаг 4: привязки исполнителей, стендовые задачи, раздача параметров, критерии-метрики (08.09.2026)

**Зачем.** Каталог говорит, ЧТО за механика у шаблона. Он не говорит,
КАКОЙ код её исполняет — а без этого «шаблон есть» ничем не отличается
от «шаблон обещан». Шаг 4 заводит третий носитель рядом с каталогом:
привязки продукта. Каждый продукт объявляет своим файлом, каким кодом
он исполняет каждый объявленный вид каждой записи — и говорит словами
там, где не исполняет: «исполнитель — другой продукт» либо «причина
такая-то». Ни одна клетка не остаётся молчащей.

Второе, что заводит шаг 4, — СТЕНД: у каждой записи каталога появляются
стендовые задачи (крошечный синтетический мир и ожидаемые числа), а
прогон стенда показывает, что названный исполнитель действительно даёт
эти числа. Привязка без стенда — обещание; привязка со стендом —
проверяемое утверждение.

**Где что лежит.** Привязки COSMOS — `vmp/bindings.json` (посев
`vmp/bindings_seed.json`, генератор `vmp/bindings_build.py`); привязки
CDPM — `cdpm/bindings.json` (только вид `check_template`). Стенд —
`vmp/stand_tasks.py` с адаптерами `vmp/stand_adapters.py`, результаты —
`vmp/stand_results.json`. Прибавки шага 4 к снимку шага 1 перечислены в
дельте `catalog/transition/step4_additions.json`.

### Форма файла привязок

Шапка называет продукт и его версию, каталог (версию и отпечаток),
момент и коммит сборки, а также ЗОНУ ОТВЕТСТВЕННОСТИ продукта — поле
`executor_kinds`:

    {"product": "COSMOS", "product_version": "1.18.5",
     "catalog_version": "0.2.0",
     "catalog_fingerprint": "<64 знака>",
     "generated_at": "<момент с поясом>", "generated_from": "<коммит>",
     "executor_kinds": [ …десять видов словаря… ],
     "bindings": [{"section": "families", "id": "duty_limits",
                   "executors": [ … ], "stand_verified": [ … ]}, … ]}

Строка исполнителя «есть» несёт язык, файл (путь от корня), символ
(точечный путь) и поля своего вида — параметр и порог у ручки решателя,
имя ограничения у ограничения, шаблон у шаблона проверки, метрику и
задачи у метрики. Строка «нет» символа не несёт: у неё обязательна
ЗАМЕТКА, называющая либо другого исполнителя (продукт, файл, символ),
либо причину. Состояние «заявлен» на шаге 4 не используется: заявок с
ключом CR нет, механизм описан читателем. Оживает он на шаге 6
(раздел 13.10): заявка каталога в состоянии «исполнитель заявлен»
даёт клетку «заявлен» под именем подавшего, а виды исполнителей
решателя, отложенные конвейером пополнения, стоят строками «заявлен»
с ключом того запроса на изменение, который их отложил. Со шага 6
генератор привязок отказывается писать строку «заявлен» без ключа CR.

`generated_from` — коммит, на котором собран файл, то есть РОДИТЕЛЬ
коммита, который его несёт (файла ещё нет в дереве в момент сборки). Так
же поступает генератор CDPM.

**Отпечаток канона.** У файла привязок два лица: сам файл (в нём есть
изменчивые поля — момент сборки, коммит, моменты записей стенда) и его
КАНОН — тот же документ без изменчивых полей. Отпечаток считается
именно от канона (`vmp.bindings_build.fingerprint`), и одна и та же
функция даёт его сверке `--check`, сводке двери, сторожу дрейфа реестра
исполнителей и гейтам. Смысл: перегенерация файла без изменения
исполнителей ничего не старит, а смена строки исполнителя старит сразу.

### Состояния, зоны и «не объявлено»

Клетка проверки — «запись × объявленный вид». Правило полноты (B04)
судит её ПО ЗОНАМ ОТВЕТСТВЕННОСТИ:

* если хоть один продукт сказал «есть» — клетка закрыта;
* иначе каждый продукт, в чьей зоне этот вид, обязан иметь явную строку
  («нет» либо «заявлен»); нет строки — ОШИБКА, и слова перечисляют всех
  продуктов: «вид X у записи Y: COSMOS — нет (заметка), CDPM — в зоне,
  но не объявил»;
* вид, которого нет ни в чьей зоне и который никем не исполняется, —
  ОШИБКА «вид X у записи Y никем не исполняется и ни в чьей зоне»;
* продукт ВНЕ зоны не должен ничего: он не «молчит», он просто не
  отвечает за этот вид.

Зона COSMOS — все десять видов словаря, зона CDPM — один вид
`check_template`. Поэтому один файл COSMOS закрывает полноту сам, а
отсутствие `cdpm/bindings.json` — не остановка, а слова «привязки CDPM
не объявлены» в сводке экрана и в печати гейта.

Слов о чужих привязках ТРИ, а не два: «объявлены», «не объявлены» и «не
читаются». Третье — когда файл CDPM лежит, но не читается (кривой JSON,
не та форма, запись не из каталога, полузаписанный файл в момент её
выпуска). Такой файл снимается с показа, причина уходит в подсказку
сводки, и проекции COSMOS живут дальше: правка в чужой зоне не смеет
останавливать нажатия. Слово «объявлены» говорится только о ПРОЧИТАННОМ
документе, прошедшем читателя (B01–B03), — «файл лежит» ещё не значит
«объявлены». Файл без поля
`executor_kinds` (прежнего образца) читается: зона выводится из самих
строк файла ПО ВСЕМ состояниям, включая «нет», — иначе продукт с одними
«нет» оказался бы вне зоны.

Одна запись может иметь у одного вида несколько строк: у
`duty_extension_penalty` ручка потолка продления — «есть», а ручка
мягкого порога смены — «нет» (ручки решателя нет, порог читают
построитель и сертификат). Для полноты берётся ЛУЧШЕЕ состояние
(«есть» > «заявлен» > «нет»), и именно лучшее показывает экран.

### Стенд шаблонов

У каждой из 24 записей есть стендовые задачи — 29 задач всего. У
четырёх записей их больше одной: `duty_limits` (три мира: предел
смены, предел посадок, размах командировки), `duty_extension_penalty`
(потолок продления и контроль его условий), `days_off_floor` и
`night_series` (по одной задаче на форму правила). Задача — это
крошечный синтетический мир (коды только `ST1…ST9`, `T1…T9`, `P1…`;
данных авиакомпаний в стенде не бывает) и ожидаемые числа по каждому
судимому виду. Записей без задач нет — это сверяет гейт паритета.

Что судится сейчас, в дереве и в pytest: `builder_method`, `check_code`
и сертификатные `check_template` — чистый Python, прогоняется здесь и
сейчас, без сети. Виды решателя (`kotlin_constraint`,
`kotlin_logic_form`, `kotlin_metric`) судятся ЖИВЫМ решателем — но
только командой с ключом `--with-solver <адрес>`; без ключа они отвечают
`skipped` со словами. Не судятся стендом вовсе `kotlin_knob`,
`kotlin_form`, `export_form` и `condition_fn` — у них нет собственного
исхода, они проверяются существованием символа в гейте.

**Живой прогон видов решателя подключён (08.09.2026).** Путь такой:
мир задачи переводится в задачу решателя
(`vmp.stand_adapters.world_to_problem`); правила свода той же задачи
уезжают НАСТОЯЩИМ пакетом постановки, собранным библиотекой CDPM
(`vmp/stand_solver.py`); пакет идёт прогоном по идентификатору, и
повкладовый счёт назначений стенда под пакетом ЭТОГО прогона даёт числа,
которые сверяются с ожиданием записи. Новых ручек решателю не нужно, и
пересборка решателя для этого не требуется — ходят три штатные ручки
кнопки (`/schedules/run`, `.../status`, `.../score-breakdown`) её же
клиентом.

Состав пакета — по правилу: посадки категории A получают ВСЕ семьи, чьи
параметры названы миром (без посадки семьи её пороги до решателя не
доедут), мягкие семьи идут с весом 1, семьи истории — посадкой с
параметрами (решатель выводит форму логики из посадки), а задача вида
`kotlin_metric` кладёт метрику записи в целевую пакета и идёт режимом
оптимизации: вклад целевой при весе 1 существует только в нём.

**Секции пакета, которые стенд несёт из мира, названы ОДНОЙ таблицей**
(`vmp/stand_adapters.py`, `WORLD_TO_PACKAGE_SECTION`; сделано
08.09.2026). Строка таблицы называет оба конца — поле мира задачи и
секцию машинных форм пакета (`threshold-forms.json`) — и носителя,
который их связывает. Сегодня строка одна: `calendar_windows`, поле
мира `rule_form.days` → секция `calendar_window_penalties`, носитель
кладёт дни словами закрытого словаря дней CDPM в цитату посадки правила
(рукотворное поле `export_solver` сборка пакета пересчитывает, а дни
выводит из формулировки и цитаты). Зачем таблица, а не условие в
сборщике: исполнитель вида `kotlin_form` — это секция пакета, и судится
он ПАРОЙ ЗАДАЧ-БЛИЗНЕЦОВ вида `kotlin_constraint`, миры которых
отличаются ровно секцией формы. Пока знание жило условием по имени
семьи внутри сборщика, новая секция требовала правки стенда; со строкой
таблицы стенд не правится. Мир, объявивший форму правила у семьи,
которой в таблице нет, — красная строка словами «секция … из мира
стенда в пакет не собирается», а не пакет без формы: молчаливый пропуск
дал бы близнецам одинаковые числа, и обе строки зеленели бы по
построению.

Судится при этом ПОЛЕ мира, а не одно лишь имя семьи: мир, объявивший у
семьи ИЗ таблицы поле, которого строка не называет (скажем, `weeks` там,
где строка говорит `rule_form.days`), — тоже красная строка словами
«поле мира … секцией пакета не несётся». Носитель отчитывается «повёз
или нет», а собранный пакет проверяется на месте: обещанная таблицей
секция обязана быть в `threshold-forms.json`, иначе строка красная
словами «секция … до threshold-forms.json не доехала». Так закрыты все
три щели молчаливого пропуска: чужое поле мира, промолчавший носитель и
пакет, собравшийся без секции.

**Формы ожиданий видов решателя объявлены ОДНИМ источником**
(`vmp/stand_solver.py`, `GOT_FORMS`; сделано 08.09.2026):
`kotlin_constraint` — `{constraint, matches, amount}`,
`kotlin_logic_form` — `{form, matches, amount: null}`, `kotlin_metric` —
`{value, matches, refusal}`. Конвейер пополнения каталога (раздел 13.10)
берёт формы этих трёх видов ОТТУДА ЖЕ импортом вместо второго литерала
(замена литерала — дорожка конвейера того же пакета работ): второй
источник закона о форме молчалив — разойдись он с
каталогом, агент писал бы ожидания не той формы, и стенд честно краснел
бы по ЛОЖНОЙ причине. Свидетель формы — тест: ключи `GOT_FORMS` равны
ключам ожиданий тех же видов в живом каталоге и ровно тем ключам,
которые стенд кладёт в полученное. Ключ `form` у формы логики
необязателен по замыслу: служба не отдала показаний прогона — судья
говорит «исполнитель значения не дал», а ожидание в полученное не
подставляется.

исполнителей планов `vmp.run.logic_checks._EXECUTORS`, а не из перечня в
стенде. Носитель истины один: форму читает `plan_from_fit`, исполняет
`run_plan` — тот же модуль. Агент конвейера пополнения дописывает форму
в `vmp/run/logic_checks.py` (путь ему открыт), а стенд ему закрыт; с
перечнем в стенде каждая новая форма краснела бы «судьи символа у стенда

кандидат новой семьи `duty_series_limit`, символ `_duty_series`, три

Любой исход `failed` вне явного перечня `KNOWN_FAILED` красит гейт.
Ожидания не подгоняются под полученное: расхождение разбирается словами
— дефект входа стенда правится в адаптере, дефект кода докладывается
владельцу и попадает в `KNOWN_FAILED` только по его слову.

Итог прогона хранится в `vmp/stand_results.json` и вливается в привязки
полем `stand_verified` каждой записи: задача, вид, исход, момент,
коммит и заметка «получено N, ожидалось N (символ)». Строк
подтверждения больше, чем задач: у задачи их столько, сколько видов она
судит (сегодня 29 задач дают 57 строк). В сводке привязок это два
РАЗНЫХ поля — `tasks` (задач) и `rows` (строк подтверждения): одно
число под двумя именами читалось бы неправдой.

Свежесть файла результатов судит гейт: отпечаток каталога и отпечатки
файлов кода обязаны совпасть с текущими, а чистые виды гейт прогоняет
заново и требует тех же исходов — файл результатов не может лгать.
Карта отпечатков кода судится В ОБЕ СТОРОНЫ: не только «названные
отпечатки сошлись с диском», но и «названы ровно те файлы, которыми
стенд свеж». Иначе укороченная карта (в пределе пустая) объявляла бы
себя свежей умолчанием, и чужие исходы попадали бы в `stand_verified`
без единого прогона исполнителя. Коммит прогона обязателен: без git
команда отказывает словами и просит `--commit`, а не пишет файл, который
дверь привязок всё равно отвергнет. Отпечатки
файлов кода считаются ПОСЛЕ приведения перевода строки к одному виду:
на машине владельца файлы материализуются с CRLF, а в облачной сборке —
с LF, и отпечаток сырых байтов объявлял бы результаты устаревшими
везде, кроме машины записи.

**Разметка смен в решении стенда.** Сертификат судит смены, а не рейсы,
поэтому решение стенда размечается ПРАВИЛОМ, а не нарезкой построителя:
рейсы одного сотрудника идут одной сменой, пока пауза до следующего
вылета короче ВЕРХА окна стыковки на станции прилёта (та же линейка
«стыковка или отдых», которой пользуется построитель — решение
владельца 06.09); пауза не короче верха — это отдых и новая смена. Низ
окна при разметке не применяется: короткая пауза остаётся стыковкой
внутри смены, и её судит проверка стыковок — иначе находка исчезала бы
не потому, что нарушения нет, а потому, что смена разрезана надвое.
Правило записано словами в заметке каждой задачи, где оно решает исход.

поле без объяснения читалось бы как «артефакт тот же».

**Стенд укладывается в предел команды сам, а серию обрывает рано**
(08.09.2026). Три отказа ПОДРЯД БЕЗ ЖИВОГО ОТВЕТА службы (соединение не
встало на постановке прогона, состояние прогона не отдано, потолок
ожидания истёк) значат «считать некому»: остальные живые строки красные
словами «решатель не отвечает: прогоны прекращены после 3 отказов
подряд» и БЕЗ новых прогонов — очередь чужой службы стенд не набивает.
ЛЮБОЙ ответ службы счётчик сбрасывает: и пакет, отвергнутый её гейтом, и
прогон, УПАВШИЙ на своём пакете. Падение — ответ живой службы о неудаче
этого пакета: оно приходит первым же опросом и времени не стоит, поэтому
обрыв по нему ничего не экономил бы, а свидетельство прочих строк терял
(три падения подряд у одной записи — не случайность, а общий шаблон мира
её задач, и слова «решатель не отвечает» были бы ложью о живой службе).

Ключ `--budget-s <секунды>` даёт команде предел времени, и отсчёт идёт
от начала серии: исчерпав его, стенд закрывает оставшиеся живые строки
словами «бюджет стенда исчерпан», а файл результатов пишет с ЧАСТИЧНЫМИ
строками — молчаливое «строк меньше» читалось бы как «задач меньше», и
упор в потолок команды конвейера кодом 124 остался бы без диагноза.
Число закрытых бюджетом строк печатается словами в итоге команды.
ОСТАТОК предела уезжает В СТРОКУ: каждое её звено (постановка прогона,
ожидание «готов», разбор счёта) получает потолок не больше остатка, и
кончившийся посреди строки остаток — та же частичная строка теми же
словами. Без этого строка, начатая у самой границы, шла бы своими
прежними потолками (клиент 120 с на обращение, ожидание 60 с) и
переезжала предел на минуты. Чистые виды бюджет не ОБРЫВАЕТ, но их
время в него входит: предел этот — предел КОМАНДЫ, поэтому берите его
секунд на 60 меньше потолка команды конвейера.

**Что правил живой прогон и что осталось красным.** Правился ВХОД
стенда, ожидания не трогались. Форма задачи решателя: аэропорт назван
кодом везде, кроме списка `airports` (второй полный объект того же кода
разбор отвергает целиком), горизонт уезжает полем `window_horizon`,
поля истории мира переводятся в имена записи набора. Норма резерва
уезжает каноном строки «ST1:1» — карту решатель отвергает словами
«норма без уточнителя-кода базы». Дни окна семьи `calendar_windows`
кладутся в цитату правила пакета: рукотворное поле `export_solver`
сборка пакета пересчитывает, а дни выводит из формулировки и цитаты по
закрытому словарю дней CDPM.

Две задачи остались красными честно — их разбор у владельца, ожидания
под расчёт не подогнаны и в `KNOWN_FAILED` без его слова не занесены:

* `families/duty_limits` `st-duty-2` — мир не называет полов отдыха, а в
  пакетном прогоне порог, которого пакет не несёт, равен нулю; нарезка
  смен режет каждый рейс в свою смену, и посадок за смену выходит одна
  вместо пяти. Проба показала: тот же мир с полами отдыха даёт ровно
  ожидаемое (`matches 1`, `amount 1`) — лечится посевом мира, а не
  правкой числа;
* `criteria/positioning_cost` `st-pos-1` — ограничение решателя
  штрафует сотрудника, чьё ПЕРВОЕ назначение вылетает не из базы
  (`ifNotExists` с «позже» отбирает назначение, раньше которого ничего
  нет), а запись каталога и мир задачи были написаны про «последнее
  назначение». Разобрано 08.09.2026: мир задачи переставлен (первое
  назначение вылетает не из базы), текст записи исправлен под
  настоящее поведение решателя словом владельца («число сотрудников,
  начинающих работу вне базы»); ожидание не менялось.

**Что правил первый прогон.** Четыре задачи со скользящими окнами и
месячным накопителем сначала дали красную строку — и правился ВХОД
стенда, а не ожидание. Причина у всех одна: окно судимого правила
заходило за начало горизонта, о сутках до которого мир молчал, либо
месячное окно не помещалось в объявленный горизонт, и исполнитель
честно отвечал «проверка частично прогнана: неизвестных обязательных
окон». Сутки до горизонта названы посуточным календарём истории (ночные
смены в окне, выходные в окне), горизонт месячного накопителя расширен
до конца месяца, а конец последней смены истории у недельного отдыха
отодвинут за начало горизонта. Числа находок при этом не менялись:
каждая из четырёх задач даёт ровно то число, которое объявлено записью.
Правки сделаны единственным законным путём — посевом
`catalog/tools/catalog_seed.json` и пересборкой каталога, поэтому
отпечаток каталога сменился, а привязки и результаты стенда были
перевыпущены под него.

### Экран «Админ → База шаблонов»

Над таблицами появилась строка сводки привязок: файл, каталог,
состояние («сошлось» / «черновик отстал» / «файла нет»), число клеток и
строк «есть», итог стенда и слово о привязках CDPM («объявлены» / «не
объявлены» / «не читаются», причина третьего — в подсказке). В таблицах
семей и критериев — две новые колонки. «Привязки» — по чипу на каждый
объявленный вид: зелёный «есть», серый «нет», жёлтый «заявлен», синий
«вид никем не объявлен» (одна карта цветов на три панели — раздел 13.9); подсказка чипа называет продукты, их состояния
и строки исполнителей. «Стенд» — три числа «прошло / упало /
пропущено»; при единице в среднем числе чип красный.

Экран ПОКАЗЫВАЕТ состояния, а не судит их: суд — гейт продукта
(`python -m vmp.bindings_gate`) и проверка читателя. Каталог недоступен
— экран отвечает 503 словами, как и прежде.

Состояние «файла нет» на ЭТОТ экран не приходит, хотя в перечне
состояний сводки оно есть: без файла привязок карта семей не строится
(запись не называет исполняющего её кода), и экран отказывает целиком
503 словами — половина правды хуже отказа. Строку «файла нет» несёт
сводка там, где её читают без карты семей: блок `bindings` реестра
исполнителей и паспорт прогона.

## 13.9. Шаг 5: служба каталога и пять экранов (08.09.2026)

**Зачем.** До шага 5 каталог правился двумя способами: посевным файлом
`catalog/tools/catalog_seed.json` с пересборкой инструментом извлечения
и правкой файлов руками (последнее ломало отпечаток шапки). Оба пути —
для того, кто читает код. Шаг 5 заводит рабочее место: отдельную службу
`catalog_service` с пятью экранами, где запись каталога правится
карточкой, правка становится ЧЕРНОВИКОМ вне пакета, а в сам пакет она
попадает осознанным действием — «Собрать черновик». Выпуск версии и
решение по заявке остаются за владельцем (слово 06.09.2026).

Служба — третья служба пакета рядом с веб-приложением COSMOS и панелью
CDPM. Она ничего не разбирает сама: читает каталог тем же читателем
`template_catalog`, что и оба продукта, а пишет — писателем
`template_catalog/writer.py`. Одно вычисление на всех: форма файлов,
отпечаток, разница версий и «лучшее состояние клетки» живут в пакете
читателя, не в службе.

### Где лежит

| Что | Где |
|---|---|
| Служба | `catalog_service/` — пакет Python (FastAPI): `__main__.py` (запуск), `settings.py` (настройки), `identity.py` (роли и права), `store.py` (экземпляр каталога, черновики, замки), `assemble.py` (сборка и правило версии), `request_queue.py` (заявки), `releases.py` (выпуск и снимок), `executors.py` (таблица исполнителей), `markers.py` (маркеры заказчика), `journal.py` (журнал действий), `errors.py` (коды и слова отказов), `app.py` (ручки) |
| Контракт службы | `catalog_service/API-CONTRACT.md` — все ручки, формы тел, машинные коды и тексты отказов, переменные, адреса экранов, карта цветов состояний |
| Интерфейс | `catalog-ui/` — одностраничное приложение (Vite + React) по образцу панели CDPM; собранная статика `catalog-ui/dist/` лежит в дереве вместе с исходниками (установка идёт без Node) |
| Писатель и разница | `template_catalog/writer.py` (форма файлов, отпечаток, проверка ДО записи, атомарная замена), `template_catalog/diff.py` («что изменилось» и подсказка уровня правки) |
| Рабочее место службы | папка `CATALOG_WORK_DIR` (умолчание `<каталог данных>/catalog-work/`): `drafts/families/<id>.json`, `drafts/criteria/<id>.json`, `drafts/dictionaries/<ключ>.json`, журнал действий `actions.jsonl`. Вне репозитория, вне отпечатка, вне отметки кэша читателя |
| Выпуски | `catalog/releases/<версия>/` — неизменяемые копии выпущенных версий (шесть файлов + `schema/` + `transition/families_order.json`) |

| Гейты шага 5 | `tests/catalog_service/` (служба, интерфейс, документы), `tests/test_template_catalog_writer.py`, `tests/test_template_catalog_diff.py`, `tests/test_template_catalog_bindings_best.py`, `tests/test_template_catalog_tool_guard.py` |

### Запуск, роли и режимы

Рабочее место владельца (локальная машина):

    set PYTHONUTF8=1
    .venv\Scripts\python.exe -m catalog_service --port 8105 --actor owner

Площадки и установка заказчика — только просмотр:

    .venv\Scripts\python.exe -m catalog_service --port 8105 --read-only

Ключи: `--port` (умолчание 8105), `--host` (умолчание 127.0.0.1),
`--actor owner|analyst`, `--read-only`, `--catalog <папка>`,
`--work-dir <папка>`. Входа и паролей у службы нет — как у панели CDPM,
она слушает петлевой адрес, наружу выходит только туннелем. Значение
`--host 0.0.0.0` задаётся явно и только для доверенной сети.

Два режима и две роли:

| Операция | просмотр | аналитик | владелец |
|---|---|---|---|
| Все экраны, выгрузка одним файлом, сравнение версий, проверка каталога, журнал | да | да | да |
| Сохранить или отменить черновик записи, словаря (без смены статуса) | нет | да | да |
| Черновик со сменой статуса («снять запись», вернуть «есть») | нет | нет | да |
| Подать заявку | нет | да | да |
| Собрать черновик | нет | да | да |
| Принять или отклонить заявку, записать ключ CR, перевести черновик заявки в записи | нет | нет | да |
| Выпустить версию, загрузить каталог одним файлом | нет | нет | да |

Недоступная кнопка не прячется: она показана неактивной, причина — в
подсказке. Отказы приходят словами: «служба каталога в режиме
просмотра: правки, заявки, сборка и выпуск — на рабочем месте владельца
(запуск с --actor owner)» либо «заявки принимает, записи снимает и
версии выпускает только владелец».

### Три слоя: пакет, рабочее место, выпуски

Пакет `catalog/` — единственное, что читают продукты и гейты; правки в
нём появляются только сборкой и выпуском. Рабочее место
`CATALOG_WORK_DIR` — черновики: их не видит ни читатель, ни дверь
COSMOS, ни отпечаток. Папки `catalog/releases/<версия>/` — неизменяемые
снимки выпусков: каждый читается как самостоятельный каталог и несёт
журнал версий с собственной записью.

Отметка кэша читателя судит только файлы верхнего уровня папки
каталога, поэтому черновики, выпуски, переходные носители и копия схемы
экземпляр продуктов не двигают. Временные файлы писателя называются
`<имя>.json.tmp-<номер процесса>` — под образец `*.json` они не подходят.

### Черновик → сборка → выпуск

**Сохранение черновика.** Служба собирает кандидата в памяти (текущий
каталог ⊕ все черновики ⊕ этот) и проверяет его целиком. Отказом
считается только НОВАЯ проблема — та, которой не было у текущего
каталога; поэтому давняя оговорка чужой записи не мешает править свою, а
асимметрия дополнения, созданная правкой, называется по адресу второй
записи. Файлы каталога при этом не меняются, отпечаток прежний.

**Сборка** («Собрать черновик») применяет черновики к телу, дописывает
историю (пять полей: дата, вид, кто, заметка, ссылка), поддерживает
производные инварианты и пишет каталог одним вызовом писателя:

* порядок лексикона — прежний порядок ∩ семьи «есть» со словами-носителями ∪ новые в конец;
* дополнения симметризуются: добавленное дополнение дописывается второй стороне, у снятой записи дополнения очищаются, а её имя убирается у остальных;
* имена, ушедшие в параметры записей, покидают словарь несвязанных имён;
* переходный порядок семей приводится к составу «есть».

Правило версии — одна формула: уровень правки («старшая / младшая /
патч») считается разницей тел, от последнего выпуска берётся пол
следующей версии, номер черновика растёт на единицу, если тройка не
изменилась. Отсюда следствие, которое стоит знать заранее: строка
истории — младшая правка, поэтому ПОСЛЕ выпуска `0.2.0` следующая
сборка даёт `0.3.0-draft.1`, а не `0.2.1-draft.1`.

Порядок замен на диске: разделы → журнал версий → переходный порядок
семей → копия схемы → шапка `catalog.json` ПОСЛЕДНЕЙ. Читатель,
заставший середину записи (миллисекунды), получает честную ошибку
«отпечаток шапки не сходится», а не тихо испорченные данные.

**Выпуск** («Выпустить версию», только владелец) — ДВЕНАДЦАТЬ
предпроверок, каждая словами; любая красная — отказ, на диске ничего не
меняется: (1) режим и роль; (2) черновиков нет; (3) перечень маркеров
заказчика прочитан; (4) проверка каталога без ошибок; (5) версия не ниже
подсказки и старше журнала; (6) репозиторий git есть и дерево `catalog/`
и `template_catalog/` чистое; (7) привязки продуктов не остановятся
сторожем версий; (8) папки выпуска ещё нет; (9) кандидатов конвейера не
осталось; (10) у записей из заявок исполнители названы; (11) заявки в
работе — предупреждение; (12) **паритет с кодом COSMOS** (пакет
«паритет на временном каталоге»): служба зовёт `catalog/tools/parity.py`
подпроцессом по своей папке каталога и своим привязкам COSMOS. Красный
вердикт — отказ `parity-red` (412) словами правила; подтверждением он
НЕ снимается. «Не судился» (инструмента рядом нет, предел, код 2) и
правило, пропущенное с признаком предупреждения (сегодня это L08b
«CDPM ещё не знает метрику …»), молчаливым проходом тоже не
считаются: это отказ `parity-unconfirmed`, который снимается
осознанным полем выпуска `confirm_parity: true` — как стоп сторожа
привязок снимается `confirm_stop`. Действие:
шапка без суффикса черновика, `released_by` — «владелец», запись в
журнале версий с перечнем изменений и полем `code`, снимок
`catalog/releases/<версия>/`.

Смысл поля `code`: это срез кода, в котором лежит ТЕЛО выпуска (дерево
чистое по предпроверке, значит текущий коммит несёт собранный черновик).
Коммит самого выпуска — шапка, журнал и папка снимка — следующий за ним.

Чек-лист после выпуска (порядок обязателен):

1. `catalog\tools\build_from_code.py --refresh --out catalog` — посев и
   дельта получают версию и отпечаток выпуска. Это не правка руками:
   инструмент переписывает только два производных файла;
2. `git add catalog && git commit -m "каталог: выпуск <версия>"` — один
   коммит выпуска: шапка, журнал, папка снимка, посев, дельта и
   удалённые кандидаты (предпроверка 6 судит всю папку `catalog/`,
   поэтому посев после СБОРКИ коммитится ещё до выпуска);
3. цепочка перегенерации привязок и стенда (ниже), генератор CDPM;
4. `catalog\tools\parity.py` → «0 красных»;
5. пакеты, закреплённые на прежнем черновике, остановятся сторожем при
   нажатии — перевыпуск за производителем (CDPM).

База заморозки (снимок шага 1) выпуском НЕ меняется; новая заморозка
нужна только при пересмотре атрибутов базовых записей или расширении
словарей CDPM — и то и другое по слову владельца.

### Заявки на шаге 5

Заявка — запись раздела `requests` вне отпечатка. На шаге 5 её подают
руками с экрана: аналитик или владелец, состояния «подана → принята |
отклонена», решение владельца — только со словами («решение владельца
без слов не записывается»). Принятая заявка получает ключ CR, а в
записи каталога превращается только сборкой: «Перевести в записи»
(`adopt`) пишет ЧЕРНОВИК, и запись со статусом «есть» появляется вместе
с состоянием заявки «есть» одним вызовом писателя. По записи держится
одна незакрытая заявка. Машинная подача от продуктов и путь «заявка →
CR → агент → кандидат» — шаг 6 (раздел 13.10).

### Пять экранов

1. **«Семьи и критерии»** (`#/records`) — список с поиском и фильтрами
   из закрытых словарей (вид, зона, класс, статус, состояние
   исполнителя, «только с черновиками», «только с заявками») и карточка
   записи: шапка, чтение истории, предмет, параметры (единицы, отношения
   и уточнители — выбором из словарей, кнопка «Взять имя из
   несвязанных»), наборы,
   условия, форма правила, семантика, исполнители, шаблоны проверок,
   стендовые задачи, приёмка, происхождение, история. Кнопки:
   «Сохранить черновик» (заметка обязательна), «Что изменилось»,
   «Отменить черновик», «Снять запись» (владелец), «Подать заявку».
   С каталога 0.5.0 в шапке карточки семьи рядом с природой стоит
   «Свидетель природы», рядом с единицей нарушения — «Размер нарушения»,
   а группа «Чтение истории» даёт вид чтения выбором из словаря
   (пусто — семья историю не читает) и слова потребности; единица
   нарушения выбирается кодом со словом каталога рядом
   («`night` — ночь»), и то же слово стоит в колонке списка. Те же поля
   правятся у черновика записи в заявке; свидетелем новой записи заявки
   интерфейс сразу ставит `change_request` — правило X18 другого ей не
   оставляет.
2. **«Словари»** (`#/dictionaries`) — опись ключей (вид, размер, число
   использований, черновик) и карточка ключа: перечень правится
   значениями, порядок лексикона — стрелками, объект — полем JSON.
   Словарь-карта «код → слово» (с 0.5.0 таков `violation_units`) сверх
   поля JSON ПОКАЗЫВАЕТСЯ таблицей «Код — слово» по правимому значению:
   слово видно сразу, а не только в разметке. Вычисляемые ключи и
   служебные перечни правке не подлежат и говорят
   это словами. Под карточкой — журнал ключа из журнала действий и
   перечней изменений выпусков.
3. **«Заявки»** (`#/requests`) — список с фильтрами, карточка заявки с
   черновиком записи и его замечаниями, действия владельца («Принять» /
   «Отклонить» со словами, «Заявить исполнителя», «Перевести в записи»),
   форма подачи `#/requests/new` с предзаполнением из ссылок продуктов.
4. **«Исполнители по продуктам»** (`#/executors`) — только чтение:
   карточка файла привязок каждого продукта (найден, версия продукта,
   версия и отпечаток каталога, момент и коммит сборки, свежесть
   «сошлось / черновик отстал / остановка сторожа / не объявлены»,
   замечания), матрица «запись × вид × продукт» с чипом лучшего
   состояния клетки, колонка стенда, итоги.
5. **«Версии и выпуски»** (`#/versions`) — шапка каталога, блок
   черновиков со «что изменилось», сборка, журнал версий с чипом папки
   выпуска, сравнение двух версий, выпуск с чек-листом предпроверок,
   выгрузка и загрузка одним файлом, журнал действий службы.

Шапка каждого экрана — строка состояния: версия и отпечаток каталога,
черновик или выпуск, режим и роль, число черновиков и открытых заявок.
Цвета состояний исполнителя одни во всех трёх панелях: «есть» —
зелёный, «заявлен» — жёлтый, «нет» — серый, «вид никем не объявлен» —
синий с подсказкой, ошибки проверки привязок — красный.

### Ссылки из продуктов

Адреса строятся из `CREW_CATALOG_URL` по образцу
`<адрес>/ui/#/records/families/<id>`; у ссылки на карточку записи два
параметра — `?version=` и `?fingerprint=`, по ним служба честно
говорит «продукт закреплён на такой-то версии, показана такая-то».
Адреса в артефакты продуктов не пишутся: в реестре, паспорте и пакете
живут только версия и отпечаток, ссылку строит экран.

### Точки наблюдения

`GET /healthz` — жив ли процесс (диск не трогает); `GET /readyz` —
готовность с перечнем проверок (каталог, собранный интерфейс, рабочая
папка) и числом ошибок проверки каталога; `GET /versionz` — версии
службы и читателя, версия и отпечаток каталога, срез кода, режим и
роль. Наружу идут состояния и отпечатки — ни абсолютных путей, ни
значений настроек.

Признак «интерфейс собран» отдаётся честно, но в готовность не
входит: служба без собранной статики продолжает обслуживать `/api`,
а обращение к `/ui/` отвечает 503 словами «интерфейс не собран». Это
состояние, а не неготовность.

### Судьба гейтов содержания после сборки

Гейты содержания после сборки НЕ краснеют по построению (пакет «паритет
на временном каталоге», 08.09.2026). База заморозки — снимок шага 1
(блок `base` посева), а рост от неё описывает вычисленная дельта:
законный рост каталога перестал быть расхождением, потому что закон
паритета сверяет каталог с КОДОМ, а не с числом. Цепочка после каждой
сборки (порядок обязателен) начинается перегенерацией производных
носителей и кончается законом:

    .venv\Scripts\python.exe catalog\tools\build_from_code.py --refresh --out catalog
    .venv\Scripts\python.exe -m vmp.stand_tasks --write-results vmp\stand_results.json
    .venv\Scripts\python.exe -m vmp.bindings_build --out vmp\bindings.json --stand-results vmp\stand_results.json --prune-pending
    .venv\Scripts\python.exe -m cdpm.stand_tables --out cdpm\stand_results.json --tasks catalog
    .venv\Scripts\python.exe cdpm\bindings_build.py --out cdpm\bindings.json --stand-results cdpm\stand_results.json
    .venv\Scripts\python.exe -m vmp.bindings_gate vmp\bindings.json cdpm\bindings.json
    .venv\Scripts\python.exe catalog\tools\parity.py

Две строки CDPM — её генераторы (стенд таблиц и привязки CDPM, часть
10): их порождённые файлы входят в тот же коммит сборки или выпуска,
что и файлы COSMOS, иначе дверь CDPM останавливается по B01, а тест
стенда таблиц краснеет (урок выпуска 0.3.0 09.09.2026: файл
`cdpm/stand_results.json` остался с отпечатком 0.2.0). Гейт привязок
читает обе стороны, поэтому идёт после них.

До первой строки правило L23 красно СЛОВАМИ («посев отстал от каталога
<версия> — выполните `--refresh`»), после неё — зелено. Посев и дельту
коммитят вместе со сборкой: предпроверка 6 выпуска судит всю папку
`catalog/`, включая `tools/` и `transition/`. Эти же пять команд службы
(`--refresh`, три команды стенда и привязок, закон паритета) приходят в
ответе «Собрать черновик» строками `next`; строка зоны CDPM в них не
входит — её выполняет производитель.

Ни один гейт при этом не убран и не смягчён: новая заморозка нужна
только при пересмотре АТРИБУТОВ базовых записей или расширении словарей
CDPM — по слову владельца.

### Как проверить

1. Поднять службу на копии каталога (живой пакет для проб не нужен):

        set PYTHONUTF8=1
        set CREW_TEMPLATE_CATALOG=<копия>\catalog
        set CATALOG_WORK_DIR=<копия>\work
        .venv\Scripts\python.exe -m catalog_service --port 8105 --actor owner

   Ожидание: строка старта с адресом, папкой каталога, версией,
   отпечатком и режимом «рабочее место: владелец».
2. Открыть `http://127.0.0.1:8105/ui/` — строка состояния несёт версию,
   отпечаток, число черновиков и открытых заявок; `/healthz` отвечает
   `ok`, `/readyz` — `ready: true` с перечнем проверок, `/versionz` —
   версии службы, читателя и каталога.
3. Открыть карточку записи, изменить заголовок, сохранить черновик с
   заметкой. Ожидание: «Черновики службы: 1», «Что изменилось» называет
   поле и уровень «патч»; отпечаток каталога НЕ изменился.
4. «Собрать черновик». Ожидание: версия по правилу (номер черновика +1
   при той же тройке), новый отпечаток, черновиков 0, в ответе — строки
   цепочки перегенерации: ПЕРВАЯ — `build_from_code.py --refresh --out
   catalog`, ПОСЛЕДНЯЯ — `catalog\tools\parity.py`.
5. Прогнать цепочку из ответа. Ожидание: `--refresh` переписал ТОЛЬКО
   посев и дельту (шесть файлов разделов и журнал байт в байт прежние);
   генератор привязок и гейт продукта зелёные; `catalog\tools\parity.py`
   отвечает «0 красных» кодом 0. Красные гейты содержания «по
   построению» — состояние, снятое пакетом «паритет на временном
   каталоге»: если закон красен, он называет ПРАВИЛО и адрес.
6. Подать заявку с экрана, принять её словами, «Перевести в записи»,
   собрать черновик. Ожидание: запись появилась со статусом «есть»,
   заявка перешла в «есть», история записи — три строки (заявка,
   решение владельца, создание).
7. «Выпустить версию» на копии в репозитории git с чистым деревом.
   Ожидание: двенадцать строк чек-листа предпроверок, двенадцатая —
   «паритет с кодом COSMOS» зелёная; шапка без суффикса, `released_by` —
   «владелец», запись журнала с полем `code`, папка
   `catalog/releases/<версия>/` читается как самостоятельный каталог с
   нулём ошибок. Подмените инструмент паритета заглушкой с кодом 1 —
   выпуск отказывает `parity-red` словами правила; заглушкой с
   пропущенным правилом-предупреждением — требует `confirm_parity`.
   На выпущенной копии: `catalog\tools\parity.py --catalog
   <копия>\catalog\releases\<версия>` → 0 (правила L13 и L23
   пропущены СЛОВАМИ: описи и посева в снимке выпуска нет).
8. Целевая команда шага 5 (полный pytest не нужен):

        set PYTHONUTF8=1 && .venv\Scripts\python.exe -m pytest -q tests\catalog_service tests\test_template_catalog_writer.py tests\test_template_catalog_diff.py tests\test_template_catalog_bindings_best.py tests\test_template_catalog_releases.py tests\test_template_catalog_tool_guard.py tests\test_template_catalog_reader.py tests\test_template_catalog_validate.py tests\test_template_catalog_current.py tests\test_template_catalog_parity.py tests\vmp\test_catalog_access.py tests\vmp\test_bindings.py tests\test_template_base.py tests\test_i18n_parity.py tests\test_declared_dependencies.py tests\test_store_isolation.py

   Перед коммитом собранного интерфейса — `npm run build` и
   `npm run lint` в `catalog-ui/`: гейт сверяет штамп свежести сборки с

## 13.9-бис. Квитанция заявки и свидетельство поддержки (12.09.2026)

**Зачем.** Аудит CDPM нашёл две дыры, из-за которых машина верила себе
на слово. Первая (K07): клиент считал заявку поданной по ЛЮБОМУ ответу
без ошибки — страница входа площадки с кодом 200 засчитывалась как
приём, и файл очереди уезжал в «отправленные», хотя служба его не
видела. Вторая (K06): служба разрешала перевести заявку в записи, если
нужный вид исполнителя был написан ХОТЬ У КАКОЙ-НИБУДЬ записи каталога
— «duty_series_limit умеет kotlin_knob» принималось за «ручка написана и
для новой семьи». Обе закрыты одинаково: у ответа и у исполнимости
появился ПРИКЛАДНОЙ носитель с версией схемы, и ни то, ни другое больше
не выводится из косвенных признаков.

### Квитанция заявки (`receipt/1`)

`POST /api/requests` отвечает квитанцией: 201 у новой заявки, 200 у
повторной подачи той же (`note`: «уже подана», `repeat: true`). Тело —
одной формы в обоих случаях:

```json
{"schema_version": "receipt/1",
 "request_id": "req-04763385720803207704", "state": "подана",
 "note": null, "repeat": false,
 "catalog": {"version": "0.5.0", "fingerprint": "<64 hex>"},
 "section": "families", "record_id": "duty_limits",
 "canon": "<64 hex канона черновика>",
 "decision": {"by": null, "at": null, "words": null, "version": 0},
 "journal_ref": {"op": "request-submit", "at": "…", "actor": "владелец"},
 "issued_at": "…", "request": {…}, "submitted_by": "CDPM",
 "words": "…", "problems": []}
```

Схема — один носитель у читателя
(`template_catalog/schemas/receipt.schema.json`) и байт-в-байт копия у
службы (`catalog_service/schemas/receipt.schema.json`): её читают обе
стороны, и разойтись им негде. Перечень слов состояния (`state`) закрыт
ТАМ ЖЕ, полем `enum`: клиент судит ответ службы, каталога которой у него
может не быть вовсе, и своей копии словаря у него нет (равенство
перечня словарю `request_states` каталога держит стенд).

**Закон клиента — одна функция, а не два похожих перечня:**
`template_catalog.receipts.validate_receipt(body, sent=<заявка>)` —
пустой перечень бед значит «квитанция». Её зовут оба клиента:
`catalog_service/import_requests.py` (COSMOS) и
`cdpm/catalog_requests.deliver_one` (CDPM). Заявка ДОСТАВЛЕНА, только
если код 201 либо 200 со словами «уже подана», содержимое —
`application/json`, тело проходит схему, состояние — слово закрытого
перечня, а номер, раздел, запись и канон черновика в теле равны
отправленным. Тип содержимого судится ТОЧНО (`application/json` с необязательными параметрами; `application/jsonp` и ответ без заголовка — не квитанция), а необязательная вложенная запись `request`, если она в теле есть, обязана быть о ТОЙ ЖЕ заявке и ТОЙ ЖЕ редакции: номер, раздел, запись, канон, состояние и
`by`/`words`/`at` решения согласованы с самой квитанцией — иначе решение одной записи подтверждало бы состояние другой. Обе строгости уже держит клиент CDPM; перенести их в общую функцию читателя (и тем самым в инструмент импорта COSMOS) — открытый остаток стороны COSMOS. Иначе исход «неизвестен»: файл остаётся в очереди, повтор
идёт ТЕМ ЖЕ номером (номер содержательный — второго не бывает). Не
квитанции: страница входа с кодом 200, пустое тело, 204, чужой номер,
ответ про ДРУГУЮ запись, состояние вне перечня, 201 с признаком
повторной выдачи и ответ СТАРОЙ службы без `schema_version`. Последнее
задумано: площадка со старой службой обязана обновляться одним раскатом.
Код ответа, тип содержимого и согласие повтора с кодом — дело
транспорта, и их добавляет клиент: тело о своём HTTP-коде не знает.

Отказ по столкновению содержания теперь один — `409 request-exists`: и
когда по записи уже открыта другая заявка, и когда тот же номер пришёл с
иным черновиком (`extra.existing`, `extra.state`, `extra.ref`). Прежний
отдельный код `duplicate-request` снят — случай один, и поступает с ним
клиент одинаково (перечень кодов в 13.10 читать с этой поправкой).
Отклонённая заявка отказывает `409 request-closed` и НАЗЫВАЕТ решение:
`extra.decision` со словами владельца, версией решения и временем — без
них панель прогона показывала бы «отклонена» без причины. Оговорка о
версии решения: до каталога 0.6.0 `decision.version` говорит только
«решения нет» (0) либо «решение есть» (1) — счётчика пересмотров у
записи заявки пока нет, и отличать новое решение от старого обязано
время `at`, а не номер версии.

### Свидетельство поддержки (`support/1`)

Носитель — файл `catalog/support.json` рядом с разделами. Он ВНЕ
отпечатка каталога (как `requests.json`): его запись не меняет ни
версии, ни отпечатка, и закреплённый на отпечатке продукт от пересчёта
не встаёт. Схема файла — `template_catalog/schemas/support.schema.json`
(у службы байт-в-байт копия, как у квитанции), и она ПРИМЕНЯЕТСЯ при
каждом чтении, а не лежит рядом для красоты. Ячейка — `раздел × запись ×
вид исполнителя × продукт`:

| Слово ячейки | Когда |
|---|---|
| `есть` | строка «есть» в привязках продукта И стенд ПО ЭТОМУ виду на этом отпечатке без провалов (≥ 1 `passed`, 0 `failed`) |
| `нет` | строки нет, либо «нет», либо «заявлен» — обещание исполнителем не делает |
| `не проверено` | строка «есть» без подтверждения на этом отпечатке: стенда нет, стенд один `skipped`, провал, либо файл привязок написан для другого каталога |

Рядом с состоянием ячейка несёт всё, чем оно доказано: строку привязок
(`binding`), идентичность файла привязок (`bindings_file`: sha256,
версия продукта, коммит генерации, версия и отпечаток каталога), стенд
(`stand`: задачи, счётчики, коммит, момент) и акт владельца
(`approved`). Для готовности «не проверено» = НЕ ПОДДЕРЖАНО: догадки
«наверное, поддерживается» в дереве больше нет.

Три роли — один носитель. **Заявляет** продукт: файлом привязок
(`vmp/bindings.json` — COSMOS, `cdpm/bindings.json` — CDPM) и
стендовыми подтверждениями. **Вычисляет** служба каталога ОДНОЙ функцией
читателя `template_catalog.bindings.support_table` — её же зовёт CDPM,
читая файл через `Catalog.support()`: второй формулы «исполнимо» в
дереве нет. **Утверждает** владелец АКТОМ ВЫПУСКА: выпуск считает
таблицу заново по выпущенному телу, заполняет `approved` у
подтверждённых ячеек и кладёт неизменяемую копию в
`catalog/releases/<версия>/support.json`. Между выпусками `approved`
пуст.

Две ручки: `POST /api/support/refresh` (аналитик+) — пересчитать и
положить файлом; `GET /api/records/{раздел}/{id}/support` —
ПРЕДСТАВЛЕНИЕ того же файла (ручка ничего не считает: второй источник
правды разошёлся бы с файлом в первый же день, когда привязки
поменялись, а свидетельство ещё нет). Свидетельства нет — ручка говорит
«не вычислено», и это не поддержка. Записи нет — `404 unknown-record`,
как у остальных ручек записи: опечатка в имени не должна выглядеть
пустой поддержкой.

Годность свидетельства судит ОДНА функция читателя
(`template_catalog.bindings.support_of`): знакома ли версия схемы
(закрытый перечень `support/1`), та же ли версия каталога и тот же ли
отпечаток. Её зовут ручка службы, дверь COSMOS и CDPM — трёх своих
сверок не бывает. Файл неизвестной версии схемы читателем не
отдаётся вовсе: `Catalog.support()` отказывает словами, а ручка
отвечает `503` («свидетельство неизвестной версии схемы …») — общий
закон 5 контракта П0. Файл ЧУЖОГО отпечатка — не отказ, а `stale: true`
со словами: ячейки показаны, исполнимостью не считаются.

**Перевод заявки в записи** (`POST /api/requests/{id}/adopt`) судит
исполнимость ОДНИМ законом — ячейками СВИДЕТЕЛЬСТВА этой записи
(`state == "есть"`, то есть строка привязок И стенд по виду И файл
привязок того же каталога). Строка «есть» без стендового подтверждения
даёт «не проверено» и перевода не открывает; файл привязок, написанный
для другого каталога, — тоже. У новой записи ячеек нет по построению
(B02: привязки не знают записи, которой ещё нет), поэтому перевод
честно отказывает `412 executor-not-present` словами:

> у записи families/audit_series_limit не подтверждена поддержка видов
> kotlin_constraint, kotlin_knob ни одним продуктом: свидетельство
> поддержки на каталоге 0.5.0 5534196f8248 — «есть» нет (строка
> привязок без стенда по виду и файл привязок иного каталога дают «не
> проверено»); продолжить осознанно — полем confirm со словами

В `extra.support` отказа лежат ЯЧЕЙКИ СВИДЕТЕЛЬСТВА этой записи — то
самое, чем судили, а не строки файлов привязок.

Осознанный обход владельца сохранён: поле `confirm` со словами переводит
запись и кладёт слова в её историю. Поздний барьер тоже сохранён —
предпроверка выпуска 10 (`executors-incomplete`) не выпускает версию,
где у записи из заявки исполнитель не назван. Вопрос у неё ДРУГОЙ, чем
у свидетельства, и потому закон другой: свидетельство отвечает
«исполнимо ли» и засчитывает одно («есть» со стендом), а предпроверка
отвечает «названы ли исполнители» и засчитывает три честных исхода —
«есть», «заявлен» с ключом CR и «нет» с заметкой. Свежесть самих файлов
привязок судит предпроверка 7 (`bindings-stop`) — там свой код, и двух
кодов на одну беду не бывает.

**Как проверить.**

    set PYTHONUTF8=1 && .venv\Scripts\python.exe -m pytest -q tests\test_w17b_catalog_service_receipt.py tests\test_w17b_catalog_service_support.py tests\catalog_service

Глазами: поднимите службу владельцем, нажмите
`POST /api/support/refresh` — рядом с разделами появится
`catalog/support.json`, а `GET /api/catalog` покажет ТОТ ЖЕ отпечаток,
что и до пересчёта. Заведите заявку на новую запись и попробуйте
перевести её в записи пустым телом — служба назовёт запись и виды, а не
скажет «вида нет в файлах привязок».

## 13.10. Шаг 6: конвейер пополнения — заявка, запрос на изменение с ключом записи, кандидат (08.09.2026)

**Зачем.** Шаги 1–5 отвечают на вопрос «что в каталоге есть». Шаг 6
отвечает на вопрос «что делать с тем, чего в каталоге НЕТ». Пробел
находится в двух местах: CDPM при разборе документов видит правило, под
которое шаблона нет (посадка категории C), а COSMOS при нажатии кнопки
расчёта видит правило, которое некому исполнить. Раньше и то и другое
превращалось в текст в очереди изменений — сегодня превращается в
ЗАПИСЬ каталога: заявку.

Путь заявки: заявка → решение владельца словами → запрос на изменение
(CR) с ключом записи → агент-исполнитель в изолированном контуре →
файл-кандидат записи с доказательствами гейтов → «Перевести в записи» и
сборка → запись каталога «есть» → выпуск младшей версии. На каждой
ступени видно состояние, и ни одна ступень не делается молча.

### Три входа заявки

| Вход | Что едет в заявку | Кто подаёт | Как рождается |
|---|---|---|---|
| Посадка категории C в CDPM | обобщённая механика правила (семь полей модели-составителя), класс документа, ссылка «прогон CDPM + хвост ключа» | `CDPM` | автоматически по готовности модели; пять слоёв проверки обезличенности до записи в очередь |
| Пробел при нажатии в COSMOS | раздел, запись, виды исполнителей, ссылка «прогон COSMOS + хвост ключа»; ни формулировки правила, ни его идентификатора, ни источников | `COSMOS` | автоматически при остановке кнопки (либо кнопкой «Заявить в каталог», если автоподача выключена) |
| Вручную с экрана службы | то, что ввёл человек; форма подсказывает правила обезличенности и даёт предпросмотр отказа до подачи | `аналитик` / `владелец` | форма `#/requests/new` |

Правило «без данных заказчика» стоит четырьмя слоями: форма заявки (у
COSMOS в файле очереди нет ни формулировки, ни источников, ни имён — это
проверяет отдельный сторож); проверка службы правилами обезличенности по
всем полям источника, черновику и СЛОВАМ РЕШЕНИЯ владельца; строка
запроса на изменение, которая несёт только обезличенную спецификацию и
виды; выпуск версии, который без перечня маркеров заказчика не делается.

### Закон номера заявки и ключа CR

Номер заявки — не счётчик, а содержание. Один закон живёт в читателе
(`template_catalog/requests.py`) и применяется всеми: CDPM, COSMOS,
службой и человеком. Иначе номера двух продуктов на трёх машинах не
сошлись бы без обмена, а повторная подача плодила бы дубли.

* материал новой записи — «раздел + вид + зона + нормализованная формулировка»; нормализация: единая форма Юникода, приведение регистра, схлопывание пробелов и знаков препинания;
* материал заявки на вид исполнителя — «kinds + раздел + запись + отсортированный набор видов»;
* материал ручной подачи — «manual + раздел + запись + канон черновика»;
* номер: `req-` и 20 цифр от первых 16 знаков отпечатка материала;
* ключ запроса на изменение: `cr` и 8 знаков от отпечатка строки «catalog-request:<номер>».

Три свидетеля одного закона — тест читателя, тест CDPM и тест продукта
COSMOS — сверяют одни и те же литералы:

| Материал | Ключ | Номер заявки | Ключ CR |
|---|---|---|---|
| `families \| HARD \| PAIRING \| «правило образец сторожа закона»` | `421af21358a4aa18…` | `req-04763385720803207704` | `crd89c9550` |
| заявка на вид: `families / duty_limits / [kotlin_knob]` | `33729a630c940327…` | `req-03707195193482806055` | `cr575b6c6a` |

Набор видов — часть содержания: те же запись и раздел с видами
`kotlin_knob, check_code` дают другой номер (`req-11038172079365523094`).
Регистр и пунктуация формулировки на номер не влияют; другой вид, зона
или раздел дают другой номер.

Честная оговорка: номер заявки на НОВУЮ запись служба пересчитать не
может — формулировки правила у неё нет и быть не должно; она принимает
номер от подателя по образцу. Номер заявки на вид исполнителя служба
пересчитывает сама и отклоняет чужой (`bad-request-id`).

### Состояния заявки и переходы

Состояния — ровно те пять, что есть в словаре каталога: «подана»,
«принята», «отклонена», «исполнитель заявлен», «есть». Ничего не
удаляется: отклонённая заявка остаётся историей пробела.

| Из → в | Кто | Чем |
|---|---|---|
| — → подана | CDPM, COSMOS (машинно, с токеном), аналитик или владелец (экран), инструмент импорта очередей | `POST /api/requests` |
| подана → принята \| отклонена | **только владелец**, со словами | `POST /api/requests/{id}/decide` |
| принята → исполнитель заявлен | COSMOS при сверке (машинно) либо владелец кнопкой | `PUT /api/requests/{id}/cr_key` |
| принята \| исполнитель заявлен → отклонена | **только владелец**, со словами | `decide` |
| отклонена → принята (пересмотр) | **только владелец**, со словами | `decide` |
| принята \| исполнитель заявлен → есть | владелец: «Перевести в записи» → сборка | `POST /api/requests/{id}/adopt`, затем сборка |

Незаконный переход — отказ словами (`bad-transition`): «заявка req-… в
состоянии «есть» — решать нечего»; «ключ CR принимается только у
принятой заявки». Отзыв подателем состоянием каталога не заводится:
пока номер не принят службой, продукт убирает файл из своей очереди;
после — путь назад только через решение владельца.

Видимость: с «подана» пробел виден на экране «База шаблонов» и в
перечне записей службы как «заявлен»; с «исполнитель заявлен» — клетки
исполнителей под именем подавшего и строка CR в очереди изменений; с
«есть» — запись, её история и привязки после перегенерации.

### Запрос на изменение с ключом записи

Строка очереди изменений COSMOS рождается СВЕРКОЙ заявок каталога с
очередью, а не второй отмашкой человека: решение владельца уже принято в
каталоге, и второй раз его не спрашивают. Ключ строки — `cr_key_of` от
номера заявки, поэтому один и тот же CR открывается в любом экземпляре
COSMOS без переноса очереди.

Что несёт строка: вид `catalog-executor`; адрес записи (раздел,
идентификатор, номер заявки, форма заявки, состояние на момент
открытия, кто подал, откуда, версия и отпечаток каталога); спецификацию
(черновик заявки либо запись целиком) и перечень видов исполнителей
к реализации с подсказкой места по образцу строк «есть» того же вида;
перечень отложенных видов с причиной; закон приёмки; ЗАКОН ПАРИТЕТА
словами (что обязана объявить запись кандидата при росте таблиц
решателя — 13.13); белый и чёрный списки путей; адрес файла-кандидата;
команды самопроверки, среди них `python catalog/tools/parity.py
--with-candidates` — тот же вердикт, который даст пятый гейт.

Задание агенту, кроме содержимого строки, несёт ИТОГИ ПРОШЛОЙ ПОПЫТКИ
(с 09.09.2026): красные строки стенда с заметками судей, слова гейтов,
которые не сказали «ok», красный паритет и имена красных тестов набора
клона прошлой попытки — обезличенно, словами судей. Ветка каждой
попытки пересоздаётся от `main`, работа делается заново, и без этого
блока следующая попытка повторяла бы прежнюю ошибку: судьи добавляются,
агент не подменяется человеком (Часть 7). Первой попытке наследовать
нечего — блока в задании нет.

Чего строка НЕ несёт — и это проверяется гейтом: машинной формы правила
авиакомпании, текста правила, источников, слов решения владельца.
Задание агенту строится из строки, значит и в задание они не попадают.

**Порядок исполнения** («Реализовать на Тест»):

1. предпосылки: клон несёт код каталога; при наличии удалённого
   репозитория ветка берётся от свежей головы; отпечаток каталога в
   клоне равен тому, по которому открыт CR (иначе отказ с двумя
   причинами: клон отстал либо каталог изменился после открытия). Сюда
   же встаёт **проба тулчейна** — у КАЖДОГО CR каталога, а не только у
   заявок с видами решателя: Java, обёртка Maven, кэш зависимостей
   нужных версий, импорты венва клона, право записи в `_repro/`.
   Причина: решатель собирается и поднимается у каждого CR (цепочка
   живого каталога иначе понизила бы строки видов решателя до
   `skipped`), поэтому «сборка недоступна» обязана звучать словами ДО
   ветки и ДО траты суточной квоты реализаций, а не после. Заодно
   снимаются эфемерные решатели прошлых попыток ЭТОГО контура, если они
   пережили перезапуск;
2. агент пишет код исполнителя только в файлах перечня исполнителей,
   строки посева привязок и файл-кандидат; команд git не выполняет.
   Модель агента названа заранее: настройка площадки «coding» в
   «Настройки → Модели», без неё — умолчание кода claude-opus-5 (слово
   владельца 09.09.2026: «Opus для реализации, Fable для суждения»); имя
   модели пишется в запись строки CR (`impl.agent_model`);
3. **коммит работы агента — ДО гейтов содержания**: красный гейт не
   стирает сделанное. Личность автора коммита конвейер везёт СВОЮ
   (умолчания «COSMOS agent» и `agent@cosmos.local`, ручки
   `COSMOS_AGENT_NAME`/`COSMOS_AGENT_EMAIL`): клон контура — машинный, и
   в клоне без настроенной личности git отказывал бы «Author identity
   unknown». Исход коммита ПРОВЕРЯЕТСЯ по коду возврата и по сдвигу
   `HEAD`; при отказе строка уходит в `needs_human` словами «работа
   агента не закоммичена: …», а сама работа сохраняется патчем
   `_repro/catalog-cr-<ключ>/attempt-<n>/agent-work.patch` (рядом —
   `agent-work-untracked.txt`, если были неотслеживаемые файлы): папка
   `_repro/` закрыта `.gitignore`, и уборка клона её не уносит;
4. **сборка решателя (шаг 3-К)** — у каждого CR: исходники берутся ИЗ
   КОММИТА ветки в отдельную папку попытки
   (`_repro/catalog-cr-<ключ>/attempt-<n>`), сборка идёт оффлайн
   обёрткой Maven с выключенным демоном компилятора. При правках
   `kotlin-solver/` (проверяется diff'ом против `main`, а не перечнем
   видов) после упаковки прогоняются тесты решателя, а отпечатки
   артефакта снимаются ДО и ПОСЛЕ них: тесты не вправе подменить то,
   что запускается. Сразу за сборкой и тестами идёт **сторож дерева
   клона**: тесты решателя исполняет surefire под учётной записью
   службы, и одна строка теста, дописывающая файл судьи, сделала бы
   зелёными всех судей разом. Дерево обязано быть тем же, каким его
   оставил коммит работы агента; красный исход НАЗЫВАЕТ файлы и
   останавливает суд. Затем из собранного артефакта поднимается
   **эфемерный решатель** — свободный порт вне резервного окна
   контуров, только петлевой адрес, метка
   `-Dcosmos.ephemeral=<тег контура>:<ключ>` (тег — восемь знаков от
   пути клона: Test, Stage и Prod живут на одной машине под одной
   учётной записью, и без тега сборщик сирот снял бы чужого живого
   судью), сверка «порт слушает именно наш процесс». Останавливается он
   в `finally`, при любом исходе гейтов. Для `implemented` сверка
   PID↔порт и свобода порта после остановки обязаны СОСТОЯТЬСЯ:
   «не проверено» считается красным наравне с «не сошлось»;
5. цепочка на живом каталоге клона: стенд → генератор привязок → гейт
   привязок (полный `pytest -q` клона идёт ПОЗЖЕ — после гейтов п. 6 и
   остановки решателя). Стенд идёт с ключом `--with-solver` на
   эфемерный решатель — свидетельство всего каталога не понижается:
   виды решателя, которые без живого решателя были бы `skipped`,
   судятся живьём. У `pytest` нет ни ключей `--ignore`, ни перечня
   «ожидаемо красных»: свидетель паритета в дереве судит «живой каталог
   ⊕ кандидаты `catalog/candidates/**`», то есть ровно то, что несёт
   ветка, — и зелен по существу (13.13);
6. гейты на ВРЕМЕННОМ каталоге «живой ⊕ запись кандидата»: стенд на
   этом каталоге ЦЕЛИКОМ (файл результатов — свидетельство всего
   каталога, сузить прогон и записать файл стенд отказывает словами),
   а суд идёт по строкам записи: у видов, которые стенд судит, — хотя
   бы одна пройденная задача и ни одной упавшей; красная строка у
   соседней записи временного каталога тоже краснит гейт и называется
   словами (правка словарей и порядка семей достаёт соседей). У видов
   решателя суд строже: по ПРЕДМЕТУ строки посева (имя ограничения,
   форма логики, метрика — совпадает ли то, что сработало, с тем, что
   заявлено) и по РАЗЛИЧАЮЩИМ задачам — одна с нулём срабатываний и
   одна с ненулевым, иначе «исполнитель, который молчит всегда»
   выглядел бы зелёным; у ручек и форм пакета — по паре
   задач-близнецов на той же записи, миры которых различаются одним
   полем. Регрессия по соседям считается ЧИСЛОМ против `main`:
   зелёных по каждому виду не меньше, красных ноль, понижение судимой
   строки до `skipped` — красное. Затем генератор и гейт привязок,
   проверка каталога с записью кандидата — ноль ошибок (каталог «живой
   ⊕ кандидат» судится с версией СЛЕДУЮЩЕГО ЧЕРНОВИКА, как временный
   каталог гейтов и как сборка службы: на выпущенном каталоге любая
   запись меняет тело и отпечаток шапки, и с номером выпуска в шапке
   читатель отвечал бы H03 «отпечаток записи журнала не равен шапке» на
   любом кандидате — по построению, а не по делу), и ПЯТЫМ —
   **закон паритета** (`catalog/tools/parity.py --catalog <попытка>/catalog
   --bindings <попытка>/bindings.json --json <попытка>/parity.json`):
   он судит тот же временный каталог его же привязками. Вердикт целиком
   ложится в свидетельство блоком `gates.parity` — конвейер его не
   пересказывает. Красный вердикт — `needs_human` со словами ПРАВИЛА
   (см. 13.13). После гейтов эфемерный решатель гасится, и только затем
   идёт полный `pytest -q` клона (с 09.09.2026): набор идёт минутами и
   законно упражняет гигиену процессов (подметание при старте зовёт
   сборщика сирот своего контура), а живой судья под ним не живёт —
   сквозная проверка потеряла решатель посреди набора, и стенд
   временного каталога судил мёртвый адрес;
7. сторож дерева клона ВТОРОЙ раз — перед свидетельством: за время
   стенда, `pytest` и гейтов в дереве вправе измениться только три
   известных файла свидетельства (их перевыпускает цепочка), всё
   прочее названо словами. Затем конвейер дописывает в кандидата блок
   доказательств и делает второй коммит — «свидетельство гейтов»;
   после записи кандидат ПЕРЕЧИТЫВАЕТСЯ тем же читателем, что и служба
   (`candidate_reload`): лишний ключ в доказательствах отверг бы
   «Перевести в записи» уже у владельца. У CR с видами решателя
   доказательства несут блок `solver`: команды и коды сборки, числа
   тестов решателя, SHA-256 артефактов, адрес, пределы и остановку
   эфемерного решателя, строки живого стенда по видам. Статус
   `implemented` — только при всех зелёных; иначе `needs_human` с
   отчётом словами.

Ветка `cr-<ключ>` остаётся человеку: два коммита, отчёт гейтов,
кандидат. Перенос на Stage и Prod — вручную, как у всех запросов на
изменение.

**Файл-кандидат** `catalog/candidates/<раздел>/<id>.json` — это черновик
записи целиком (спецификация + статус «есть» + стендовые задачи) плюс
номер заявки, ключ CR и блок доказательств (гейты, ветка, коммиты).
Кандидат лежит вне отпечатка и вне проверки каталога; читает его только
служба при «Перевести в записи», путь она строит сама — файл снаружи
папки кандидатов не принимается. Сборка удаляет кандидата и называет его
в ответе: удаление обязано войти в коммит сборки, иначе выпуск откажет
на грязном дереве.

### Исполнители решателя (виды `kotlin_*`) — тот же агент, тот же CR

**Исполнителей решателя пишет тот же агент тем же запросом на
изменение** (слово владельца 08.09.2026: в контуре автоулучшения всё
пишет сам COSMOS; прежняя дорожка «6-К», где виды решателя откладывались
человеку, отменена). Отложенных видов больше нет: `kotlin_*` идут в
перечень к реализации наравне с прочими, строка CR рождается принятой, а
суточная квота тратится на настоящую работу.

Судьи взамен человека: сборка решателя из коммита ветки, тесты решателя
после упаковки, эфемерный решатель из собранного артефакта и живой стенд
на временном каталоге (шаги 4–6 порядка исполнения выше).

**Что открыто агенту.** Точным совпадением пути — семь файлов решателя:
провайдер ограничений `FlightCrewSchedulingConstraintProvider.kt`
(`kotlin_constraint`), пороги `RunThresholds.kt` (`kotlin_knob`), формы
логики `LogicForms.kt`, `LogicCompiler.kt`, `LogicModel.kt`
(`kotlin_logic_form`), разбор пакета `TaskPackage.kt` (`kotlin_form`) и
режимы задач `TaskModes.kt` — последний ТОЛЬКО блоком `METRIC_EXECUTORS`
(`kotlin_metric`): судья сверяет текст ВНЕ блока с `main` побайтно, и
приписанный комментарий или удалённая строка вне блока — такое же
красное, как дописанный код, с именем файла и номерами строк. По началу
пути — три папки, и в них дозволены ТОЛЬКО
НОВЫЕ файлы: папка исполнителей решателя (помощники под судьёй токенов),
`src/test/kotlin/` (новые файлы `*Test.kt`) и `src/test/resources/`.

**Что закрыто.** Инструмент измерения (ручки HTTP `rest/`,
`PackagedRuns.kt`, `RulesConfig.kt`, `ResourceRules.kt`,
`CoverageReport.kt`, `RosterLayoverCost.kt`, `HistoryAssumption.kt`) —
им судят измеряемое; машинерия поиска и чужие профили (`ChainMoves.kt`,
`LargeMoves.kt`, `ChainSearchRules.kt`, `DeadheadSeats.kt`,
`WorkingSeatsFilter.kt`, `Gerad*.kt`, папки `domain/` и `spp/`);
конфигурация запуска и сборки (`src/main/resources/`, `pom.xml`,
`mvnw*`, `.mvn/`, `run.bat`, `target/`); читатель таблиц
`vmp/kotlin_tables.py`; прихожие пакетов `vmp/__init__.py` и
`vmp/run/__init__.py`; судьи в зоне COSMOS — стенд решателя
`vmp/stand_solver.py` и сборка `vmp/solver_build.py`. Отдельный судья
токенов не пускает в добавленные строки решателя `@Path(`, `@GET`,
`@POST`, `System.getenv(`, `System.getProperty(`, `ProcessBuilder`,
`File(`, `Files.`, `Path.of(`, `Paths.get(`, `FileInputStream(`, `URL(`,
`URI(`, `HttpClient`, `Socket(`, `Class.forName`: исполнитель читает мир
только из пакета постановки. **Тот же судья токенов судит и НОВЫЕ ФАЙЛЫ
ТЕСТОВ решателя**: чтение среды, диска и сети запрещено и в тексте
теста — их исполняет сборка ДО остальных судей и под учётной записью
службы. Ресурсами тестов нельзя погасить прогон —
`application*.properties`, `junit-platform.properties` и что-либо под
`META-INF/` не заводятся и новыми файлами.

**Тесты решателя обязательны, и их гигиену судит машина**: хотя бы один
НОВЫЙ файл `*Test.kt` с литералом предмета посева; правка или удаление
существующего файла тестов — красное (это путь самосертификации);
`@Disabled`, `@Ignore`, `assumeTrue`, `@EnabledIf*`, `@DisabledIf*` в
новом файле — красное (выключенный и пропущенный тест судья считает
одинаково); файловых операций в тексте теста нет; число `@Test` на
ветке больше, чем на `main`, а surefire исполнил ровно столько тестов,
сколько их в исходниках, при нуле падений и ошибок, и пропущенных не
стало больше, чем на `main`.

**Свидетельство** (`gates.solver` отчёта гейтов и файла-кандидата):
`class` — класс правки; `build` — команды, коды, длительности, тулчейн и
версии, счёт surefire, SHA-256 четырёх артефактов и их совпадение до и
после тестов; `test_hygiene` — числа тестов на `main` и на ветке, новые
файлы, литералы; `tables_growth` — девять таблиц решателя поимённо;
`run` — адрес, порт, флаги JVM, баннер, пределы, время старта,
остановка и свобода порта после неё; `stand` — числа по видам, по
предмету, пары близнецов, мера регрессии против `main` и до двадцати
строк живого суда. Рядом с ним `gates.parity` — вердикт закона паритета
целиком (13.13). В карточке строки — выжимка `impl.solver`: класс, код
сборки, числа тестов, начало отпечатка архива приложения, адрес
решателя, числа стенда по видам.

**Два класса правок.** **К-исп** — таблицы решателя не выросли (новое
ограничение, форма логики, потребитель известной ручки). **К-табл** —
таблицы выросли (новый параметр, метрика, семья истории, мягкая семья).
Класс — механическое имя того, что случилось, и путь до `implemented`
открыт ОБОИМ: К-табл доходит до `implemented` при зелёном паритете
временного каталога, потому что рост, ОБЪЯВЛЕННЫЙ записью кандидата,
законен (13.13). На живом каталоге паритет станет зелёным после того,
как служба соберёт запись и пройдёт цепочка после сборки, — но CR к
этому мигу уже закрыт честно, а не отложен. Красный вердикт закона —
`needs_human` со словами правила: значит рост записью не объявлен либо
объявлен не так (единица, отношение, зона, текст отказа). Человек в код
не входит и здесь: он решает в каталоге и выпускает версию.

Если на контуре нет Java, обёртки Maven или кэша зависимостей, кнопка
отказывает словами до ветки — квота цела (проба тулчейна, п. 1 порядка
исполнения).

### Ручки и коды

Служба (машинный канал требует заголовков `X-Catalog-Product` со
значением `CDPM` или `COSMOS` и `X-Catalog-Token`):

| Ручка | Что делает |
|---|---|
| `POST /api/requests` | подача заявки: машинно от продукта либо с экрана |
| `POST /api/requests/dry-run` | предпросмотр отказа и номера до подачи; ничего не пишет |
| `GET /api/requests` | перечень с фильтрами; у каждой строки — ожидаемый ключ CR и адрес кандидата |
| `PUT /api/requests/{id}/cr_key` | «исполнитель заявлен»: ключ обязан быть по закону |
| `POST /api/requests/{id}/decide` | решение владельца словами; отсюда же отклонение принятой и пересмотр отклонённой |
| `POST /api/requests/{id}/adopt` | «Перевести в записи»; с кандидатом — вместе со стендовыми задачами и доказательствами |
| `PUT /api/drafts/dictionaries/{key}` | создание ключа `document_classes` черновиком (прочие неизвестные ключи — отказ) |
| `POST /api/versions/release` | выпуск с тремя добавленными предпроверками (ниже) |
| `python -m catalog_service import-requests --inbox <папка> [--reply]` | приём очередей продуктов с площадок на рабочем месте владельца |

| Ручка | Что делает |

| `POST /api/cr/catalog/sync` | сверка заявок каталога с очередью изменений |
| `POST /api/cr/catalog/deliver` | повторная доставка файлов очереди в службу |
| `POST /api/task-package/current/press/catalog-requests` | подача заявок на вид исполнителя по артефакту последнего нажатия |

| 11 | заявок в состоянии «исполнитель заявлен» — предупреждение словами «заявок в работе: N» | предупреждение, выпуску не мешает |

### Площадки: почтового ящика у службы нет

Обещание шага 5 держится буквально: на площадках и у заказчика служба
работает только в режиме просмотра и не пишет на диск ни байта.
Заявки, рождённые там, копятся в ОЧЕРЕДЯХ ПРОДУКТОВ под каталогом
данных: `<каталог данных>/cosmos-catalog-requests/outbox` у COSMOS и
своя папка у CDPM. Перенос на рабочее место владельца — копией папок по
чек-листу раската, приём — командой `import-requests --inbox <папка>
--reply`: на каждый файл кладётся ответ с номером, признаком приёма,
перечнем замечаний и словами. Повторный прогон файлы с ответом
пропускает. Машинный канал у заказчика выключен по построению — токена
там нет.

Как устроена очередь. Заявка — файл `<номер заявки>.json`; ОТВЕТ службы
ложится рядом файлом `<номер заявки>.reply.json`, и он же служит
маркером «доставлено»: строка «ожидает доставки» на экране считает
только файлы БЕЗ ответа. Кнопка «Доставить очередь» повторяет подачу
именно этих файлов — содержание заявки при повторе не меняется (номер
содержательный), меняется только то, что о ней знает служба.

Свидетельство нажатия. Заявки, поданные при остановке расчёта, названы
в папке нажатия файлом `catalog-requests.json`: форма прогона, а в ней
строка на каждое правило — раздел, запись, виды, номер заявки, её
состояние, признак доставки и слова службы. Файл виден в выгрузках
прогона COSMOS под именем «заявки-каталога-пейринга»; повторные подачи
того же нажатия строки ДОПИСЫВАЮТ, а не стирают.

Подписанного свидетельства у кандидата нет — блок доказательств есть

попытки, а живой становится зелёным после сборки записи службой и
цепочки после сборки (13.9, 13.13). Почтового ящика заявок у службы
нет. Пересмотр прежних посадок категории C после выпуска новой версии
каталога — отдельная работа.

## 13.11. Шаг 7-А: инструмент извлечения без снимка словарей CDPM (08.09.2026)

**Зачем.** Шаг 7 снимает у CDPM носители кода: словари и семьи она
берёт только из каталога. Первым идёт шаг 7-А — часть COSMOS, и он
касается инструмента извлечения. До части 7-А `catalog/tools/build_from_code.py`
читал три вещи из чужой зоны: снимок словарей CDPM
`final-report/KATALOG-CDPM-SLOVARI-CLD.json`, порядок слов-носителей из
модуля лексикона CDPM и перечень зон из её модели. Пока носители кода
живы, это работало; как только они снимаются, инструмент покраснел бы —
и покраснел бы ПОСЛЕ того, как поправить его было бы нечем. **Часть 7-А
сдана 08.09.2026**: ниже описано то, что уже сделано в дереве.

**Что делает 7-А.** Курируемые словари CDPM переезжают в посевной файл
`catalog/tools/catalog_seed.json` — в зону COSMOS — отдельным разделом
`cdpm_dictionaries`: имена параметров с единицами, слова-носители,
дополнения, порядок лексикона и перечни (единицы параметров и кодов,
отношения, пояса, уточнители области, категории посадки). Вычисляемые
ключи посеву не нужны: их считает читатель.

Содержимое переносится МАШИННО из последнего снимка, а не переписывается
руками: CDPM выполняет свой инструмент выгрузки словарей на базовом
коммите и передаёт файл вместе с извещением; при равенстве множеств
порядок остаётся прежним. После переезда инструмент читает посев и
перестаёт импортировать модули CDPM — ни лексикон, ни модель. Таблицы
шаблонов проверок остаются его входом: это таблицы исполнителей, а не
словари CDPM.

**Гейт паритета после 7-А** (полный перечень правок, иначе он краснеет в
команде стадии): порядок лексикона берётся из посева и каталога вместо
модуля CDPM (правило про слова и пары — L06); правило «снимок равен
коду» снимается (сравнивать нечего — код CDPM словарей больше не
несёт); правило про мягкие семьи сверяется с таблицами решателя без
перечня из кода CDPM; правила про зоны, категории посадки и старую
ревизию реестра не меняются — импорт модели CDPM у гейта остаётся
свидетелем «одна мерка». **Правая сторона правил про имена параметров,
слова-носители и словари (L05, L06, L07) до окна 7-Б — по-прежнему
СНИМОК словарей CDPM** `final-report/KATALOG-CDPM-SLOVARI-CLD.json`
(переходный свидетель, зелёный): на посев переведён только порядок
лексикона. Перевод правой стороны L05–L07 на посев — окно 7-Б, по
договорённости сессий.

**Честная оговорка.** После окна 7-Б правая сторона этих правил станет
входом того же инструмента, который пишет каталог, и они будут
проверять детерминизм и самосогласованность, а не паритет: независимого
свидетеля словарей CDPM в гейте паритета не останется, и это говорится
заранее. Сторожами остаются: пересечение имён с таблицами решателя
(правая сторона независима), поведенческие тесты CDPM по конкретным
именам и единицам, проверка «перечни схемы модели ⊆ словарей каталога»,
а также версия и отпечаток каталога в паспорте прогона и в манифесте
пакета. С пакетом «паритет на временном каталоге» (08.09.2026) оговорка
уточнена: посев — это ЖЁСТКИЕ БЛОКИ владельца ⊕ машинная проекция
каталога (`--refresh`), и правая сторона L05–L07 — жёсткий блок
`cdpm_dictionaries` (факт прошлого, руками только по слову владельца)
плюс свежесть проекции, которую судит L23. Имя, которого нет ни в блоке
CDPM, ни в таблицах решателя, ни в черновике заявки владельца, законным
не становится ни от истории записи, ни от того, что его написал тот же
агент.

**Следствие для процесса.** С шага 7 новое имя параметра или новая
единица CDPM — это правка посева в зоне COSMOS и новый черновик
каталога; со службой каталога (13.9) тот же словарь правится с экрана
«Словари». Формы заявки на строку словаря нет: заявки принимают записи
семей и критериев, не ключи словарей.

**Порядок коммитов** (одно окно, без красного промежутка): сначала
COSMOS сдаёт 7-А — посев с разделом словарей CDPM, инструмент без
снимка и без импортов CDPM, гейт по перечню выше; от переезда словарей
каталог остаётся байт в байт прежним, потому что данные те же.
СДЕЛАНО 08.09.2026 вместе с переносом пятнадцати стендовых задач формы
«tables» (договорённость С2) — вот от него отпечаток каталога и
сменился: раздел `families` вырос на задачи, прочие файлы каталога
байт в байт прежние. Затем CDPM сняла носители кода (её стадия 1б,
СДЕЛАНО 08.09.2026): словари и лексикон семей — из каталога, гейт
против воскрешения носителей, `cdpm/bindings.json` и
`cdpm/stand_results.json` перевыпущены по новому отпечатку каталога.
Свой инструмент выгрузки словарей и снимок она оставила ПЕРЕХОДНО
(инструмент читает только каталог, снимок перевыпущен байт в байт по
данным).

**Окно 7-Б СДАНО 08.09.2026** — см. 13.12.

## 13.12. Шаг 7-Б: обёртка — тонкая проекция, режим среза снят (08.09.2026)

**Зачем.** Шаг 7 доводит переезд до конца: у одной вещи одна мерка и
один источник. К части 7-Б в дереве оставались три остатка прежнего
устройства — режим СРЕЗА базы шаблонов (второй, необъявленный источник
рядом с каталогом), правая сторона трёх правил гейта паритета,
читавшая снимок словарей CDPM из её зоны, и тест этого снимка. Окно 7-Б
снимает их одним коммитом двух сессий, чтобы красного промежутка не
было.

**Что снято и чем заменено.**

## 13.13. Паритет как закон: временный каталог, посев-проекция, выпуск переносит рост (08.09.2026)

**Зачем.** До этого пакета паритет каталога с кодом жил внутри одного
теста и был пришпилен к живому каталогу числами: «семей 16», «имён 46»,
«несвязанных 17». Пока каталог не рос, это работало. Как только контур
автоулучшения научился писать исполнителей решателя (13.10), всякая
правка, от которой таблицы решателя РАСТУТ (новая ручка, метрика, семья
истории, мягкая семья), делала тест красным по построению — и строка
уходила в «нужен человек» не потому, что что-то не сошлось, а потому,
что закон был записан числом.

**Слово владельца (закон пакета):** в контуре автоулучшения всё пишет
сам COSMOS; `needs_human` допустим только как честный исход красного
гейта, а не как маршрут по построению. Пакет выполняет три требования:
(1) паритет судит ВРЕМЕННЫЙ каталог «живой ⊕ кандидат» — рост,
объявленный записью, законен; (2) в законе не остаётся чисел-литералов
живого каталога — каждое правило есть равенство двух источников;
(3) после выпуска каталога паритет живого каталога зелен без единой
правки числа человеком.

### Закон — модуль и команда

Закон живёт в одном месте — `catalog/tools/parity.py` (зона `catalog/`,
запретный путь агента: закон защищён от того, кого он судит).

    .venv\Scripts\python.exe catalog\tools\parity.py [--catalog <папка>]
        [--bindings <файл>] [--with-candidates] [--candidate <файл>]
        [--json <файл>] [--quiet]

| Ключ | Умолчание | Смысл |
|---|---|---|
| `--catalog` | `catalog/` дерева | судимая папка: живой каталог, временный каталог попытки CR, папка выпуска `releases/<версия>/` |
| `--bindings` | `vmp/bindings.json` | файл привязок судимой папки; файла нет — правила L19/L22 отвечают «пропущено» словами |
| `--with-candidates` | выключено | судить «живой ⊕ все кандидаты `catalog/candidates/**`»: движок материализует временный каталог сам и строит привязки В ПАМЯТИ, а `--bindings` при этом НЕ читается (что судило строки, сказано в `catalog.bindings` вердикта). Отказ генератора привязок на таком каталоге — свойство кандидата: L19/L22 краснеют его словами |
| `--candidate` (значение — файл) | нет | файл кандидата, УЖЕ положенного в судимую папку зовущим (так делает пятый гейт CR): движок ничего не материализует, а берёт адрес записи и номер заявки — этим правило L21 «запись ≡ заявке» получает предмет суда |
| `--json` | нет | записать вердикт файлом — это и есть блок `gates.parity` свидетельства CR |
| `--quiet` | выключено | без построчного отчёта (для службы); `--json` пишется всегда |

Коды возврата: `0` — красных правил нет (пропущенные не красят), `1` —
есть красное правило, `2` — судить не удалось (папка, таблицы решателя
или посев не читаются, аргументы негодны). Вердикт — объект с полями
`ok`, `rc`, `catalog` (версия, отпечаток, путь), `growth_judged` (какое
поле таблиц решателя каким правилом судится), `counts`, `rules` (по
правилу: `ok`, `words`, `numbers`, `skipped`, `warning`) и `words` —
склейкой слов всех красных правил. Числа правил ПЕЧАТАЮТСЯ, а не
утверждаются: утверждаются равенства множеств с именами.

Двери продуктов (`vmp/catalog_access`, `cdpm/catalog_bridge`) читают
переменную `CREW_TEMPLATE_CATALOG`. Движок её не ставит и не снимает —
это свидетель правила L10; отдаёт её подпроцессу зовущая сторона
(конвейер CR, служба). Читают двери другую папку — L10 отвечает
«пропущено» СЛОВАМИ, а не тихим «зелено».

Свидетель закона — `tests/test_template_catalog_parity.py`: он зовёт
движок, печатает числа и краснеет на нарочно испорченных копиях. Числа
он не хранит.

`--refresh` разделов отпечатка не касается, под `releases/` и на папке
без `tools/` отказывает словами; ключа принуждения у `refuse_write`
по-прежнему нет. Дельта перехода не курируется, а ВЫЧИСЛЯЕТСЯ (`base`,
`params_to_families`, `params_relation_set`, `executor_kinds_added`,
`criteria_added`, `families_added`, `history_added`, словари, гейты,
`fingerprint`); ключи прежние — их читают обёртка, сторож дрейфа и
правила шага 4.

**Свидетель имени параметра вне Kotlin** — только жёсткий блок
`cdpm_dictionaries.params` либо черновик ЗАЯВКИ каталога (заявка принята
владельцем, `draft.params[]` называет имя, единицу и отношение). Строка
истории записи свидетелем НЕ является: историю и запись кандидата пишет
один и тот же агент, а заявка — решение владельца.

### Временный каталог в конвейере CR (пятый гейт)

Гейты CR идут на временном каталоге «живой каталог клона ⊕ запись
кандидата»: стенд → генератор привязок → гейт привязок → проверка
кандидата → **паритет**. Пятая команда судит тот же временный каталог
его же привязками, а вердикт целиком ложится в свидетельство блоком
`gates.parity` — конвейер его не пересказывает. Для `implemented`
требуется `gates.parity.ok == true`; класс правки К-табл больше не
закрывает путь (13.10, «Два класса правок»).

Три следствия, которые стоит знать заранее:

* `pytest -q` клона зелен ПО СУЩЕСТВУ: свидетель паритета в дереве судит
  «живой ⊕ кандидаты `catalog/candidates/**`», ключей `--ignore` и
  перечней «ожидаемо красных» у конвейера нет. Держится это тремя
  вещами, и каждая — стенд: вердикт ЖИВОГО каталога рядом печатается, но
  не утверждается (на ветке роста он красен по делу); числа гейта
  сверяются с НЕИЗМЕНЯЕМОЙ папкой выпуска, а не с живым каталогом;
  свежесть носителей (L23 и `--refresh --check`) считается сравнением
  ПРОЕКЦИЙ без сборки каталога — рост таблиц решателя на неё не влияет.
  Воспроизводимость судимой папки (`--check --from-catalog`, L18) на
  дереве с кандидатами судится по папке «живой ⊕ кандидаты». Сквозная
  проверка 08.09.2026 добавила к этому ещё три вещи, без которых
  «зелен по существу» держалось не до конца: копия каталога в стендах
  берёт строки привязок записи-кандидата ИЗ ПОСЕВА дерева тем же
  построителем, что у генератора (пробная строка «нет» вышла бы у
  метрики решателя без поля `metric`); стенд, который МАТЕРИАЛИЗУЕТ
  временный каталог, кладёт кандидатов дерева первыми (иначе посев
  дерева называет запись, которой в его папке нет); а там, где судья
  по построению смотрит на замороженный посев инструмента
  (`catalog/tools/catalog_seed.json`) или на ЖИВОЙ каталог без
  кандидатов — предпроверка выпуска у службы, — стенд пропускается
  СЛОВАМИ «рост таблиц под кандидатом — судит закон паритета на
  временном каталоге», и только при двойном условии: кандидат рядом
  есть И судья отказал;
* строки посева привязок, опережающие живой каталог (ручка параметра,
  которого в живом каталоге ещё нет), законны ПО КАНДИДАТУ: генератор
  пропускает такую строку словами «ожидают записи кандидата: …», а
  после сборки службой она входит в файл сама;
* самопроверка агента — та же команда, что у гейта:
  `python catalog/tools/parity.py --with-candidates`;
* судьи закона агентом не правятся: под `tests/` (включая `tests/vmp/`)
  ему дозволены только НОВЫЕ файлы, а перечни `vmp/run/roster_certify.py`
  (`PEOPLE_FAMILIES`, `WORLD_PARAM_FAMILIES`, `EXTENSION_CONDITIONS`,
  `SOFT_MEASURE_TEMPLATE`, `WORLD_PARAM_TEMPLATE`), по которым закон
  судит природу записи, её условия и сертификатные шаблоны, снимаются ДО
  и ПОСЛЕ работы агента — расхождение даёт `needs_human` словами «правка
  свидетеля паритета». Сам файл закрыть нельзя: он исполнитель строк
  «есть» посева.

### Выпуск переносит рост

Двенадцатая предпроверка выпуска — паритет с кодом COSMOS (13.9): служба
зовёт закон подпроцессом по своей папке каталога. Красный вердикт —
отказ `parity-red`; «не судился» и предупреждение (L08b) — отказ
`parity-unconfirmed`, снимаемый осознанным подтверждением владельца
`confirm_parity`, а не молчание. После выпуска цепочка
(`--refresh` → коммит выпуска → стенд и привязки → `parity.py`) делает
паритет ЖИВОГО каталога зелёным без правки чисел человеком — это и есть
требование (3) пакета.

### Чего пакет НЕ делает

ветки CR в `main` по-прежнему делает человек (13.10).

## 13.14. Каталог РАСТЁТ: режим роста в наборе тестов и предполётная проверка задания (10.09.2026)

### Зачем это заведено

09.09.2026 через конвейер пополнения прошла первая новая семья каталога
(`duty_series_limit`). До записи она дошла с ПЯТОЙ попытки агента, и
четыре сорванные попытки сорвались не о шаблон и не о правило
авиакомпании, а о СКРЫТЫЕ ДОПУЩЕНИЯ судей и тестов: они были написаны на
каталог, который не растёт. Жёсткое число записей в ожидании теста;
рукописный перечень судей стенда; рукописные перечни «семей истории»;
правило «запись с таким id уже есть» у читателя; копия каталога без
заявки-свидетеля; посев привязок, который о новой записи не знает.
Каждая такая попытка стоит одной реализации дня и получаса машинного
времени, а находится всё это ДО агента и дёшево.

Отсюда два механизма. Первый — **режим роста каталога**: весь набор
тестов умеет прогоняться на каталоге, который ВЫРОС. Второй —
**предполётная проверка задания агенту**: по строке заявки на изменение
строится заготовка записи, и по ней прогоняются те же судьи ещё до
запуска агента.

Носитель у обоих один — модуль `template_catalog/growth.py`: там живут
синтетическая запись, заготовка кандидата и слова ожидаемых пробелов.
Второго носителя не заводится: помощник копий тестов
(`tests/catalog_copies.py`) и предполётная проверка берут запись оттуда.

### Режим роста каталога в наборе тестов

Включается переменной среды `COSMOS_TEST_CATALOG_GROWN`. Без неё
поведение прежнее — обычный гейт продукта не меняется ни на байт.

| Значение | Что подмешивается в КАЖДУЮ копию каталога |
|---|---|
| `extension` (или `1`) | Синтетическая семья-РАСШИРЕНИЕ `zz_probe_growth` и синтетический критерий `zz_probe_growth_rate`: вид исполнителя объявлен, самого исполнителя нет — так выглядит кандидат ДО работы агента |
| `clone` | Та же пара, но семья — КЛОН существующей записи: те же виды исполнителей и те же строки привязок (символы образца), покрытие настоящее |
| путь к файлу заготовки | Запись НАСТОЯЩЕЙ заявки: набор прогоняется на той записи, которую предстоит реализовать (этим пользуется предполётная проверка) |

Опечатка в значении — отказ словами, а не тихое умолчание: молчание
превратило бы описку в «режим выключен», и прогон «в режиме роста»
ничего бы не проверял.

Что несёт копия каталога в режиме роста, кроме самих записей:

* строки привязок синтетических записей (у расширения — «нет», у клона —
  «есть» с символами образца);
* **посев привязок копии** `vmp-bindings-seed.json` рядом с разделами.
  Посев — третий носитель знания об исполнителях, и до 10.09.2026 двери
  у него не было: каталог подменялся переменной `CREW_TEMPLATE_CATALOG`,
  привязки — `CREW_COSMOS_BINDINGS`, а посев брался ИЗ ДЕРЕВА. Судья,
  который пересобирает привязки сам, отказывал «запись каталога в посеве
  не названа» на любой записи, которой в дереве ещё нет. Теперь у посева
  есть своя дверь `CREW_BINDINGS_SEED`, а закон паритета читает посев,
  лежащий рядом с судимой папкой каталога;
* освежённые носители инструмента, если тест кладёт рядом папку
  `tools/` (помощник `catalog_copies.copy_tools`): посев инструмента и
  дельта приколочены к отпечатку каталога, и выросшая копия обязана
  нести их пересчитанными.

Копия, которая обязана РАВНЯТЬСЯ выпуску или посеву инструмента
(`copy_catalog(..., candidates=False)`), синтетических записей не несёт:
её отпечаток — предмет суда.

### Почему синтетическая семья именно такая

Открытых вариантов было два, и код ответил на вопрос сам.

**Клон с ТЕМИ ЖЕ именами параметров невозможен.** Правило X02 читателя
запрещает одно имя параметра в двух записях, а карта `Catalog.params()`
плоская — «имя → семья»: при повторе имя молча досталось бы последней
записи. «Одно имя — одна семья» здесь не допущение судей, а ЗАКОН
каталога, и клон честен только с переименованными параметрами.

**Параметров у синтетической записи нет вовсе.** Своё имя параметра
потребовало бы заявки-СВИДЕТЕЛЯ в очереди КАЖДОЙ копии: единицу имени,
которого не знают ни словарь CDPM, ни таблицы решателя, подтверждает
только черновик принятой заявки. Такая заявка меняла бы очередь всех
стендов службы каталога, и помощник роста стал бы вторым предметом суда
вместо пробы. Семьи без параметров в каталоге законны — их две среди
живых записей.

**Природа клона — «расписание».** Природа выводится ИЗ КОДА в обе
стороны (правило L15): семьями истории код зовёт те, чью форму знают
таблицы решателя. Синтетической записи код не знает ни с одной стороны,
и любая другая природа была бы у неё ложью.

Оба режима честны и проверяют разное, поэтому оставлены оба: расширение
отвечает на вопрос «что скажут судьи, когда исполнителя ещё нет», клон —
«останутся ли судьи зелёными, когда покрытие есть».

### Заявленные пробелы: чем красное отличается от поломки

Договор режима: **судья либо остаётся зелёным, либо называет пробел
СЛОВАМИ с именем записи**. У синтетической записи по замыслу нет
исполнителя и нет стендовых задач — их пишет агент, и сказать это работа
судьи, а не его беда. Помощник копий даёт две функции:
`catalog_copies.probe_only(слова)` — красное объясняется только
синтетическими записями? — и `catalog_copies.verdict_ok(вердикт)` для
закона паритета. Без режима роста обе всегда отвечают «нет»: красное
остаётся красным.

Судья, который сломался или пожаловался, НЕ НАЗВАВ записи, споткнулся о
сам рост каталога — это допущение, и оно чинится в коде судьи, а не в
тесте.

### Предполётная проверка задания агенту

Шаг 0-П конвейера CR каталога: выполняется при нажатии «Реализовать на
Тест» ДО создания ветки, ДО списания квоты дня и ДО запуска агента.
Отдельной точки в интерфейсе не заведено — проверка живёт внутри
реализации; вызвать её без реализации можно функцией
`webapp.change_requests.preflight_catalog_cr(строка_CR)`.

**Что судится.** По строке CR строится ЗАГОТОВКА записи — файл-кандидат
той же формы, какой напишет агент, но без исполнителей: черновик заявки
⊕ состояние «есть» ⊕ пустой перечень стендовых задач. На временном
каталоге «живой каталог клона ⊕ заготовка» идут дешёвые судьи:

| Судья | Что смотрит |
|---|---|
| `catalog` | читатель и его правила: ошибки `validate()` целиком, предупреждения — о самой заготовке |
| `reader` | запись видна дереву: `candidates.record_in_tree` отдаёт её каталогом либо кандидатом |
| `bindings` | генератор привязок собирается по посеву ⊕ строки «нет» заготовки; гейт привязок судит собранный документ |
| `kinds` | каждый объявленный вид исполнителя НАЗВАН строкой привязок (пусть «нет») |
| `prune_pending` | отметка ожидания в посеве снимается сама, как только каталог назвал запись (`--prune-pending` на КОПИИ посева, дерево не правится) |
| `stand` | перечень судей стенда читается и выводится из кода исполнителей, а не из рукописного списка |
| `tests` | набор тестов копий каталога в режиме роста С ЭТОЙ заготовкой |

Перечень судей открыт намеренно (`change_requests.PREFLIGHT_JUDGES`):
судьи ДОБАВЛЯЮТСЯ — это принцип контура самоулучшения.

**Как читаются находки.** У находки три вида:

* `gap` — судья НАЗВАЛ запись по имени и говорит о том, чего у заготовки
  нет по замыслу («исполнителя нет», «стендовых задач нет»). Сказать это
  работа судьи, закрыть — работа агента.
* `draft` — ОШИБКА читателя о самой записи: заготовка негодна, и
  посылать по ней агента незачем (чинится заявка).
* `assumption` — судья сломался либо пожаловался, записи не назвав:
  он споткнулся о сам рост каталога (чинится код судьи).

**Вердикты.**

| Вердикт | Когда | Что происходит |
|---|---|---|
| `ok` | судьи возражений не нашли | реализация идёт как обычно |
| `expected-gaps` | судьи назвали только пробелы заготовки | реализация идёт, а перечень пробелов вкладывается в задание агенту разделом «ЧТО ОБЯЗАНО ЗАКРЫТЬСЯ» |
| `judge-assumption` | судья сломался либо пожаловался, не назвав записи (`assumption`), ЛИБО заготовка негодна по читателю (`draft`) | строка уходит «нужен человек» ДО агента, с перечнем находок; квота дня не тратится, облачная модель не зовётся. Слова вердикта различают два случая: первый чинится в коде судьи, второй — в заявке |

**Где это видно.** В строке CR появляется поле `preflight`:
`{at, verdict, findings: [{judge, kind, words}], gaps, judges, record,
candidate, words}`. Поле `words` — та же фраза, что показывает карточка.
В задании агенту ожидаемые пробелы идут отдельным разделом перед итогами
прошлой попытки: их назвали судьи ДО его работы, и вернуться зелёными те
же судьи обязаны после неё.

**Как это выглядит в карточке.** На вкладке «Изменения» карточка строки
несёт блок **«Предполётная проверка»** — между сведениями о записи и
итогом работы агента, потому что и сама проверка идёт до него. В шапке
блока стоит чип вердикта и момент проверки: `ok` — зелёное «судьи
молчат»; `expected-gaps` — жёлтое «ожидаемые пробелы: N» (число — это
находки судей, а не строки заготовки; реализация идёт своим ходом);
`judge-assumption` — красное «допущение судей — нужен человек» (строка
уже ушла в этот статус ДО агента). Ниже — таблица находок «Судья · Вид ·
Слова», где вид тоже покрашен: ожидаемый пробел жёлтым, негодная
заготовка и допущение судьи красным. Замыкает блок короткий перечень
«Что обязано закрыться» — первые пять пробелов, остаток назван числом;
целиком он едет в задание агенту. У строк прежних версий поля
`preflight` нет, и блок им не рисуется вовсе: «неизвестно» карточка не
выдумывает. Незнакомое слово вердикта или вида находки (судьи
ДОБАВЛЯЮТСЯ) показывается как есть нейтральным чипом.

### Как проверить

    set PYTHONUTF8=1
    rem обычный режим — как было
    .venv\Scripts\python.exe -m pytest -q tests\test_catalog_growth_mode.py tests\test_change_requests.py

    rem режим роста: семья-расширение без исполнителя
    set COSMOS_TEST_CATALOG_GROWN=extension
    .venv\Scripts\python.exe -m pytest -q tests\test_template_catalog_parity.py tests\catalog_service tests\vmp

    rem режим роста: клон существующей семьи с исполнителями
    set COSMOS_TEST_CATALOG_GROWN=clone
    .venv\Scripts\python.exe -m pytest -q tests\test_template_catalog_parity.py tests\catalog_service tests\vmp
    set COSMOS_TEST_CATALOG_GROWN=

Все прогоны зелёные. Красный тест в режиме роста — найденное допущение
«каталог не растёт»: чинится КОРЕНЬ в коде судьи, а не число в тесте.

Предполётная проверка на строке CR (без реализации):

    .venv\Scripts\python.exe -m pytest -q tests\test_change_requests.py -k предполётная

### Чего эти механизмы НЕ делают

Режим роста не заменяет живой прогон конвейера: синтетическая запись не
несёт ни параметров, ни стендовых задач, и путь «единица имени —
свидетель — закон паритета» судится на настоящих кандидатах (13.13).
Предполётная проверка не судит СМЫСЛ записи и не пишет ни строки в
дерево: она называет пробелы и допущения словами, а решение принимает
человек либо агент.
