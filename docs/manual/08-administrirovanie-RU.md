## 1. О чём эта часть

Всё, что относится к управлению системой: пользователи и доступ, «Установки» супер-администратора, журнал активности, инфраструктура ИИ, а также эксплуатация: топология контуров, процедура деплоя, манифесты и восстановление.

## 3. Пользователи и доступ («Админ» → «Пользователи»)

Таблица: «Email / Роль / Статус / Создан / Последний вход / Входов / Задач / Загрузок». Форма «Добавить пользователя»: «Email» + «Роль» («пользователь» / «администратор»). Пояснение интерфейса: «Пользователь получит доступ после входа по коду на указанный email (Cloudflare Access).»

Механика доступа (подробно — [Часть 1](01-vvedenie-i-ustrojstvo-RU.md), раздел 3):
- доменный allow-list: домены организации-эксплуатанта и, при необходимости, отдельные адреса (например, `example-corp.ru`, `admin@example.com`) → роль администратора при первом входе (авто-провижининг с источником «allow-list»); конкретный список задаётся конфигурацией развёртывания;
- статус «revoked» (отозван) сильнее allow-list;
- супер-администратор — один фиксированный email, задаваемый конфигурацией; определяется по адресу.

Владение данными: каждый загруженный экземпляр принадлежит загрузившему (администратор видит колонку «Владелец» в списке экземпляров); идентификатор владельца устойчив к совпадению имён из разных доменов.

## 4. «Установки» (только супер-администратор)

Из описания экрана: «Здесь задаётся API-ключ Claude, извлекается список актуальных моделей и назначается модель на каждое использование (кодинг, обработка текстов, Ask AI и др.). Облачные модели применяются ТОЛЬКО там, где облако уже разрешено контуром данных; данные заказчика во внутреннем контуре по-прежнему обрабатывает локальная модель.»

- **API-ключ Claude** — хранится в файле вне системы контроля версий; в интерфейс никогда не возвращается в открытом виде (не «эхом»); поле служит только для записи нового значения.
- **Извлечение моделей** — запрос списка актуальных облачных моделей у поставщика; список сохраняется для выбора.
- **Назначение модели на использование** — для каждой роли ИИ в системе (кодинг агентов-исполнителей, обработка текстов, Ask AI, советник по решателям, агенты Автоулучшения) выбирается своя модель.
- Инвариант контура сохраняется всегда: назначение облачной модели **не** открывает облако там, где его запрещает контур данных, — маршрутизация по области данных первична.

Сервер перепроверяет право супер-администратора на **каждом** запросе `/api/settings*` — скрытие вкладки не единственная защита.

## 5. Журнал активности («Админ» → «Журнал»)

Из описания: «Кто входил и выходил и какие разделы открывал. Журнал хранится на сервере (последние записи), виден только администратору; фиксируются вход, выход и переключение разделов.»

Фильтры: точный email и тип события («Все события» / «Вход» / «Выход» / «Переход»), кнопка «Показать». Колонки: «Время (UTC — всемирное координированное время) / Email / Событие / Деталь». Технические свойства: переходы по разделам пишутся с троттлингом (защита от флуда) и в отдельный файл от входов/выходов — навигационный поток не вытесняет историю входов.

## 6. Инфраструктура ИИ

- **Локальная модель** — сервер Ollama на машине внутреннего контура; обрабатывает все ИИ-задачи над данными заказчика (импорт-маппинг, Ask AI по наборам типа L, агентов на Prod/Stage). Модель доверия: «локальный» бэкенд — это самостоятельно развёрнутый (self-hosted) Ollama по адресу, который задаёт оператор (переменной окружения или в «Установках» супер-администратора); адрес может указывать и на удалённый **собственный** хост — код не ограничивает его приватной сетью. Гарантия «только локально» означает «данные не уходят стороннему ИИ-провайдеру» при условии доверенной конфигурации оператора, а не сетевой периметр; изменить адрес может только супер-администратор или владелец окружения процесса.
- **Облачные модели** — только внешний контур (Test) и только публичные данные; назначение моделей — в «Установках».
- **Маршрутизация** — по «Области данных» набора (`local-only`/`any`): в «Ask AI» действует правило «затронут хотя бы один набор L → отвечает локальная модель»; вопросы и ответы Ask AI не сохраняются.
- **Реестр точек вызова** — «Админ» → «ИИ-контур»: полный перечень мест обращения к моделям (назначение, модуль, маршрутизация, модели, данные в запросе). Реестр — артефакт для аудита заказчика в строгом режиме («облако запрещено для данных заказчика») и охраняется автотестом: новая точка вызова без записи в реестре роняет тесты. Гранулярность сторожа — модульная: автотест ловит первое обращение к модели в новом модуле и устаревшие записи реестра; отдельные новые вызовы внутри уже зарегистрированного модуля он не различает — это зона внимания код-ревью.

## 7. Эксплуатация: топология и деплой

Оговорка об охвате: этот раздел — **обзор** эксплуатационной процедуры для понимания процесса. Исполняемый runbook (пошаговый регламент с точными командами, полным перечнем runtime-каталогов, целевыми показателями восстановления RPO/RTO — допустимой потерей данных и временем восстановления, расписанием и проверкой резервных копий, учебным восстановлением) — отдельный операционный документ; его подготовка в дорожной карте.

### 7.1 Топология

| Контур | Порт | Доступ снаружи |
|---|---|---|
| Prod | 8090 | основной домен приложения |
| Stage | 8091 | `cos-stage.fregene.ai` |
| Test | 8092 | `cos-test.fregene.ai` |

Все три контура — зеркальные копии репозитория на одном производственном сервере, опубликованные через туннель Cloudflare; вход защищён Cloudflare Access ([Часть 1](01-vvedenie-i-ustrojstvo-RU.md)). Машина разработки/предподготовки — отдельная (stage-копия вендора).

В каждом контуре работают три службы пакета — веб-приложение, панель CDPM и служба каталога шаблонов (`catalog_service`, [Часть 13](13-katalog-shablonov-RU.md), раздел 13.9), плюс решатель ростеринга:

| Контур | Веб-приложение | Панель CDPM | Решатель | Служба каталога |
|---|---|---|---|---|
| Prod | 8090 | 8097 | 8099 | **8107** |
| Stage | 8091 | 8096 | 8100 | **8106** |
| Test | 8092 | 8095 | 8098 | **8105** |
| Установка заказчика | 8090 | 8095 | 9096 | **8105** |

Служба каталога на площадках поднимается пусковиком `run-catalog.cmd` с ключом `--read-only`: она показывает каталог и не пишет на диск ни байта. Рабочее место владельца — единственное место, где каталог правится (`--actor owner`); там же принимаются заявки и выпускаются версии. Края доступа: `cosmos-catalog-{test,stage,prod}.fregene.ai` под существующей маской Cloudflare Access `cosmos-*.fregene.ai`.

### 7.2 Процедура деплоя (полный цикл)

Порядок обязателен; прод-деплой — только по свежей отмашке владельца в текущем диалоге/заявке.

1. **Подготовка**: полный прогон тестов + гейты неизменности канонических результатов; при изменениях алгоритмов — адверсарное ревью новых код-путей ([Часть 7](07-samousovershenstvovanie-RU.md)).
2. **Доставка кода**: git-бандл с новыми коммитами копируется на сервер; из него делается fast-forward (только вперёд, без слияний) в каждом из трёх зеркал.
3. **PAUSE-файл**: на время замены создаётся файл-флаг PAUSE, останавливающий фоновые процессы оркестрации; если менялась JVM-часть — в этом же окне заменяется собранный JAR солвера (на сервере нет средств сборки — привозится готовый архив).
4. **Рестарт**: процессы-слушатели портов 8090–8092 останавливаются, затем ensure-скрипт поднимает все три контура заново; PAUSE снимается.
5. **Верификация**: каждый контур отвечает кодом 401 без авторизации (значит, жив и защищён); в статике сервера проверяются маркеры новой версии; сверка исходников с ожидаемым коммитом.
6. **Кэш CDN**: если менялась статика (`app.js`, `i18n.js`, стили), выполняется «Purge Everything» кэша Cloudflare — иначе браузеры будут получать старые файлы.

### 7.3 Манифесты целостности

- **Манифест сборки Kotlin** — фиксирует соответствие собранного JAR исходникам (какие файлы, какие контрольные суммы, результат тестов сборки). Сборка воспроизводима через закреплённый Maven Wrapper (фиксированная версия системы сборки).
- **Манифесты активного ростера** — на каждый результат пишется манифест с отпечатками входов; с 2026-07-20 вердикт — **барьер промоции**: указатель активного ростера переключается только при вердикте `OK` ([Часть 3](03-optimizaciya-RU.md), раздел 8). При статусе «stale» — пересчитать; манифесты руками не редактируются. Важно про хранение: канонические файлы решений существуют в одном экземпляре на метку и заменяются только **удавшимся** прогоном — неудачный прогон рабочий ростер не портит; неизменяемы именно манифесты прогонов — они хранят пути и контрольные суммы SHA-256, без копий содержимого. Диагностические копии решений создаются при **любом** не-OK вердикте и складываются в `runs/stage2-diagnostics`.
- **Raw-зона** — неизменяемые исходники с манифестом SHA-256 ([Часть 2](02-podgotovka-dannyh-RU.md), раздел 5).

### 7.4 Что живёт вне контроля версий (runtime-состояние)

Часть состояния — локальные файлы сервера, не входящие в git: загруженные экземпляры и raw-зона; конфигурации (ставки, параметры оплаты/сайзинга, привязки экипажа, API-ключ); журналы (активность, дельты, задачи); манифесты прогонов; **наблюдения контуров самоусовершенствования** (снимки здоровья данных, журнал переделок доски, профиль прогонов, перепись стыковок, эпизоды ремонта, отметка последнего исследовательского скана — [Часть 9](09-spravochnik-RU.md), раздел 3.2). Резервное копирование этих каталогов — обязанность эксплуатации; git-история покрывает только код и канонические артефакты.

Про наблюдения контуров это особенно важно: они накапливаются месяцами и **невосстановимы** — при переносе стенда без их копирования вся история контуров пропадёт молча, а вместе с ней и способность контуров говорить «стало хуже».

### 7.5 Откат

- Код: модель «только вперёд» (fast-forward) не позволяет откатиться назад бандлом прежней версии. Возврат выполняется новым revert-коммитом (коммитом отмены изменений) поверх текущей истории — то есть отмена тоже идёт вперёд по истории — с обычной процедурой деплоя.
- Результаты: отката на прежний прогон нет — канонические артефакты заменены новым **удавшимся** прогоном, а манифесты хранят только пути и контрольные суммы. Возврат к прежнему решению — это пересчёт солвером. Обратная сторона барьера вердикта: неудачный прогон рабочее решение не портит, но и не даёт нового — от него остаётся только диагностическая копия, активным ростером она не становится.
- Данные: экземпляры не перезаписываются молча; дельты журналируются с отпечатками — историю применений видно в «Журнале» дельт.

## 7-бис. Точки наблюдения: жив, готов, что развёрнуто (с 2026-07-27)

Три адреса отвечают **без входа** — наблюдение за живостью, требующее авторизации, бесполезно. Поэтому наружу идут только состояния и отпечатки: ни имён файлов заказчика, ни путей, ни значений настроек.

| Адрес | На какой вопрос отвечает | Что означает отказ |
|---|---|---|
| `/healthz` | Жив ли процесс. Не трогает ни диск, ни базу | Нет ответа — процесс мёртв или порт занят чужим |
| `/readyz` | Готов ли обслуживать: схема канонического формата, база пользователей, разрешатель правил | `ready: false` — контур поднялся, но работать не может; смотрите, какая из проверок ложна |
| `/versionz` | Что именно развёрнуто: срез кода и чистота дерева, отпечаток JAR решателя и совпадение с манифестом сборки, отпечаток договора правил | `matches_manifest: false` — работает решатель, собранный не из этих исходников |

Прежде запрос к `/health` попадал на общий обработчик статики: без авторизации — переадресация, с авторизацией — сама страница с кодом 200. Наблюдатель видел «здоров» всегда, включая наглухо сломанный контур.

Те же три адреса есть у каждой службы пакета на своём порту. У службы каталога `/readyz` дополнительно называет версию и отпечаток каталога, число ошибок и предупреждений его проверки и режим («просмотр» или «рабочее место»), а `/versionz` — версии службы и читателя и срез кода. Наружу и здесь идут только состояния и отпечатки: ни абсолютных путей, ни значений настроек.

**Версия продукта внизу экрана (с 2026-10-04, РВ-141).** В правом нижнем углу каждого экрана COSMOS мелким шрифтом стоит номер версии продукта (например, «1.4.10»). Номер — одна настройка площадки: переменная `CREW_PRODUCT_VERSION` в пусковике. Одно и то же значение задаётся для COSMOS, CDPM и службы каталога; браузер получает его вместе с данными о вошедшем пользователе (`/api/me`). Переменная не задана — подписи нет: номера в коде нет. Поменять номер — значит поменять пусковик и перезапустить службу; код не правится. Подпись — для людей; срез кода по-прежнему проверяется по `/versionz`.

**Как пользоваться при раскате.** После рестарта сверьте `/versionz` на каждом из трёх контуров: поле среза кода обязано совпасть с раскатанным коммитом. Это заменяет прежнюю косвенную проверку «по времени перезапуска». Для службы каталога к этому добавляется сверка версии и первых знаков отпечатка каталога на всех площадках — они обязаны совпадать между собой и с головой раската.

## 8. Частые ошибки и что они означают

| Симптом | Причина | Действие |
|---|---|---|
| Пользователь не видит админ-вкладок | Роль «пользователь» | Поднимите роль в «Пользователях» |
| Вход не работает у пользователя из allow-list-домена | Статус «revoked» | Отзыв сильнее allow-list; верните доступ явно |
| «Установки» не видны администратору | Вкладка только для супер-администратора | Это норма |
| После деплоя интерфейс «старый» | Кэш CDN не сброшен после смены статики | Выполните «Purge Everything» в Cloudflare |
| Контур не отвечает после рестарта | Ensure-скрипт не поднял процесс либо порт занят | Проверьте слушателей портов 8090–8092 и журналы процессов; повторите рестарт |
| Фоновые агенты «замерли» | Остался PAUSE-файл | Убедитесь, что PAUSE снят после окна деплоя |
| `/versionz` показывает `matches_manifest: false` | Развёрнутый JAR решателя собран не из этих исходников | Пересоберите решатель и доставьте JAR в том же окне паузы, что и код |
| `/readyz` отвечает `ready: false` после раската | Одна из зависимостей недоступна: схема, база пользователей или разрешатель правил | Смотрите, какая проверка ложна, — адрес называет её поимённо |

## 8-бис. Правила тестов: без литералов среды

Правило одно: **тест не имеет права зависеть от того, что запущено на
машине и что лежит в живом каталоге.** Иначе он зелёный у разработчика и
красный на чистом раннере — так 09.09.2026 упал прогон CI № 73: проверка
ждала службу каталога на порту 8105, а локально на этом порту отвечала
живая служба разработчика. Тем же корнем краснели стенды каталога в
клоне агента: они брали живой номер заявки из `catalog/`.

### Что в тестах запрещено

| Запрещено | Почему |
|---|---|
| Номер порта службы пакета или контура (8090–8107, 8123, 9099 и прочие) | На чистой машине там никто не слушает, на машине разработчика — слушает чужое |
| Адрес петли с портом 1024 и выше (`127.0.0.1:8105`, `localhost:9099`) | То же самое: проверяется не продукт, а то, что запущено рядом |
| Путь машины разработчика (`C:\work…`, `C:\Users…`, `/home/…`, `/Users/…`) | На другой машине такого пути нет; тест либо падает, либо молча уходит в пропуск |
| Адрес площадки (`fregene.ai`, `cos-test`, `cos-stage`) и имя машины | Площадки меняются, тест об этом не узнает |
| Личность машины владельца: его почтовый адрес и учётное имя из него | Личность человека — такой же носитель среды, как порт и путь: в чужом клоне её нет, а в исходниках и в выводе прогонов ей не место |
| Живой номер заявки, ключ CR или отпечаток из `catalog/` | Каталог живёт: сегодня значение есть, завтра его нет или оно другое |

### Чем это заменяют

- **Порт** — свободным: слушателя поднимают на порту 0 и читают
  фактический номер у самого слушателя. Если связи нет вовсе (запрос
  подменён), берут вымышленный адрес зоны `.invalid` — она закреплена
  RFC 6761 и не разрешается никогда.
- **«Служба не отвечает»** — заведомо закрытым портом ниже 1024
  (обычно `http://127.0.0.1:1`): службы там не бывает ни на машине
  разработчика, ни на чистом раннере. Это законный приём, и сторож его
  не трогает.
- **Идентификатор** — синтетическим, построенным в самом тесте: номер
  считают тем же законом ключа, что и продукт, либо берут заведомо
  вымышленный.
- **Путь** — `tmp_path` и `monkeypatch`; внешний файл ищут рядом с
  репозиторием или по переменной окружения, а не по зашитому пути.
- **Личность** — константой `ADMIN_EMAIL` из `tests/_stand_identity.py`:
  это вымышленный адрес зоны `.invalid`, которым `tests/conftest.py`
  задаёт `CREW_SUPER_ADMIN` на весь прогон. Производные от неё берут
  оттуда же — `ADMIN_SLUG` (папка выгрузок) и `LEGACY_UPLOAD_ID` (запись
  карты владения с коротким слагом). Личная почта владельца машины в
  тестах запрещена: до 10.09.2026 она стояла в `conftest` и повторялась
  литералом в сорока с лишним файлах.
- **Число, которое уже есть в коде** (порт по умолчанию, адрес
  продукта) — константой боевого кода: повтор числом расходится с кодом
  молча.

### Как работает сторож

Файл `tests/test_no_environment_literals.py` разбирает каждый тест
разбором исходного текста (`ast`) и смотрит только **значения** —
строковые, байтовые и числовые константы. Комментарии и строки описания
он не читает: рассказ о происхождении теста зависимостью не является.
Зона CDPM (`test_cdpm_*`, `test_installer*`, `test_uninstaller*`) — под
своим сторожем дорожки CDPM.

Перечень живых значений каталога сторож берёт с диска, из `catalog/*.json`:
зашитый список сам был бы литералом среды.

Находка — красный тест со словами: файл, строка, что за литерал и чем
его заменить.

### Как обосновать исключение

Исключения ведутся списком `ALLOWLIST` в том же файле — «файл: что:
почему». Строка нужна, только когда значение **необходимо** и безопасно:
боевой код принимает лишь такой адрес (проверка «модель обязана быть
локальной»); значение — искомое самого теста (страж утечки путей
доказывает, что пути в выдаче НЕТ); файл в зоне другого исполнителя и
находка передана отчётом. Обоснование пишется словами, а не пометкой.

Список не зарастает: второй тест сторожа проверяет каждую строку — файл
существует, находка такого вида в нём есть, обоснование написано. Если
прощать стало нечего, строку обязаны снять.

## 9. Как проверить

1. Добавьте тестового пользователя с ролью «пользователь». Ожидаемо: строка в таблице; после первого входа заполняются «Последний вход» и «Входов».
2. Под администратором откройте «Журнал», отфильтруйте по своему email. Ожидаемо: события «Вход» и «Переход» с разделами, время в UTC.
3. Супер-администратором откройте «Установки», извлеките список моделей. Ожидаемо: список актуальных моделей; ключ в открытом виде нигде не показывается.
4. Откройте `/versionz` на любом контуре без входа. Ожидаемо: срез кода, отпечаток решателя и признак совпадения с манифестом сборки; ни одного имени файла заказчика.
5. После деплоя: каждый из трёх адресов контуров без авторизации отвечает 401; версия статики содержит маркеры нового релиза; после Purge браузер получает новый интерфейс. Ответ 401 — минимальная проверка живости и защиты HTTP-слоя; полную готовность (JVM-солвер, локальная модель Ollama, файловые хранилища) подтверждает только пробный расчёт на тестовом экземпляре.
