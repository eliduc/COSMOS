# Код выхода 4 этапа 1: вердикт, а не сбой

## Контекст

Контракт кодов возврата построителя цепочек (`_pairing_builder.py`):
0 — покрытие полное и каталог опубликован; 2 — перебор не достроил
(каталог отложен в `.pending`); 3 — ослабленное покрытие (отложен);
**4 — непокрытое есть, но всё оно непокрываемо в принципе: каталог
опубликован, свидетельство внутри**. Публикация под каноническим именем
разрешена только вердиктам из белого списка самого писателя (внешний
аудит R7, P0-05), поэтому свежий канонический каталог — доказательство
публикации.

Исполнитель задач (`webapp/jobs.py`) знал gate-семантику «ненулевой код
при завершённых артефактах = вердикт, а не сбой» **только для этапа 2 и
мультироли**. Прогон этапа 1 из интерфейса на данных с доказуемо
непокрываемыми участками (у набора заказчика такие рейсы встречались —
краевой эффект горизонта) завершался кодом 4 и помечался «ошибкой»,
хотя каталог был опубликован и годен (найдено владельцем при проверке
инструкции 2026-08-12: допустимое решение с малым зазором и полным
каталогом цепочек — и красная пометка «ошибка»).

## Решение

Та же gate-семантика для этапа 1, зеркально этапу 2 и fail-closed:

- «успешно» + `gate_nonzero` ставится **только** коду выхода 4 и только
  при каталоге, записанном ЭТИМ прогоном (штамп `run_id` внутри каталога;
  для каталогов без штампа — строгий `mtime >= started_ts`);
- коды 2/3 канонический каталог не пишут и остаются ошибками; любой
  другой ненулевой код — настоящий сбой, даже при свежем каталоге
  (сбой после публикации честно виден в журнале);
- код 4 без опубликованного каталога — ошибка.

## Следствия

- Проверка `_stage1_catalog_completed` в `webapp/jobs.py` — зеркало
  `_stage2_artifact_completed`; ветка в `_watch` требует ровно код 4.
- Контракт (`webapp/API-CONTRACT.md`), справочник статусов (руководство,
  часть 9) и обзор системы дополнены этапом 1.
- Эталон инструкции ввода контура заказчика дополнен строкой «статус
  задачи: успешно, с пометкой вердикта гейта».
