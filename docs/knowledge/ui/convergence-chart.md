# График схождения оптимизации

Задача владельца (2026-08-12): во время пейринга и ростеринга видеть не
только метрики процесса, но и график целевой функции — достигнутого и
оценки снизу, чьё схождение означает оптимальность.

## Образ

«Коридор неопределённости»: сверху спускается ступенчатая линия
достигнутой стоимости (каждое решение — ступенька с маркером), снизу
поднимается доказанная граница; полупрозрачная полоса между ними —
недоказанный зазор. Смыкание полосы = доказательство оптимальности.
Линии ступенчатые намеренно: наклон рисовал бы несуществующие
промежуточные решения.

Этап 2 (локальный поиск) нижней границы не имеет — рисуются штраф
незакрытого спроса и пунктир идеала (ноль штрафа), об отсутствии
границы сказано подписью, а не молчанием; при падении на порядки шкала
автоматически логарифмическая.

## Ось времени — весь бюджет (правка 2026-08-13)

Замечание владельца: «по оси абсцисс должен сразу быть весь интервал, и
кривая должна двигаться слева направо». Прежде домен растягивался по
последнему событию — ростеринг, нашедший решение на 114-й секунде из
600, рисовал обвал у ПРАВОГО края, и читалось это как «улучшение
случилось в конце», хотя оно случилось на пятой части бюджета. Теперь
домен — `[0, бюджет]` (расширяется только если прогон бюджет перебрал),
деления 0 / ¼ / ½ / ¾ / бюджет, свыше 15 минут — в минутах; последняя
ступень тянется до «сейчас», пунктирная отметка стоит на текущем
моменте, и секундный тикер двигает кривую между опросами.

Там же убрана вторая помеха чтению: первая «нижняя граница» CP-SAT
отрицательна (границы ещё нет) — она тянула шкалу до −298 млн и
сплющивала весь содержательный ход в линию. Отрицательные границы не
входят ни в шкалу, ни в полосу зазора; полоса начинается там, где
граница появилась, а в шапке до этого момента стоит прочерк.

## Устройство

- **Машинный след**: решатели пишут события улучшений в
  `runs/progress/<run_id>.jsonl` (`_opt_progress.ProgressWriter`).
  Этап 1 — из колбэка CP-SAT (инкумбент + граница, из той же точки,
  что печать «ход точного покрытия»); этап 2 — слушатель улучшений в
  Kotlin, снимок по `GET /schedules/progress` изолированной JVM,
  поллер пишет след. Журнал не парсится (правило «числа из машинного
  отчёта»); после завершения прогона след неизменяем.
- **API**: `GET /api/jobs/{id}/progress` — события по публичному id
  задачи через приватную личность прогона (`jobs.run_id_of`).
- **Панель**: `renderConvergence` в `app.js` — чистый SVG без
  библиотек (офлайн-контур), числовая шапка (достигнутое / граница /
  зазор %), подписи через словарь на пяти языках, цвета — токены темы.

## Возврат к графику завершённого прогона

Кнопка «Журнал» в строке истории делает прогон текущим и перерисовывает
его график. Чтобы это работало и после перезапуска приложения, личность
прогона (имя файла следа) сохраняется в записи задачи — служебным
блоком, который публичный ответ API не несёт; записям прежних прогонов
она восстанавливается по идентификатору постановки (манифест лежит в
каталоге, чьё имя и есть личность) и записывается разово. До этого
перезапуск сервера — включая любой раскат — обрывал связь задачи со
следом, и график исчезал навсегда (вопрос владельца 2026-08-13).
