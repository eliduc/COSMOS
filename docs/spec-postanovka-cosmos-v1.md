## 1. Назначение

Пакет постановки — единица обмена между CDPM (формализация
документов авиакомпании) и решателем COSMOS: всё, что нужно, чтобы
решатель решал ИМЕННО задачу, собранную и подтверждённую конвейером
CDPM, — правила, целевые функции, веса мягких, режимы задач и
очищенные операционные данные, — одним самодостаточным артефактом с
контрольными суммами.

Производитель: CDPM (экспорт «Пакет постановки» прогона).
Потребитель: COSMOS (webapp + kotlin-solver); контуры
заказчиков — тем же кодом.

## 2. Состав пакета

Пакет — zip-архив (или каталог) со следующими файлами. Обязательные
помечены «(об)».

| Файл | Что это |
|---|---|
| `manifest.json` (об) | Паспорт пакета: версия, перечень файлов с SHA-256, разрешённые режимы задач |
| `model.json` (об) | Машинная модель CDPM (контракт П-1): правила, вопросы, целевые функции; схема — `cdpm/schemas/cdpm-model.schema.json` |
| `objective.json` (об) | Критерий оптимизации: целевые по задачам, компоненты-мягкие с весами, матрица корректности, семантика свёртки |
| `clean-data.json` | Очищенные операционные данные (`{customer, tables, cleaning}`); отсутствует, если книга данных в прогон не загружалась |
| `svod.md`, `anketa.md` | Человекочитаемые свод и анкета (справочно; истина — model.json) |
| `freeze/clauses/<sid>.json` | Клаузы заморозки исходных документов правил — записи один в один с `cdpm-runs/<run>/freeze/clauses` (те же имена и байты); сводка в `manifest.freeze_clauses` (дополнение к 1.17, 2026-09-06). Потребитель сверяет решения с исходными документами (проверки по ИДАК) без доступа к каталогу прогонов CDPM; отсутствуют, если сборка шла без комплекта заморозки |

## 3. manifest.json

```json
{
  "spec_version": "1.3",
  "customer": "«Полярис» (нано, эталон вехи А)",
  "source_run": "run-0025",
  "revision": 3,
  "files": [
    {"name": "model.json", "sha256": "…", "bytes": 12345},
    {"name": "objective.json", "sha256": "…", "bytes": 2345}
  ],
  "readiness": "в",
  "allowed_modes": {
    "pairing":  ["feasibility-hard", "feasibility-soft", "optimization"],
    "rostering": ["feasibility-hard", "feasibility-soft"]
  },
  "objectives": {
    "pairing":  ["O-S1-табл-2-строка-2-кол-3"],
    "rostering": []
  },
  "has_data": true,
  "crew_size": {"value": 2, "rule": "R-S1-табл-2-строка-3-кол-3"}
}
```

- `spec_version` — «MAJOR.MINOR». Потребитель ОБЯЗАН отказаться от
  пакета с неизвестным MAJOR; при известном MAJOR и большем MINOR —
  читать известные поля, неизвестные игнорировать.
- `files` — каждый файл пакета, кроме самого манифеста; потребитель
  ОБЯЗАН сверить SHA-256 всех файлов до какого-либо чтения
  (несовпадение — отказ всего пакета).
- `allowed_modes` — разрешённые режимы per задача, вычисленные из
  матрицы корректности на момент выгрузки: ячейка ready=true →
  режим в списке; для optimization дополнительно требуется непустой
  список целевых. Это ГЕЙТ ЗАПУСКА: потребитель не имеет права
  запускать режим, которого нет в списке.
- `objectives` — идентификаторы незаблокированных целевых per
  задача; запуск режима optimization требует явного выбора ОДНОЙ
  целевой из списка (каждая целевая — отдельная задача).
- **Один пакет обслуживает ОБЕ задачи** (уточнение 2026-08-22 по
  вопросу этапа Б): отдельной выгрузки «под пейринг» не существует —
  один прогон CDPM даёт одну постановку. Задача (pairing |
  rostering) — параметр запуска потребителя; гейт запуска — по
  allowed_modes ВЫБРАННОЙ задачи; для optimization выбранная целевая
  обязана принадлежать списку objectives этой задачи.
- `revision` — ревизия модели CDPM (meta.revision источника).

## 3а. Машинные параметры правил (ревизия 1.3)

У правила может быть поле `params` — список записей
`{name, value, unit, as_written, relation, qualifier?, tz?}`:

- `name` — из закрытого словаря (`cdpm.model.PARAMS`; имена первой
  волны сравнения порогов согласованы со стороной COSMOS, полный
  перечень и смыслы — дизайн 17-DIZAJN-1.3 ревизия 2); имя вне
  словаря производителем не проставляется (след — в примечании
  правила);
- `value` — канонизированное число: длительности и время суток —
  В МИНУТАХ («12:00» → 720; разбор двоеточия и словесных форм
  («12 часов», «45 минут», «7 суток») делает ТОЛЬКО производитель,
  под гейтом со сверкой против `as_written`; след минутной природы
  БЕЗ явной единицы времени — голое «12» — не канонизируется и
  краснит запись: трактовка угадыванием инвертировала бы сверку),
  количества — целые; время суток ограничено 0..1439;
- `unit` различает ПРИРОДУ величины: `duration_minutes` ≠
  `time_of_day_minutes` ≠ `count` ≠ отношения кредита
  (`hours_per_credit_hour` / обратная `credit_hours_per_hour`) ≠
  `credit_hours`; смешение природ в сравнении — отказ, не
  арифметика;
- `as_written` — след «как было в правиле», для сверки человеком;
- `relation` — `max` | `min` | `eq` | `window`; `window` — ОКНО
  применения границы («в каждые 7 суток»), окном не является ни
  порог, ни предел: сравнивать window с max/min/eq запрещено;
- `qualifier` — необязательный уточнитель контекста записи
  (например, код базы у нормы резерва): несколько записей одного
  имени в правиле законны только с разными уточнителями; у
  параметров ОБЛАСТИ действия (`min_turnaround`) — только закрытый
  словарь «база» | «вне базы» (ревизия 1.4, синонимы законны в
  пакетах до 1.4);
- `tz` — обязателен при `time_of_day_minutes`, закрытый перечень
  `"UTC"` | `"base-local"` (местное время БАЗЫ); станционное
  местное время в этой версии запрещено — смещение не пояс, перевод
  часов уезжает молча; `local:<IANA>` — будущей ревизией.

Параметры лежат ПРИ правиле: заблокированное правило выводит свои
параметры из оборота вместе с собой. Потребитель на пути пакета не
имеет права ни на откат вне диапазона, ни на догадку — только отказ
с именем параметра, значением, единицей и правилом-источником.

## 4. Семантика режимов и критерия

Три режима задачи (у пейринга и ростеринга независимо):

1. **feasibility-hard** — найти любое решение, удовлетворяющее всем
   жёстким правилам; любое такое решение оптимально.
2. **feasibility-soft** — среди допустимых минимизировать сумму
   штрафов мягких правил; при полном нуле штрафов любое из таких
   решений оптимально.
3. **optimization** — выбранная целевая функция; критерий =
   целевая + Σ штрафов мягких СВОЕЙ задачи при направлении
   minimize, целевая − Σ штрафов при maximize. Каждая целевая —
   отдельная задача оптимизации (отдельный запуск).

**Ярусы важности и ничьи (обязательство версии 1.0, зафиксировано
2026-08-22).** Ярус важности целевой в этой версии ВСЕГДА равен 1:
потребитель вправе рассчитывать на два уровня счёта
(жёсткие/мягкие+целевая) и не обязан закладываться на третий.
Появление ярусов больше 1 — только ревизией этой спецификации, не
молча. Правило разрешения ничьих в записи целевой — справочная
проза для человека: в контур счёта решателя оно НЕ входит, и
приближать его слагаемым с малым весом НЕЛЬЗЯ (малое слагаемое на
больших масштабах искажает критерий недоказуемым образом); при
равных решениях ничья разрешается вне решателя.

Веса мягких берутся ТОЛЬКО из `objective.json`
(`{pairing|rostering}.components[].weight`); вес — целое
неотрицательное число либо null. Null означает «вес не
подтверждён» — при разрешённых режимах feasibility-soft или
optimization таких компонентов в зоне быть не должно (гейт пакета
это проверяет; потребитель, встретив null при этих режимах, обязан
отказаться, а не подставлять свои умолчания).

## 5а. Машинные метрики целевых (словарь версии 1.1)

Поле `objectives[].metric` — имя из закрытого словаря; ставится
формализатором только при точном смысловом соответствии, иначе
опускается (целевая без метрики исполняется таблицей соответствий
потребителя; `statement` всегда остаётся человеку для сверки).
Направление — всегда из машинного поля `direction`.

| metric | Смысл | Применима задачам | Оговорка |
|---|---|---|---|
| `total_pairing_cost` | суммарная стоимость пейрингов | pairing | вычислима только раздельным прогоном пейринга |
| `layover_nights_total` | суммарное число ночей вне базы | pairing, rostering | |
| `credit_hours_spread` | разброс кредитных часов между членами экипажа | rostering | решатель вправе заявить приближение (например, минуты рейсов) в отчёте применённого |
| `positioning_cost` | стоимость перегонов (позиционирования) | pairing, rostering | |
| `uncovered_seats` | число непокрытых мест | pairing, rostering | |
| `preferred_days_off_violations` | нарушения предпочитаемых выходных | rostering | |

Расширение словаря — только ревизией спецификации (MINOR).
Потребитель, встретив неизвестное имя (его словарь старее), обязан
исполнять целевую как безметричную (таблица соответствий) либо
честно отказать — подставлять догадку нельзя. Гейт производителя
отвергает метрику вне словаря и метрику, неприменимую зоне целевой.

## 6. clean-data.json

`{"customer": …, "tables": {sid: {лист: {"columns": […],
"rows": [{колонка: значение}, …]}}}, "cleaning": {"removed": […],
"kept_findings": […]}}`. Очистка — вычитание строк с адресными
находками блокирующей/критической серьёзности отчёта проверок 3.3;
каждая исключённая строка перечислена в `cleaning.removed`.

## 7. Обязанности потребителя (COSMOS)

1. Сверить SHA-256 всех файлов; проверить spec_version.
2. Уважать `allowed_modes` (гейт запуска) и требовать явного
   `objective_id` для режима optimization.
3. Применять веса ТОЛЬКО из пакета; отсутствие веса — отказ, не
   умолчание (fail-closed).
4. После решения вернуть перечень фактически применённых параметров
   (веса, режим, целевая) — производитель сверяет, что решалась
   присланная задача (гейт применённого).
5. Правила, которым нет исполнителя в решателе, — в явный отчёт
   «формализовано, не исполняется»; молчаливый пропуск запрещён.

## 8. Проверка пакета

Гейт `python -m cdpm.gates.gate_task_package <пакет>` — самотест,
сверка сумм, схема модели, пересчёт матрицы и допустимых режимов,
веса при разрешённых режимах. Печатает число рассмотренных объектов
и ВЕРДИКТ; красный — код возврата 1.

## Дополнение к 1.14 (2026-09-04): признак допуска моделей комплекта

Решение владельца 04.09.2026: работа CDPM заканчивается выпуском и

   проходит. Заявлять адресатами остатка ВОПРОСЫ, которых в

во всех исполнителях (лист «Аэропорты» больше не перекрывает контракт
молча).

`manifest.time` — объект, ключ присутствует только при правиле шкалы
времени (семья `time_scale`, параметр `base_tz_offset_min`):
- `time_scale`: `"base-local"` (сдвиг 0 — метки данных в местном времени
  главной базы) | `"shifted"` (ненулевой сдвиг; число — рядом);
- `base_tz_offset_min`: сдвиг шкалы меток из параметра правила;
- `source_rule`: идентификатор правила-источника;
- `base_time_zone` (необязательно): IANA-имя пояса главной базы из листа
  «Аэропорты» очищенных данных (колонки «Код» / `timeZone`): единственная
  зона всех аэропортов листа либо зона кода из свойства набора «главная
  база»; при неоднозначности ключа нет (не угадываем);
  `base_time_zone_basis` — словами, откуда взят пояс.

Признак `tz` у параметров времени суток (`UTC | base-local |
acclimatized`) и у календарных окон остаётся в правилах (ревизия 1.4+);
потребитель обязан отказывать словами, если исполнителя для заявленной
системы нет. Гейт пакета ≥ 1.16 пересчитывает `manifest.time` из
model.json + clean-data.json и краснит расхождение; пакеты младше судятся
прежним законом.

### 1.18.1. Объявленный горизонт — `manifest.horizon`

Источник: лист «Свойства» книги данных, ключи `planSince` и `planUntil`
(канон дат 1.15, система времени 1.16). Раздел:

```json
"horizon": {
  "start": "2026-10-01T00:00",
  "end_inclusive": "2026-10-31T23:59",
  "end_exclusive": "2026-11-01T00:00",
  "scale": "minute",
  "tz": "<из объявления системы времени пакета (1.16)>",
  "source": {"sheet": "Свойства", "keys": ["planSince", "planUntil"], "sid": "<лист>"}
}
```

- `end_inclusive` — минута `planUntil` как есть (так её сегодня судит
  `task_package.py`: рейс принадлежит горизонту при `start ≤ вылет ≤
  end_inclusive`); `end_exclusive = end_inclusive + 1 минута` вычисляется
  ровно один раз — производителем; читатели окон (сертификатор, решатель)
  берут `[start, end_exclusive)` и не прибавляют минуту повторно.
- Нет обоих ключей в «Свойствах» — ключа `horizon` в манифесте нет (как у
  `history`), читатель судит «горизонт не объявлен»: диагностика по
  назначениям допустима только как частичная (`source=inferred`), полного
  зелёного результата она не даёт.
- Проверка данных `горизонт-объявлен` (встроенная, класс «пропуск данных»):
  оба ключа читаемы, `start < end_inclusive`, один пояс; «границы на
  полных сутках» — показание (не замок), пока форма окна не потребует
  суточных границ. «Срез истории = start» — условие пригодности ПЕРЕДАННОЙ
  истории (шаблон `история-срез`): несовпадение — показание, ограничивающее
  перенесённое состояние семей истории («история непригодна» → третий
  исход для них), не запрет пакета и не стирание доказательств внутри
  горизонта; при отсутствии истории третий исход и решения
  `continue_zero` / `continue_partial` не меняются.

Проводная структура раздела `history` (1.17.2) не меняется: список

- `location_intervals[]` — канонический выход: объединение (union) дублей и

  объявленное условие до факта не повышается.
- `conflicts[]` — перекрытие РАЗНЫХ станций по времени:
  `{start, end, stations: [...], rows: [provenance…]}`; в этой области

Читатели (Kotlin `historyLocationIntervals`, `vmp/run/cost_scope.py`)
берут только `location_intervals[]` с `kind` и `conflicts[]`;
`location_evidence[]` они не интерпретируют. Без строк листа полей нет —
`unknown`; из среза, снимка `location`, `continue_zero` или базы приписки
интервал не выводится. Проверки данных (класс «история»): станция в сети
(лист станций/маршрутов), `start < end`, вид из перечня, `history_fact`

противоречие); другая станция в другом прошлом интервале — не

### 1.18.3. Отчёт данных: статус «частично прогнана» и покрытие окон

`CHECK_STATUSES = ("прогнана", "частично прогнана", "не применима", "не прогнана")`.
Проверка со статусом «частично прогнана» обязана нести `reason` и
`window_coverage`; находка может ссылаться на «прогнана» или «частично
прогнана» и сохраняет доказанное нарушение при неизвестности других окон;
строка свода с блокером не даёт ни «прогнана», ни «частично прогнана».

```json
"window_coverage": {
  "expected": 12, "evaluated": 9, "unknown": 3,
  "granularity": "windows" | "continuous_critical_cells",
  "expected_unit": "windows" | "critical_cells",
  "windows": [
    {"employee": "E1", "start_inclusive": "…", "end_exclusive": "…",
     "status": "evaluated" | "unknown", "outcome": "pass" | "violation" | null,
     "reason": "<доказательство либо причина неизвестности>"}
  ]
}
```

Инварианты (судятся кодом контракта отчёта и гейтом сертификата):
`expected = evaluated + unknown = len(windows)`; счётчики сверяются с
адресным списком; адрес окна `(employee, start_inclusive, end_exclusive)`
уникален; окно без причины — дефект; `unknown > 0` ⇔ статус «частично
прогнана»; «частично прогнана» без неизвестных окон — дефект.
Сертификат `certified = true` невозможен при любой «частично прогнана»,
«не прогнана» или `unknown ≠ 0`.

Непрерывное доказательство (`granularity = "continuous_critical_cells"`,
`expected_unit = "critical_cells"`) — обязательная форма доказательства
правил «отдых ≥ R в любом окне W» (K-15): единица — критическая ячейка
области окончаний окна (точка либо открытый интервал между точками
разбиения), а не старт окна по календарным суткам; суточная форма
остаётся диагностикой, её показания `cells/1` полным доказательством не
называются. Раздел несёт `ending_domain {start_inclusive, end_inclusive}`,
`employee_proofs {emp: {window_minutes, required_rest_minutes,
occupancy_basis: "normative_duties", known_occupancy_intervals[],
proven_rest_intervals[], passing_window_end_spans[], fully_known_window_end_spans[]}}`,
у каждого окна `ending_domain {start, end, kind: "point" | "open_interval",
start_closed, end_closed}` и, для неизвестной ячейки с доказанной нижней
границей нарушения, `lower_bound_violation: true`. Код контракта
пересчитывает объединения по интервалам и требует, чтобы ячейки покрывали
всю область окончаний ровно один раз; отсутствие раздела у правила
непрерывного окна читается как «не прогнана», а не «прогнана».
Производитель, решатель и сертификатор используют одну нарезку, одни
адреса, одну единицу штрафа и одну версию показаний.

### 1.18.4. Источник конфигурации роли — `config_source`

Отпечаток канала стадии (A11) и журнал стадии несут
`config_source ∈ {"site-default", "run-explicit", "none"}` (смысл — `default` /
`explicit_override` таблицы S06; `none` — раскладки нет, действует умолчание
канала без конфигурации роли), `requested: {provider, model, channel}`
и `effective: {provider, model, channel}`. Семантика (S06, принята тремя
сторонами): допуск = признак комплекта ∩ запрет контура; неизвестный /

### 1.18.5. Раскладка не объявлена — облачная стадия не стартует (S06-R2)

Уточнение семантики `config_source = "none"` (решение владельца
2026-09-06, план единой версии §3.7): значение `none` допустимо только
для локального класса политики файлов (локальная модель — своя у
площадки). Для облачного класса модель стадии обязана быть объявлена —
площадкой (носитель `agents-default.json` каталога данных) или прогоном
(`agents.json`); иначе панель CDPM не подставляет облачную модель «по
умолчанию канала», а отказывает словами до первого вызова модели
(HTTP 409: что не объявлено, где объявить). Порядок отказов: допуск
«только локально» — старший (отказ дисциплины контура словами признака
комплекта), раскладка судится только там, где облако допуском
разрешено. Ранний признак — ключ `layout` статуса прогона с момента
создания: `{"source": "site-default" | "run-explicit" | "none",
"cloud_gate": "open" | "blocked", "detail": <слова отказа при blocked>}`.
Настройка ролей прогона — полный снимок: интерфейс шлёт всю действующую
раскладку с правкой роли поверх; частичное тело по API делает прочие
облачные роли «не объявленными». Роль объявляет облачную модель только
слотом класса «cloud» с провайдером или моделью; роль с одним локальным
слотом, пустыми каналами или одной инструкцией облачную стадию не
открывает (отказ словами с именем роли и действующей конфигурации), а
`layout.undeclared_roles` перечисляет такие роли-семейства (worker,
auditor, arbiter, applier) заранее; `layout` пересчитывается после
правки ролей и признака комплекта. Установка COSMOS создаёт носитель
площадки из образца `cdpm/agents-default.json.example`, если его нет, и
записывает его в журнал установки вместе с отпечатком байтов; удаление
по журналу считает такой носитель созданным установкой только пока его
байты совпадают с журналом — изменённый владельцем носитель есть его
данные, и удаление каталога данных останавливается.
Пакет постановки этой ревизией не меняется (`spec_version` остаётся
`1.18`); журнал стадий `stage_channels` и отпечаток канала — без
изменений.


Семантика. Ключ `catalog` — ровно два поля, версия и отпечаток, и ничего больше: потребитель судит форму этого ключа буквально. Производитель берёт отметку у ТОГО экземпляра каталога, которым сажает правила: у строк пакета (`template_fit.registry_rev`) и у манифеста отпечаток совпадает по построению, а не по добросовестности сборщика. Смысл полей разный и путать их нельзя: `template_fit.registry_rev` отвечает на вопрос «по какому каталогу посажена ЭТА строка» (отпечаток на момент посадки), `catalog` — «каким каталогом выпущен пакет». Сторож COSMOS перед нажатием кнопки судит только `manifest.catalog` против привязок исполнителей (версии и отпечатка каталога, к которому привязан решатель): старшая версия каталога у пакета — стоп словами (при версиях 0.x — и младшая); патч или черновик того же ядра версии — предупреждение; равная версия с иным отпечатком — предупреждение в состоянии и журнале. Происхождение ключа сторожу безразлично.

Ключ `fits_catalog` пишется, когда в модели пакета есть хотя бы одна посадка с ревизией, и говорит ровно три вещи: какие ревизии встретились (`revs`, без повторов, отсортированы), одна ли это ревизия (`uniform`) и та ли она, которой выпущен пакет (`matches_catalog`; без ключа `catalog` сравнивать не с чем — null). Слова `note`: «посадки по прежнему каталогу (rev …)» при единственной ревизии, не равной отпечатку, и «посадки разных ревизий каталога: …» при нескольких; сходится всё — null. Это ПРЕДУПРЕЖДЕНИЕ, а не отказ: ревизия строк, отличная от отпечатка каталога (в том числе 12-значные ревизии посадок, сделанных до переезда на каталог), пакет не порочит — выпуск не останавливается, потребитель видит расхождение словами и решает сам. Гейт производителя судит форму обоих ключей и пересчитывает сводку по строкам `model.json` пакета: расхождение сводки с посадками — красный (подделка справки), расхождение ревизии строк с отпечатком каталога — нет.

Режим среза базы шаблонов (`CREW_VMP_TEMPLATE_BASE`, обратная задача H0): посадки идут по срезу, каталог панели к пакету отношения не имеет — отметка берётся из полей самого среза `catalog_version` и `catalog_fingerprint`, а без них ключа `catalog` в манифесте нет. Пакет без ключа читается прежним законом: «каталог не объявлен» — это предупреждение сторожа, а не отказ; пакеты, выпущенные до переезда, законны и судятся как прежде. Версия спецификации (`SPEC_VERSION`) не меняется — оба ключа необязательные, по образцу «Дополнения к 1.17»: читатель, который их не знает, читает пакет как раньше.

## Дополнение к 1.18 (2026-09-11, третье): непротиворечивость в пакете — `manifest.consistency`

Слово владельца 11.09.2026 («давай реализуем оба предложения») по предложению CDPM: принцип ВМП о непротиворечивости свода держится кодом целиком. Машинная проверка через SMT (СМТ-1: языковая модель переводит жёсткие правила в SMT-LIB, решатель Z3 выносит вердикт и называет ядро конфликта) перестаёт быть отдельным действием панели и становится ОБЯЗАТЕЛЬНЫМ рубежом выпуска: пакет постановки несёт вердикт о своде, которым он выпущен.

```json
"consistency": {
  "verdict": "sat | none",
  "model_sha256": "<64 hex — sha256 байтов КАНОНИЧЕСКОЙ модели прогона>",
  "n_rules": "<сколько жёстких правил свода проверялось>",
  "n_translated": "<сколько утверждений вернул переводчик>",
  "translator": {"role": "smt_translator",
                 "provider": "<действующий провайдер | null>",
                 "model": "<действующая модель | null>"},
  "report": "extract/smt-report.json"
}
```

Семантика вердикта. `sat` — ВСЕ жёсткие правила переведены и утверждения совместны: противоречия не найдено (с 12.09.2026, A01: `n_translated == n_rules` обязательно; «sat» по части свода вердиктом не является). `none` — проверять было нечего: жёстких правил (HARD, DATA, DEF) в своде нет, и тогда `n_rules` — ноль. ДРУГИХ вердиктов у выпущенного пакета не бывает: `unsat` (конфликт с названным ядром), неполный перевод (переведены не все жёсткие правила — код `smt-incomplete`, перечень непереведённых ключом `items` тела 409) и отсутствие вердикта (решателя на площадке нет, канал переводчика не построился, перевод не прошёл парсер Z3 и после единственного повтора, решатель не пришёл к вердикту; ноль утверждений при непустом своде — частный случай неполного перевода, код `smt-incomplete`) ОСТАНАВЛИВАЮТ выпуск словами — `409` с телом `{"detail": "<слова>", "code": "smt-contradiction" | "smt-incomplete" | "smt-unavailable", "items": [<правила, если применимо>]}`. Отчёт прогона `extract/smt-report.json` несёт версию схемы `schema_version: "smt-report/2"` и статус каждого жёсткого правила (`translations[].status`: translated / untranslatable / missing); отчёт старой формы свежим не считается. Fail-closed: «обязательный» значит, что без вердикта пакета не существует, а не «выпускается без проверки». `detail` остаётся строкой (её читают панель и раннер наборов), `code` — добавочный ключ; у прежних отказов выпуска он пустой.

Свежесть вердикта. Отчёт проверки (`extract/smt-report.json` в каталоге прогона — один носитель у кнопки панели и у рубежа выпуска) годится ровно тогда, когда он о ТОМ ЖЕ своде: отпечаток `model_sha256` равен sha256 байтов канонической модели прогона. Отчёта нет, он о прежнем своде или сделан до 11.09.2026 (без отпечатка) — рубеж проверяет свод сам, тем же каналом роли `smt_translator`, и сохраняет отчёт; вызов модели ложится в журнал вызовов прогона и считается в записи о прогоне наравне с остальными — проверка рубежа записывается ДЕЙСТВИЕМ прогона «smt-verify» (тем же, что пишет кнопка панели; происхождение в журнале действий — «гейт выпуска пакета»), и вызов несёт его номер. Поэтому обычная цена рубежа — ОДИН вызов модели на свод, а не на нажатие кнопки: второй экспорт того же свода вердикт берёт из отчёта. У ПОТОМКА ПОВТОРА вердикт берётся из отчёта ИСТОЧНИКА при том же отпечатке свода (своды потомка и источника байт-идентичны по Ф-1.7): отчёт копируется в потомка и едет в его манифест, модель не вызывается — у повтора «из журнала» её и вызвать нечем, запроса переводчика в журнале источника нет.

Чего в ключе нет и почему. Метки времени проверки нет: два одинаковых по смыслу экспорта обязаны давать байт-идентичный манифест (Ф-1.7 — по нему сертификаты разных нажатий кнопки сравнимы, и по нему же пакет потомка повтора совпадает с исходным), а момент проверки живёт в отчёте прогона, на который указывает `report`. Сам отчёт в пакет не кладётся: он о КАНОНИЧЕСКОМ своде прогона, а пакет несёт свод после машинного лечения сборкой (`model.json` пакета), и отпечаток в ключе указывает на прогон, а не на файл пакета — потребитель его не пересчитывает.

Гейт производителя (`cdpm/gates/gate_task_package.py`) судит форму ключа (ровно перечисленные поля), вердикт из перечня `{sat, none}`, правдоподобие счётчиков (переведённых не больше жёстких, `none` только при нуле правил, `sat` не бывает без единого утверждения) и роль переводчика. Пересчитать вердикт по пакету нельзя и не нужно — гейт стережёт другое: пакет с вердиктом, которого рубеж выпуска не выпускает, подделан или собран в обход рубежа. Ключ необязательный: пакеты, выпущенные до 11.09.2026, читаются прежним законом «непротиворечивость не объявлена». Версия спецификации (`SPEC_VERSION`) не меняется — по образцу «второго дополнения»: читатель, который ключа не знает, читает пакет как раньше.

## Дополнение к 1.18 (2026-09-12, четвёртое): предмет проверки непротиворечивости — `subject_sha256`, `subject` и отчёт в пакете

Исправление A01-F1/F2 независимого аудита («четыре принципа ВМП», вердикт VERDICT-A01 от 12.09.2026). Третье дополнение (11.09.2026) выше оставлено в том виде, в каком было выпущено: опубликованное дополнение не переписывается задним числом. Там, где это дополнение с ним расходится, действует ЭТО — оно моложе датой.

Что нашёл аудит. Рубеж выпуска судил КАНОНИЧЕСКИЙ свод прогона (`extract/model.json`), а в пакет ложится свод ПОСЛЕ преобразований сборки: правило с устаревшим ярлыком SOFT, посаженное на жёсткую семью каталога, становится HARD. Пакет уходил со справкой о другом наборе правил («sat 1/1», а при пустом каноническом наборе — «none 0/0»), и сверить справку с `model.json` пакета было нечем: отчёта в пакете не было, а имена правил без формулировок ничего не привязывают (A01-F1). Второе: записи ответа переводчика ВНЕ ФОРМЫ (не объект в `asserts`, не строка в `decls`) отбрасывались молча — «полный перевод» получался из неполного ответа (A01-F2).

Форма ключа `manifest.consistency` (два новых поля; всё остальное — как в третьем дополнении):

```json
"consistency": {
  "verdict": "sat | none",
  "model_sha256": "<64 hex — sha256 байтов КАНОНИЧЕСКОЙ модели прогона>",
  "n_rules": "<сколько жёстких правил ВЫПУСКАЕМОГО свода (model.json пакета) проверялось>",
  "n_translated": "<сколько из них переведено (строки translated отчёта)>",
  "translator": {"role": "smt_translator",
                 "provider": "<действующий провайдер | null>",
                 "model": "<действующая модель | null>"},
  "report": "extract/smt-report.json | extract/smt-report-package.json",
  "subject_sha256": "<64 hex — sha256 канонического JSON предмета проверки: [{id, kind, statement}] жёстких правил model.json ПАКЕТА, по id>",
  "subject": "canonical | package"
}
```

Предмет проверки. `subject_sha256` — отпечаток того, что переводчик читает из жёстких правил ВЫПУСКАЕМОГО свода (идентификаторы, виды HARD/DATA/DEF, формулировки `statement`; функции `smt_verify.subject_of` / `subject_fingerprint`; посадка, зона, параметры и примечания в задание переводчику не идут и предмет не меняют). `subject` = `canonical` — предмет выпускаемого свода равен предмету канонического, вердикт вынесен отчётом кнопки `extract/smt-report.json`; `subject` = `package` — сборка изменила набор жёстких правил или их формулировки, отчёт кнопки о выпускаемом наборе не судит, и вердикт вынесен отдельным отчётом пакета `extract/smt-report-package.json`; `report` называет путь того отчёта в прогоне. Копия этого отчёта едет в пакете файлом `smt-report.json` (назван в `files` с суммой): по нему гейт производителя и любой читатель сверяют перевод с жёсткими правилами `model.json` пакета. Каждый отчёт (`smt-report/2`) несёт `subject_sha256` своего предмета; отчёт пакета — ещё и `subject_changes` (слова об отличиях от канонического свода: «R-7 — стало жёстким при сборке (SOFT→HARD)»). Отчёт пакета живёт ровно пока предмет выпуска расходится с каноническим: вернулся предмет к каноническому (сменился каталог шаблонов — правило больше не становится жёстким), и прежний отчёт пакета при следующем выпуске снимается, чтобы не читаться как отчёт о нынешнем выпуске; отчёт кнопки рубеж не переписывает никогда.

Свежесть вердикта — к закону третьего дополнения добавлен ПРЕДМЕТ. Отчёт годен, когда он о том же своде (`model_sha256` равен отпечатку канонической модели прогона) И о том же предмете: `subject_sha256` отчёта равен отпечатку предмета выпускаемого свода. Отчёт, не назвавший своего предмета (форма без `subject_sha256`), свежим не считается ни в одном из двух путей — вердиктом о выпускаемом наборе правил он не является, и рубеж проверяет свод сам. У ПОТОМКА ПОВТОРА при разошедшемся предмете нужен отчёт ПАКЕТА источника о том же предмете; без него — отказ `smt-unavailable` со словами об изменившихся правилах и советом выпустить пакет в источнике, а не выпуск на старых счётчиках.

Полнота перевода и записи вне формы (A01-F2). «sat» требует, чтобы переведены были ВСЕ жёсткие правила выпускаемого свода: `n_translated == n_rules`. Записи ответа переводчика вне формы (`null`, число, строка, список, `true` в массиве `asserts`; не строка в `decls`; сам массив не список) — нарушение формы: оно тратит тот же единственный повтор с запиской, называющей позицию и вид («asserts[3]: не объект (null)», «decls[1]: не строка (number)»), а сохранившись после повтора, оставляет отчёт без вердикта (перечень `malformed` с позицией, видом и началом значения) и останавливает выпуск кодом `smt-incomplete` с позициями в `items` — даже когда все правила названы. Тем же законом имени: запись-объект, которая правила не назвала (`rule` отсутствует, пуст или не строка), попадает в `dropped` не выдуманным идентификатором, а своей исходной позицией в массиве ответа («asserts[3]»), и той же позицией — в `items` отказа.

Беда самой проверки — отказ с кодом. Решателя на площадке нет, канал переводчика не построился, перевод не прошёл парсер Z3 и после повтора, отчёт некуда положить (путь отчёта занят каталогом или не записывается) — выпуск останавливается словами с кодом `smt-unavailable`; путь отчёта, видный заранее, судится ДО вызова модели, и вызов на такой выпуск не тратится. Молчаливого выпуска без вердикта и трассировки наружу не бывает ни в одном из этих случаев.

Гейт производителя (`cdpm/gates/gate_task_package.py`) к прежнему (форма ключа, вердикт из перечня `{sat, none}`, правдоподобие счётчиков, роль переводчика) добавляет СВЯЗЬ справки с выпущенным набором правил: `subject_sha256` равен отпечатку жёстких правил `model.json` пакета; `report` отвечает `subject`; строки `translations[]` отчёта `smt-report.json` из пакета покрывают точный набор жёстких правил `model.json` (жёсткое правило без строки `translated`, чужая, повторная строка, строка без тела, запись `malformed` — красные); `n_rules`/`n_translated` равны пересчёту по отчёту и `model.json`; `none` невозможен при жёстких правилах в пакете; отчёт в пакете о том же своде и предмете, что ключ — `subject_sha256` в самом отчёте ОБЯЗАТЕЛЕН и обязан совпасть с пересчитанным по `model.json` пакета (он привязывает строки перевода к ФОРМУЛИРОВКАМ правил, а не к одним их именам). Вердикт решателя по пакету не пересчитывается — переводчика у гейта нет.

### Совместимость: кто читает как раньше, а кто нет

Версия спецификации не меняется (`SPEC_VERSION` = 1.18): форма ключа расширена, а не переименована. Но «читатель читает как раньше» — НЕ про всех читателей, и вот точный список.

ТЕРПИМЫЕ читатели — новых полей не знают и знать не обязаны:
- раннер H0 в COSMOS (`open-bench/polyaris-h0/run_local_pipeline.py`: `consistency_words` печатает вердикт, счётчики, переводчика и путь отчёта; `consistency_problems` сверяет одно слово вердикта с ожиданием набора) — ключ с шестью полями и ключ с восемью он читает одинаково;
- приёмник пакета COSMOS (`webapp/task_package.py`, `load`) — раздела `consistency` он не читает вовсе;
- любой читатель пакета БЕЗ ключа `consistency` (выпущен до 11.09.2026) — прежний закон «непротиворечивость не объявлена» в силе.

НЕТЕРПИМЫЙ читатель — гейт производителя (`cdpm/gates/gate_task_package.py`), и он же стоит в приёмнике COSMOS: `webapp.task_package.load` перед разбором запускает гейт (`run_producer_gate`), так что отказ приходит от гейта, а не от разбора. Совместимости здесь нет НИ В ОДНУ сторону, и делать вид, что есть, нельзя:
- гейт редакции 12.09.2026 КРАСИТ пакет прежней формы (шесть полей, без отчёта в пакете) словами «сверить справку с набором жёстких правил пакета нельзя; выпустите пакет заново»;
- гейт редакции 11.09.2026 КРАСИТ пакет новой формы: восемь полей он читает как «иное, чем перечислено», то есть как подделку справки.

Почему это законно. Панель (сборщик пакета) и гейт производителя выпускаются ОДНИМ СРЕЗОМ — один репозиторий, один коммит; приёмник COSMOS запускает гейт из того же дерева (`cdpm.gates.gate_task_package` тем же интерпретатором из корня репозитория). Пакет принимается гейтом СВОЕГО среза, а не чужого, и раскатывать панель и гейт порознь нельзя. Пакеты прежней формы, выпущенные 11–12.09.2026, не «читаются как раньше» — они ВЫПУСКАЮТСЯ ЗАНОВО: рубеж проверит выпускаемый свод и положит отчёт в пакет. Это осознанная плата за A01-F1: справка, которую нельзя сверить с набором правил пакета, вердиктом не является.

Ранняя часть исправления — снятие безусловных заявлений полноты: продукт нигде не объявляет смысловой полноты, а называет ровно то, что доказано, и пробел.

Что доказывают ключи `coverage`, `measure` и протокол измерителя. Ровно ФАКТЫ ПОКРЫТИЯ: каждая клауза комплекта заморозки получила вердикт (покрыта строкой свода, целевой или вопросом анкеты либо признана аудитором «не правило» с причиной); ни одна строка свода не осталась без объявленного источника; ни один якорь строки, целевой или вопроса не висит вне комплекта; каждая ВЕЛИЧИНА клаузы (число с единицей, время, доля, код перечня, день недели) взята машинным полем строки, спрошена анкетой или закрыта вердиктом аудитора; каждый нормативный носитель имеет строку, вердикт «не правило» или открытый вопрос на себе.

Чего они НЕ доказывают. Единица счёта — клауза, якорь и величина, а не ОБЯЗАТЕЛЬСТВО. В одном абзаце могут стоять две нормы: числовой предел смены («не более 600 минут») и нечисловое требование («сотрудник обязан иметь действующий допуск к типу воздушного судна»). Привязка любой строки покрывает якорь абзаца, учёт величин закрывает число, и второе — нечисловое — обязательство пропадает молча: замок покрытия, замок содержания, измеритель и индикатор «Биекция» при этом зелёные. Живой LLM-аудитор такой пример обнаружить может, но проверенные механизмы не делают обнаружение обязательным.

Ключ манифеста. Там, где пакет предъявляет факт покрытия, он тут же называет его предел:

```json
"coverage": {
  "clauses": 2, "covered_by_rows": 2, "not_rule": 0, "missing": 0,
  "values_without_addressee": 0, "normative_without_rows": 0,
  "values_by_verdict": 1, "normative_not_rule": 0,
  "meaning_completeness": "полнота обязательств внутри клаузы — в том числе нечисловых — не доказана (A12); ведомость атомарных обязательств — волна 19"
}
```

`meaning_completeness` — СЛОВА ПРЕДЕЛА, а не признак. Значения «доказана» у ключа не бывает и до ведомости атомарных обязательств (волна 19: по каждой клаузе перечень обязательств — числовых и нечисловых, — у каждого обязательства свой исход, второй независимый читатель, счётчики покрытия по обязательствам) быть не может: машинного доказательства смысловой полноты естественного языка у производителя нет, и объявлять его нечем. Пакет без комплекта заморозки покрытия не заявляет вовсе (`coverage` отсутствует) — предел там называть не о чем.

Потребитель читает ключ как справку карточки пакета: запуск он не блокирует и гейтом не пересчитывается (пересчитывать в нём нечего — это слова производителя о границе собственного доказательства). Читателю ЗАПРЕЩЕНО выводить из зелёного `coverage` вывод «все нормы документов перенесены в ВМП»: доказано перечисленное выше и не более. Версия спецификации (`SPEC_VERSION`) не меняется — по образцу второго и третьего дополнений: ключ необязательный, читатель, который его не знает, читает пакет как раньше (принцип 1.10 п. 7 — неизвестные ключи игнорируются); пакеты, выпущенные до 12.09.2026, читаются прежним законом «предел не объявлен», и молчание пакета пределом не отменяется — он тот же.

Те же слова несут карточка прогона (блок «Четыре принципа ВМП», строка «Биекция: факты покрытия», поле `meaning_completeness`), руководство 10 и таблица четырёх принципов: носитель слов один — `cdpm.coverage.MEANING_GAP`.

### A12: необязательное сопровождение ведомостью обязательств

В интеграционной реализации при наличии `exchange/obligations.json` пакет
сохраняет её исходные байты в `obligations-ledger.json` и добавляет
`obligations-report.json`, рассчитанный по точным выпускаемым байтам
`model.json`. Оба файла входят в обычный список `manifest.files` с SHA-256.
Сводка `manifest.obligations` называет файлы, форму, актуальность,
непроверенную смысловую полноту и границу независимости читателей.

Это доказательное сопровождение, не новый допуск исполнения и не заявление
полноты: `meaning` остаётся `not_proven`. Устаревшая или некорректная
ведомость не исправляется автоматически; её исходные байты и отрицательный
статус сохраняются. Изменение ведомости во время сборки или невозможность
прочитать её без потерь останавливают передачу свидетельств. Без ведомости
новых файлов и ключа нет — прежний предел смысловой полноты сохраняется.
Дополнение не включает SPEC 1.20 на площадке и не заменяет его предпосылки.

## Ревизия 1.20 — согласованный контракт, подготовка к включению

Основание: П0 v1.13, §0.1 и §11.2 п.1, SHA-256
`93403A20AD972EB64B3342623A8467C705BC46B71835D592E0CFE4710B986567`.
Номер 1.20 уже согласован для проекции `objective.json` и ключей
манифеста `families`/`support`. Посадка `landing/2` относится к отдельной
ревизии 1.21; это дополнение не вводит её под номером 1.20.

Статус этой записи — подготовка спецификации к общей интеграции.
Она не меняет текущую константу производителя `SPEC_VERSION = "1.18"`,
не активирует новую ревизию на площадке и не подтверждает готовность
выпуска. Сам номер ревизии не является решением о выпуске каталога.

При включении 1.20 действуют следующие согласованные обязанности:

- `objective.json` сверяется с проекцией `model.json` общим модулем
  `vmp.objective_projection`; направление берётся из каталога.
  Отсутствие нужного словаря не заменяется подразумеваемым направлением.
- `families` переносит сведения об использованных семьях; готовность
  и проверка пакета не скрывают недостающие обязательные параметры
  наличием или отсутствием вопроса анкеты.
- `support` переносит проекцию свидетельства точного каталога по
  использованным семьям и критериям. Совпадение снимка с местным
  свидетельством проверяется отдельно от разрешения исполнения для
  конкретного продукта, его версии, задачи и режима. Одного наличия
  блока или совпадения его отпечатка для исполнения недостаточно.
- Отсутствующее, неподтверждённое или несовместимое свидетельство
  останавливает затронутый путь. Если производитель отказал в выпуске,
  не требуется сначала создавать негодный пакет ради отказа приёмника.

Включение проверяется на согласованной общей версии производителя и
потребителя с подходящим каталогом, утверждённым свидетельством поддержки
и актуальными привязками. Акт выпуска каталога и его предпроверки
сохраняются; тестовое заполнение `approved` их не заменяет. Менять
ревизию отдельно от проверки этих предпосылок нельзя.

Проверяемая граница — реальный экспорт ZIP, гейт, полный приём пакета
и проверка выбранного исполнения: здоровый случай допускается,
подмена снимка и отсутствие подтверждения не проходят молча. Подмена
константы версии в тесте доказывает только соответствующую ветвь кода,
не факт её включения в выпускаемом продукте и не работу решателя.

Ранее выпущенные пакеты 1.18 не переписываются. Отсутствие у них нового
блока остаётся явно несудимым по закону 1.20, а не положительным
свидетельством поддержки. Эта запись не расширяет их прежний допуск
исполнения и не меняет отдельные правила миграции и отката.
